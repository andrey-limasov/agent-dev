# Мульти-агентная разработка приложений

> **Контекст:** Курс для 4 курса бакалавриата (108 часов). Связан с курсом "Конфигурирование приложений": выпускной проект общий, у команды два репозитория — бэкенд (строится в "Конфигурировании") и мульти-агентный помощник разработчиков этого бэкенда (строится здесь).

Устройство методического репозитория курса: структура и связи документов, педагогическая концепция, стек, правила разработки материалов.

## Модель веток

Репозиторий живёт в двух ветках, подключённых через `git worktree`:

| Ветка | Рабочая папка | Что содержит |
|---|---|---|
| `main` | `multi-agent-all/multi-agent/` | Материалы для студентов |
| `teacher` | `multi-agent-all/multi-agent-teacher/` | Всё из `main` + преподавательские материалы (`workshops-teacher/`, файлы `*-teacher*`) |

- В `main` файл `.gitignore` скрывает `*-teacher*` и `workshops-teacher/`; в `teacher` эти правила удалены.
- Общие документы правятся только в `main`, затем `git merge main` в рабочей папке `teacher`. Ветка `teacher` в `main` не мержится.
- Преподавательский файл создаётся только в `multi-agent-teacher/`: в рабочей папке `main` `.gitignore` его молча проигнорирует.
- Из студенческих документов нельзя ссылаться на `workshops-teacher/` — в `main` этих файлов нет.
- Ветка `main` публикуется в открытом репозитории [github.com/andrey-limasov/agent-dev](https://github.com/andrey-limasov/agent-dev) — в нём только она. Ветка `teacher` живёт только в приватном репозитории курса и студентам недоступна.

### Как студенту получить материалы

Один раз — клон в любой рабочий каталог (на практиках удобнее родительский каталог клонов бэкенда и помощника):

```bash
git clone https://github.com/andrey-limasov/agent-dev
```

**Как понять, что получилось.** Первая строка вывода — `Cloning into 'agent-dev'...`, ошибок нет; `ls agent-dev/templates` показывает каталог шаблонов (PowerShell: `Test-Path agent-dev\templates` печатает `True`). Дальше перед каждым занятием — `git -C agent-dev pull`. В материалах путь к этому каталогу обозначен `<клон курса>`.

**Если не получилось.** `git: command not found` — не установлен Git ([git-scm.com/downloads](https://git-scm.com/downloads), 5 минут). Сеть не пускает к GitHub (`Could not resolve host`, таймаут) — на странице репозитория Code → Download ZIP, распакуйте архив; `<клон курса>` — распакованный каталог `agent-dev-main`, обновление — скачать архив заново.

## Зависимости между документами

```
ROADMAP.md (что создавать следующим)
    ↓ (порядок производства материалов)
course-overview.md
    ↓ (определяет стек и философию)
syllabus.md
    ↓ (детализирует по неделям)
workshops/workshop-N.md ←→ workshops-teacher/workshopN/workshop-N-scenario.md (ветка teacher)
    ↓ (задания для студентов)        ↑ (методическое обоснование)
workshops/practice-N.md
    ↓ (требования к коду)
definition-of-done-ai.md
    ↓ (критерии оценки)
project-requirements-ai.md
```

**Правило:** При подготовке нового материала (например, `workshop-3.md`):
0. Прочитать `ROADMAP.md` → понять, какой артефакт следующий в очереди
1. Прочитать `syllabus.md` → понять место модуля в программе
2. Прочитать `course-overview.md` → соблюсти педагогические принципы
3. Прочитать предыдущий воркшоп → обеспечить преемственность
4. Прочитать `definition-of-done-ai.md` → убедиться, что задание ведёт к DoD

## Педагогическая концепция (КРИТИЧНО при подготовке материалов)

### Запрещено:
- "Говорящая голова" — лекции в формате монолога
- Live coding на лекциях (код только на практиках)
- Готовые ответы без процесса открытия
- Передача фактологии, которую можно найти в документации

### Обязательно:
- **Flipped Classroom:** теория вне аудитории, очное время — для применения
- **Problem-Based Learning:** каждая тема начинается с реальной проблемы
- **Project-Based Learning:** всё привязано к выпускному проекту
- **Конструктивизм:** студенты сами "изобретают" концепции через решение задач
- **Peer Review:** взаимная оценка кода и архитектурных решений

### Формат занятий:
- **Нечётная неделя:** Лекция-воркшоп (90 мин) — обсуждение, проектирование, презентации
- **Чётная неделя:** Практика (180 мин) — Pair Programming, код, интеграция

## Технологический стек

### Обязательные технологии:
- **Python 3.11–3.13 (CrewAI не поддерживает 3.14)** — основной язык
- **FastAPI** — фреймворк бэкенда из курса "Конфигурирование", с которым работает помощник (читает код и OpenAPI-схему); в самом помощнике не обязателен
- **Ollama** — локальный запуск LLM (бесплатно, без API-ключей)
- **Qwen3:4b-instruct** — рекомендуемая локальная модель (2,5 ГБ, есть возможность tools). Альтернатива покрупнее — **Qwen2.5:7b**. Внимание: модель для агента обязана поддерживать function calling: у `qwen2.5-coder` возможности tools нет, Ollama отклоняет такие запросы с ошибкой `does not support tools`
- **Облачный OpenAI-совместимый провайдер** — OpenRouter (бесплатные модели, регистрация без карты) или Yandex AI Studio (оплата рублями); нужен для проверки переключения провайдеров
- **pydantic-settings** — управление конфигурацией через `.env`
- **pytest + unittest.mock** — тестирование с мокированием LLM
- **ChromaDB** — векторное хранилище для RAG в репозитории помощника (альтернатива: **pgvector** в собственном контейнере помощника, не в БД бэкенда)

### Фреймворки для мульти-агентов (выбор команды через ADR):
- CrewAI
- LangGraph
- LangChain
- Чистый Python (без фреймворка)

### Репозиторий бэкенда (из курса "Конфигурирование") — объект работы помощника:
- Код FastAPI-приложения и OpenAPI-схема (`/openapi.json` работающего приложения) — что помощник читает и анализирует
- Docker Compose (FastAPI + PostgreSQL) — локальный стенд, на котором помощник получает OpenAPI-схему
- Конфигурация линтера и pre-commit — по ним помощник проверяет сгенерированный код
- PR-процесс и CI/CD пайплайн (GitHub Actions / GitLab CI) — через них результат помощника попадает в бэкенд
- PostgreSQL, миграции, деплой на VPS — зона "Конфигурирования"; помощник их не меняет

## Выпускной проект

### Концепция:
Выпускной проект общий для двух курсов, у команды **два репозитория**:
- **Курс "Конфигурирование":** бэкенд — FastAPI, БД, Docker, CI/CD, деплой
- **Курс "Мульти-агенты":** помощник команды разработчиков этого бэкенда — генерация кода и тестов, ревью, анализ кода. Живёт в отдельном репозитории: свой venv, `.env`, зависимости, CI

Бэкенд для помощника — объект работы: помощник его читает и анализирует, а изменения в него вносят люди обычным Pull Request. В репозитории бэкенда ради помощника ничего не правится. Помощника запускают командой из его репозитория (CLI) и job в его CI (в CI — только моки LLM).

### Пример архитектуры:
```
┌──────────────────────────────┐          ┌──────────────────────────────┐
│ Репозиторий бэкенда          │          │ Репозиторий помощника        │
│ (курс "Конфигурирование")    │  чтение  │ (<проект>-assistant)         │
│                              │◄─────────│                              │
│ FastAPI + PostgreSQL         │          │ Crew: Исследователь → Кодер  │
│ main.py, /health,            │          │       → Ревьюер              │
│ /openapi.json                │          │ Tools: find_endpoint,        │
│ Docker Compose, CI/CD        │   Pull   │   read_file, run_linter      │
│                              │◄─────────│ Результат: тесты, ревью,     │
│                              │ Request  │   отчёт → PR делают люди     │
│                              │ (люди)   │ Запуск: CLI + job в CI       │
└──────────────────────────────┘          └──────────────────────────────┘
```

### Definition of Done (AI-часть):
1. 2+ агента с чёткими ролями
2. Кастомные Tools (включая code-analysis)
3. RAG для работы с документацией проекта
4. Мокирование LLM в тестах (CI/CD остаётся зелёным)
5. Переключение моделей через `pydantic-settings`
6. ADR с обоснованием выбора фреймворка
7. Помощник в отдельном репозитории; бэкенд меняется только через Pull Request, который принимают люди

## Ограничения и предупреждения

1. **Бюджет на API:** Студенты работают в рамках бесплатных лимитов облачного провайдера (OpenRouter: бесплатные модели, 50 запросов в сутки). Локальная разработка через Ollama обязательна.

2. **CI/CD интеграция:** AI-тесты НЕ должны вызывать реальные LLM в CI/CD пайплайне. Только моки.

3. **Командная работа:** Все материалы рассчитаны на команды 3-4 человека. Индивидуальные задания не предусмотрены.

4. **Синхронизация с "Конфигурированием":** Помощник работает над репозиторием бэкенда своей команды и опирается только на то, что там есть к этой неделе. Изолированные AI-компоненты, не связанные с бэкендом команды, не засчитываются; правки в бэкенде ради помощника не делаются.

5. **Оценивание 360°:** 50% преподаватель, 25% другие команды, 25% сокомандники (с коэффициентом вклада 0.5–1.2).

6. **Источник истины по темам — `syllabus.md`.** Если названия или номера циклов в `ROADMAP.md`, воркшопах или практиках расходятся с программой — прав `syllabus.md`, остальное нужно править.

7. **Векторная БД одна на курс:** ChromaDB в репозитории помощника по умолчанию, pgvector — как альтернатива только в собственном контейнере помощника (БД бэкенда помощник не использует). Другие варианты (FAISS, Qdrant и т. п.) в материалах курса не используются.
