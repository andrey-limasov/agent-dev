# Технические требования к AI-части итогового проекта

**Курс:** Мульти-агентная разработка приложений  
**Формат:** Командный проект (3-4 человека, те же команды, что и в курсе "Конфигурирование")  
**Стек:** Python 3.11–3.13 (CrewAI не поддерживает 3.14), CrewAI / LangChain, Ollama + облачный OpenAI-совместимый провайдер, ChromaDB / pgvector  
**Статус:** Базовые требования для AI-компонентов (помощник работает с репозиторием бэкенда команды)

---

## 🎯 Цели AI-части проекта

1. **Автоматизация:** Автоматизировать задачи разработчиков бэкенда, который команда строит в курсе "Конфигурирование", там, где жёстко закодированная логика не справляется: генерация кода и тестов, ревью, анализ кода с проверкой результата.
2. **Встраивание в процесс разработки:** Мульти-агентный помощник живёт в отдельном репозитории, бэкенд читает и анализирует, а изменения предлагает через Pull Request, который принимают люди. Запуск — командой из репозитория помощника (CLI) и job в CI.
3. **Надежность:** Обеспечить предсказуемость и тестируемость AI-компонентов, несмотря на недетерминированную природу LLM.

---

## 🤖 Минимальный функциональный продукт (MVP) для AI-части

Каждая команда должна реализовать **минимум** следующий AI-функционал, соответствующий выбранной предметной области проекта:

### 1. Мульти-агентная оркестрация (Crew)

**Требования:**
- Реализована система из **минимум 2-х специализированных агентов**, работающих совместно над одной задачей.
- Использован паттерн оркестрации: последовательный (Sequential) или иерархический (Hierarchical/Manager).
- Каждый агент имеет четко определенную:
  - **Роль** (Role): например, "Senior Data Analyst", "Code Reviewer", "Support Triage Specialist".
  - **Цель** (Goal): что агент должен достичь.
  - **Backstory**: контекст и стиль поведения (влияет на промпт).
- Агенты передают результаты друг другу (output одного является input для другого).

### 2. Использование инструментов (Tool Use / Function Calling)

**Требования:**
- Минимум **2 кастомных инструмента (Tools)**, реализованных как Python-функции и переданных агентам.
- **Обязательный инструмент:** Инструмент для работы с кодовой базой или файловой системой проекта (например, `read_file`, `search_codebase` (аналог ctags/grep), или запуск линтера `ruff check`).
- **Второй инструмент:** Над кодом, контрактом или процессом бэкенда (например, `find_endpoint` — поиск обработчика эндпоинта, получение OpenAPI-схемы работающего бэкенда, получение diff Pull Request, разбор отчёта CI).
- Инструменты должны иметь четкие описания (description), чтобы LLM понимала, когда и как их вызывать.
- Реализована обработка ошибок при вызове инструментов (агент должен получить сообщение об ошибке и попытаться скорректировать действие, а не упасть).

### 3. Retrieval-Augmented Generation (RAG)

**Требования:**
- Реализован пайплайн RAG для предоставления агентам внешнего контекста.
- **Источник знаний:** Документация и код бэкенда (README, ADR, `CONTRIBUTING.md`, docstrings), документация самого помощника.
- **Векторизация:** ChromaDB в репозитории помощника (по умолчанию) или pgvector в собственном контейнере помощника; БД бэкенда для векторов не используется.
- **Процесс:** Текст разбивается на чанки (chunking), векторизуется (embeddings), сохраняется в БД. Агент использует Tool для семантического поиска перед генерацией ответа.

### 4. Управление памятью и контекстом

**Требования:**
- Реализована краткосрочная память (контекст текущего выполнения Crew).
- Для RAG реализована долгосрочная память (векторное хранилище).
- (Опционально, но рекомендуется) Использование `Memory` модуля CrewAI или LangChain для сохранения краткой истории взаимодействий между сессиями.

### 5. Конфигурация и переключение моделей

**Требования:**
- Код агентов **не содержит жестко заданных API-ключов или названий моделей**.
- Используется `pydantic-settings` (тот же, что в курсе "Конфигурирование" с недели 7; здесь нужен с недели 2) для управления:
  - Выбором провайдера (облачный OpenAI-совместимый или локальный Ollama).
  - Названием модели (например, свободная модель на OpenRouter или `qwen3:4b-instruct` в Ollama).
  - Параметрами генерации (temperature, max_tokens).
- Помощник должен корректно работать как с облачным провайдером, так и с локальной Ollama-моделью (при наличии ресурсов). Модель в обоих случаях обязана поддерживать вызов функций.

## 🏗️ Архитектурные требования

### Встраивание в процесс разработки

Помощник — не изолированный скрипт и не функция продукта для его пользователей: он работает над репозиторием бэкенда своей команды.
1. **Отдельный репозиторий:** свой venv, `.env`, `requirements.txt`, CI. Путь к бэкенду — настройка `AI_REPO_ROOT`.
2. **Бэкенд — только чтение:** инструменты читают и анализируют код, OpenAPI-схему, diff; файлы бэкенда помощник не изменяет. В репозитории бэкенда ради помощника ничего не правится.
3. **Изменения — только через Pull Request:** результат помощника (тесты, код, замечания ревью) человек проверяет и вносит в бэкенд обычным Pull Request.
4. **Точки запуска:** по запросу разработчика — командой из репозитория помощника (CLI); в CI репозитория помощника — job на каждый Pull Request (тесты и сценарий на моках LLM).

### Обработка ошибок и Guardrails

**Требования:**
- Реализован механизм **Retry** при сбое вызова LLM или инструмента (минимум 2 попытки).
- Реализован **Fallback**: если сложная модель недоступна или превышает лимит, система переключается на более простую модель или возвращает понятное сообщение пользователю ("Временно недоступно, попробуйте позже").
- Валидация вывода агента: если агент должен вернуть JSON, используется структура Pydantic для валидации ответа (например, через `OutputParser` или `StructuredOutput`).

## 🧪 Тестирование AI-компонентов

**Требования:**
- Написаны unit-тесты для **кастомных инструментов (Tools)** (без вызова LLM).
- Написаны интеграционные тесты для **Crew/агентов** с использованием **мокирования (mocking)** ответов LLM.
  - *Запрещено* делать реальные вызовы к облачному провайдеру или Ollama в CI/CD пайплайне (это медленно, нестабильно и тратит лимиты).
  - Используйте библиотеки типа `pytest-mock` или кастомные фикстуры, возвращающие предопределенные JSON-ответы.
- Покрытие тестами AI-логики: минимум 40% (сложнее достичь 60% из-за моков, но инструменты должны быть покрыты хорошо).

## 📝 Примеры AI-сценариев для тем проектов

### 1. Система управления задачами (Task Tracker)
- **Агент-Генератор тестов:** Берёт OpenAPI-схему работающего бэкенда, находит эндпоинты задач, генерирует pytest-тесты по Pydantic-контракту и проверяет их линтером через Tool; результат — файл тестов, который команда вносит в бэкенд Pull Request.
- **Агент-Ревьюер кода:** По diff Pull Request вызывает `ruff` и `mypy` через Tools, анализирует вывод и готовит текст ревью на естественном языке; публикует его в PR человек.

### 2. Система учета заявок (Help Desk)
- **Агент-Исследователь (RAG):** Отвечает разработчику на вопрос вида «где обрабатывается смена статуса заявки и что при этом проверяется?»: ищет по коду и документации бэкенда (README, ADR) и возвращает файлы и строки с указанием источников.
- **Агент-Кодер:** По описанию задачи и найденному контексту готовит черновик изменения (эндпоинт и тест к нему); человек проверяет и оформляет Pull Request.

### 3. Система управления библиотекой
- **Агент-Аналитик модуля:** Объясняет новому участнику команды устройство бэкенда (роутеры, модели, зависимости), строит карту эндпоинтов по OpenAPI-схеме и находит эндпоинты без тестов.

### 4. API для сервиса доставки еды
- **Агент-Документатор:** По diff Pull Request готовит черновик записи CHANGELOG и ADR, проверяет, что изменения контракта API отражены в документации.

## ⚠️ Ограничения и допущения

### Ограничения:
1. **Бюджет:** Использование только бесплатных лимитов облачного провайдера или локальных моделей через Ollama. Команды должны самостоятельно мониторить расход токенов.
2. **Сложность:** Не требуется создавать полностью автономных агентов, способных к бесконечному self-improvement. Фокус на управляемых, ограниченных по времени выполнения (timeout) сценариях.
3. **Интерфейс:** Помощник запускается командой из своего репозитория (CLI); результат — файлы и вывод в терминале. Чат-интерфейс — бонус, но не обязателен.

### Допущения:
1. **Качество генерации:** Оценивается не "креативность" текста, а корректность использования инструментов, структура вывода (JSON) и устойчивость к ошибкам.
2. **Инфраструктура:** Векторная БД (ChromaDB) может работать в памяти или в локальном файле для упрощения деплоя, если иное не оговорено с преподавателем.

## 📋 Этапы реализации AI-части (по `syllabus.md`)

- **Недели 1-2:** Репозиторий помощника, окружение (Ollama + облачный провайдер, `pydantic-settings`), первый агент с одним Tool над кодом бэкенда.
- **Недели 3-4:** Инструменты для анализа кода бэкенда (`read_file`, `search_codebase`, `run_linter`) с безопасной обработкой ошибок.
- **Недели 5-6:** RAG по документации и коду бэкенда.
- **Недели 7-8:** Crew из 2–3 агентов (например, Исследователь → Кодер → Ревьюер), цикл «генерация кода → линтер → исправление».
- **Недели 9-10:** OpenAPI-схема работающего бэкенда → pytest-тесты по Pydantic-контракту (Structured Output), таймауты и retry, запуск из CLI; лучшие тесты — Pull Request в бэкенд.
- **Недели 11-12:** Guardrails и fallback, pytest-тесты помощника с моками LLM, job в CI репозитория помощника.
- **Недели 13-14:** Логирование трасс (ReAct), кэш, аудит защиты от prompt injection.
- **Недели 15-16:** ADR по AI-архитектуре, подготовка демо на бэкенде команды, защита.

## 💡 Бонусные задачи (по желанию)

1. **Human-in-the-loop:** Реализация точки остановки, где агент запрашивает подтверждение у человека перед выполнением критического действия (например, создание ветки или Pull Request в репозиторий бэкенда).
2. **Оценка качества (LLM-as-a-Judge):** Автоматизированный скрипт, который оценивает ответы агента по заданным критериям (релевантность, формат) с помощью отдельного вызова LLM.
3. **Observability:** Интеграция с LangFuse или LangSmith для визуализации цепочек рассуждений и затрат токенов.
4. **Streaming:** Потоковый вывод ответа агента в терминал при запуске из CLI.

**Важно:** Бонусные задачи не компенсируют невыполненный MVP. Сначала — стабильная работа базовых агентов и инструментов, потом — дополнительные фичи.
