# Как мы работаем с репозиторием

Документ для всех, кто вносит изменения в «Заметки». Если правило мешает,
предложите поправку Pull Request к этому файлу, а не обходите его.

## Ветки

Работаем по GitHub Flow: `main` всегда рабочий, изменения приходят только
через Pull Request.

- Новая ветка — от свежего `main`: `git switch main`, `git pull`,
  затем `git switch -c feature/<кратко>`.
- Имя ветки — латиница в kebab-case: `feature/delete-note`, `fix/health-status`.
- Одна ветка — одна задача. После слияния ветку удаляем.

## Коммиты

Сообщения — по Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`.
Первая строка — до 72 символов, в повелительном наклонении: `feat: add note deletion`.
Один коммит — одно логическое изменение: форматирование и логику не смешиваем.

## Окружение

- Python 3.11–3.13, своё виртуальное окружение `.venv` в корне репозитория.
- Зависимости: `pip install fastapi uvicorn`. Файл со списком зависимостей
  появится, когда команда выберет менеджер зависимостей.
- Каталог `.venv` в репозиторий не попадает: он указан в `.gitignore`.
- Новая зависимость добавляется в том же Pull Request, где она понадобилась.

## Настройки окружения

Сейчас у сервиса нет значений, которые нельзя публиковать. Когда они появятся
(например, ключ внешнего сервиса), они хранятся только в локальном файле `.env`
в корне репозитория. Файл `.env` указан в `.gitignore` и не коммитится никогда.
В репозиторий кладётся `.env.example` с теми же именами переменных и пустыми
значениями, чтобы новый участник знал, что заполнить.

Если значение всё же попало в коммит, удалить строку недостаточно: значение
считается скомпрометированным, его отзывают и выпускают новое.

## Проверки перед Pull Request

Перед тем как открыть Pull Request, автор проверяет у себя:

1. Ветка обновлена от `main`, конфликтов нет.
2. Сервер запускается командой `uvicorn main:app` без ошибок.
3. `GET /health` отвечает `{"status": "healthy"}`.
4. Новые эндпоинты добавлены в таблицу «Эндпоинты» в `README.md`.
5. У новых функций есть docstring в одну строку.
6. Если в репозитории есть каталог `tests/`, тесты проходят: `python -m pytest -q`.
7. Линтер не находит ошибок: `ruff check .`.
8. В изменениях нет файла `.env` и отладочных `print`.
9. Сообщения коммитов соответствуют разделу «Коммиты».

## Pull Request

- Заголовок — как первая строка главного коммита.
- В описании: что изменено, как проверить, ссылка на задачу.
- Нужен один одобряющий отзыв участника, который не писал этот код.
- Сливаем через Squash and merge, ветку после слияния удаляем.

## Ревью

Ревьюер отвечает в течение одного рабочего дня. Замечание пишется по форме
«заметил → чем грозит → предлагаю». Вопросы стиля, которые ловит линтер,
в ревью не обсуждаются.

## Если нашли ошибку

Создайте задачу с заголовком в одну строку и тремя пунктами: что делали,
что ожидали, что получили. Приложите команду `curl` или шаги в `/docs`,
по которым ошибка повторяется.
