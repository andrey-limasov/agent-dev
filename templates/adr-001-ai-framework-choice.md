## 1. Контекст и проблема

Нам необходимо реализовать интеллектуальный слой для нашего приложения, который сможет:
- Понимать естественный язык пользователя.
- Выполнять действия в системе (создавать задачи, искать информацию).
- Быть легко интегрируемым с основным Backend (FastAPI), разработанным в рамках курса "Конфигурирование приложений".
- Поддерживать переключение между локальными (Ollama) и облачными (OpenAI-совместимый провайдер) моделями без изменения кода.

Главная проблема: выбор архитектурного подхода к созданию агентов. Простого вызова LLM недостаточно, требуется оркестрация, управление памятью и вызов инструментов (Tools).

---

## 2. Рассмотренные варианты

### Вариант А: Самостоятельная реализация Agent Loop на чистом LangChain
- **Описание:** Ручное создание цикла: Prompt → LLM → Parse Tool Call → Execute Tool → Append to History → LLM.
- **Плюсы:** Полный контроль над каждым шагом, минимальное количество зависимостей, глубокое понимание механики.
- **Минусы:** Высокая сложность реализации, необходимость самостоятельно обрабатывать edge-cases (бесконечные циклы, ошибки парсинга), много шаблонного кода.

### Вариант Б: Использование CrewAI
- **Описание:** Высокоуровневый фреймворк, ориентированный на ролевое программирование (Role-Playing). Позволяет легко создавать "Крю" (Crew) из агентов с разными ролями, целями и инструментами.
- **Плюсы:** Минимальный boilerplate-код, встроенная поддержка делегирования задач между агентами, отличная документация, простая интеграция с LangChain Tools.
- **Минусы:** Меньше контроля над низкоуровневым графом выполнения по сравнению с LangGraph, может быть избыточен для простых сценариев с одним агентом.

### Вариант В: Использование LangGraph
- **Описание:** Библиотека для построения циклических, управляемых состоянием графов (Stateful Graphs).
- **Плюсы:** Максимальная гибкость, идеальный контроль над потоком выполнения, нативная поддержка сложных сценариев (human-in-the-loop, циклы).
- **Минусы:** Высокий порог входа, сложность отладки, избыточен для базовых задач курса.

---

## 3. Принятое решение

Мы выбрали **Вариант Б (CrewAI)** в качестве основного фреймворка для оркестрации, с использованием **LangChain Tools** для реализации кастомных инструментов.

**Обоснование:**
1. **Скорость разработки:** CrewAI позволяет быстро создать работающий прототип мульти-агентной системы, что критично в условиях ограниченного времени курса.
2. **Ролевая модель:** Концепция "Роли" и "Цели" агента идеально ложится на нашу предметную область (например, "Агент-классификатор" и "Агент-исполнитель").
3. **Совместимость:** CrewAI нативно поддерживает LangChain, что даёт нам доступ к огромной экосистеме готовых Tools и интеграций (включая работу с векторными БД для RAG).
4. **Конфигурируемость:** Мы можем легко внедрить `pydantic-settings` для управления параметрами LLM (модель, температура, провайдер), не меняя логику Crew.

**Решение по Tools:**
Мы реализуем кастомные Tools с использованием декоратора `@tool` из `crewai.tools`. Каждый Tool будет:
- Иметь строгую типизацию входных параметров.
- Содержать подробный docstring (это промпт для LLM).
- Возвращать структурированные данные (JSON), а не неформатированный текст.
- Быть покрыт изолированными unit-тестами (без вызова реальной LLM).

## 3а. Дизайн первого Tool

Заполняется по первому Tool команды (практика 1). Пишите конкретно: каждый пункт ревьюер должен проверить по коду и логу.

| Что | Наше решение | Почему так (и что отвергли) |
|---|---|---|
| Имя для модели (аргумент `@tool`) | `get_...` | |
| Назначение — одно предложение из docstring | «...; вызывай, когда ...» | |
| Вход: параметры, типы, допустимые значения | `status: str` — одно из `new`, `in_progress`, `done` | |
| Выход при успехе | `{"status": "ok", ...}` | |
| Выход при ошибке | `{"status": "error", "message": "<что не так и как исправить>"}` | |
| Пустой результат | успех с пустым списком, не ошибка | |
| Откуда данные сейчас и потом | словарь-заглушка в модуле → эндпоинт FastAPI (цикл 5) | |
| Конфигурация LLM | `pydantic-settings`, `.env`, одна точка создания `get_llm()` | |

**Безопасный возврат.** Тело Tool не выбрасывает исключений: любая ошибка возвращается строкой в формате выше, из текста понятно, что исправить. Отдельный исход — проверка схемы аргументов фреймворком до тела Tool (пропущенный обязательный параметр, неверный тип): запишите, как она проявилась у вас.

**Что показала трасса.** Вызывал ли агент Tool, какие аргументы подставлял, как вёл себя на ошибке, отличались ли локальная и облачная модели. Ссылки на файлы логов.

## 4. Последствия решения

### Позитивные:
- Команда может сосредоточиться на бизнес-логике Tools и промпт-инжиниринге, а не на написании инфраструктуры Agent Loop.
- Код становится декларативным и легко читаемым.
- Проще масштабировать систему: добавление нового агента или инструмента требует минимальных изменений.

### Негативные и риски:
- **Риск:** CrewAI может скрывать детали выполнения, что усложняет отладку, когда агент "застревает" в цикле.
  - *Митигация:* Обязательное использование `verbose=True` при отладке и строгое ограничение `max_iter` (максимального количества итераций) для агентов.
- **Риск:** Зависимость от внешней библиотеки, которая может обновляться с breaking changes.
  - *Митигация:* Фиксация версий зависимостей в `pyproject.toml` / `requirements.txt` (контролируется курсом "Конфигурирование").

---

## 5. Критерии пересмотра решения

Мы вернёмся к пересмотру этого решения (например, в сторону LangGraph), если:
1. Нам потребуется реализовать сложный сценарий с циклами и условиями, который CrewAI не может выразить декларативно.
2. Производительность или стоимость вызовов LLM станет критической, и потребуется тонкий контроль над каждым токеном на уровне графа.
3. Появится требование "Human-in-the-loop" (одобрение действия человеком перед выполнением Tool), которое сложнее реализовать в CrewAI, чем в LangGraph.
