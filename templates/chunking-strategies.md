Теория — в СРС к циклу 3 ([`materials-3.md`](../workshops/materials-3.md), «После воркшопа»), здесь только то, что нужно для кода. Читать 10 минут.

## 1. Что уже делает каркас

| Шаг | Где в `rag_pipeline.py` | Что происходит |
|---|---|---|
| Разделы по заголовкам | `split_markdown`, `MarkdownHeaderTextSplitter` | Документ режется по `#`, `##`, `###`. Заголовки внутри блоков кода (```` ``` ````) не считаются: строка `# комментарий` в примере bash раздел не начинает |
| Длинный раздел | `split_markdown`, `RecursiveCharacterTextSplitter` | Раздел длиннее `CHUNK_SIZE` символов (1500) режется по пустой строке, затем по строке, затем по пробелу. Перекрытия нет (`CHUNK_OVERLAP = 0`). Заголовок, оставшийся без текста, отдельным чанком не становится: он приклеивается к следующему куску |
| Заголовок | `make_chunks` | Цепочка заголовков («README > Эндпоинты») — в метаданных `heading` и в начале текста, по которому считается эмбеддинг. Агенту возвращается текст чанка без этой строки |
| Номера строк | `split_markdown` | `lines` — строки исходного файла, например `19-28`: по ним агент и вы находите место в документе |
| Docstrings | `docstring_chunks` | Каждая docstring модуля, функции, класса бэкенда — отдельный чанк с `symbol` (имя) и `lines` (строка `def`). Целые `*.py` не индексируются |
| Слишком длинный чанк | `embed`, `truncate: false` | Ollama по умолчанию обрезает длинный вход молча. Каркас просит ошибку: `build` остановится и назовёт файлы порции |

Всё, что ниже, — варианты для «TODO по вашей схеме» в `split_markdown` и рядом с `CHUNK_SIZE`.

## 2. Три семейства нарезки и чем они представлены в LangChain

| Семейство | Сплиттер `langchain-text-splitters` | Главные параметры | Когда брать |
|---|---|---|---|
| По длине | `CharacterTextSplitter`, `TokenTextSplitter` | `chunk_size`, `chunk_overlap` | Базовая линия для сравнения (стратегия С1 воркшопа 3). Режет таблицы и предложения |
| По структуре текста | `RecursiveCharacterTextSplitter` | `chunk_size`, `chunk_overlap`, `separators` (по умолчанию `["\n\n", "\n", " ", ""]`), `add_start_index` | Длинный раздел без подзаголовков: сначала абзацы, потом строки |
| По структуре документа | `MarkdownHeaderTextSplitter` | `headers_to_split_on`, `strip_headers` | Markdown с осмысленными заголовками — README, ADR, CONTRIBUTING (стратегия С2) |

Подробности и примеры — [Text splitters](https://docs.langchain.com/oss/python/integrations/splitters/index) (обзор трёх семейств, 5 минут), [Split markdown](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter) (раздел *How to constrain chunk size* — та же комбинация, что в каркасе, 5 минут), [Splitting recursively](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter) (параметры и разделители по умолчанию, 3 минуты).

`chunk_size` у `RecursiveCharacterTextSplitter` по умолчанию считается в **символах** (`length_function=len`), а предел модели эмбеддингов — в **токенах**.

## 3. Три правила с воркшопа 3 и как их выполнить в коде

Правила записаны в разделе 2 вашей схемы. Ниже — что каждое значит для каркаса.

**1. Не резать таблицы, списки и предложения.** Раздел до `CHUNK_SIZE` каркас не режет вовсе. Длинный раздел режется сначала по пустой строке, но таблица Markdown — это строки без пустых строк между ними, и длинная таблица всё равно разрежется по строке: второй кусок останется без шапки. Так было в проверочном прогоне на схеме окружения бэкенда (таблица чек-листа из 9 строк разрезана после пятой: строки 6–9 ушли в отдельный чанк без шапки). Если в вашей схеме «таблицы не режем», один из вариантов — оставлять раздел с таблицей целым, пока он короче предела модели:

```python
HARD_LIMIT = 5000  # символов: меньше предела embeddinggemma (около 7000) с запасом


def _has_table(body: str) -> bool:
    return any(line.lstrip().startswith("|") for line in body.splitlines())

# в split_markdown, вместо `if len(body) <= CHUNK_SIZE:`
        if len(body) <= CHUNK_SIZE or (_has_table(body) and len(body) <= HARD_LIMIT):
```

Цена — большой чанк: он займёт больше места в контексте агента (правило 3).

**2. Заголовок раздела — в метаданные или в начало чанка.** Каркас делает и то и другое. Менять стоит, только если заголовки у вас неинформативные («Раздел 1», «Прочее»): тогда в текст для эмбеддинга полезно добавить имя файла — `f"{rel} > {heading}\n{c['text']}"` в `make_chunks`.

**3. Размер чанка — это «объём» из воркшопа 2.** В контекст агента уходит до `top_k` × размер чанка: с каркасом — до 5 × 1500 символов. Чем крупнее чанк, тем меньше `top_k` можно себе позволить. Ответ, разнесённый по нескольким разделам (вопрос В4 воркшопа), нарезка не спасает: помогает `top_k` больше 1 или второй вызов `search_docs` агентом по найденному разделу.

## 4. Размер чанка: верхняя граница и разумное значение

**Верхняя граница — контекст, с которым Ollama запускает модель.** Длиннее — вход обрезается (или, в каркасе, `build` падает с ошибкой `the input length exceeds the context length`).

| Модель | Контекст в Ollama | Сколько это символов русского Markdown |
|---|---|---|
| `embeddinggemma` | 2048 токенов | около 7000 (замерено на `CONTRIBUTING.md` бэкенда «Конфигурирования») |
| `qwen3-embedding:0.6b` | 4096 токенов (у самой модели 32K, но Ollama по умолчанию запускает с 4096) | примерно вдвое больше |

Префикс из `AI_EMBED_DOC_PREFIX` и строка с заголовком тоже занимают место — оставляйте запас.

**Разумное значение — меньше границы.** Чанк должен содержать один ответ, а не раздел целиком: в исследовании ChromaDB ([Evaluating Chunking Strategies for Retrieval](https://www.trychroma.com/research/evaluating-chunking), разделы *Results* и *Conclusion*, 10 минут) небольшие чанки (около 200 токенов) без перекрытия держатся стабильно хорошо, а крупные с большим перекрытием — среди худших. Для документации курса 800–2000 символов — нормальный диапазон; 1500 в каркасе — середина.

**Перекрытие** (`CHUNK_OVERLAP`) помогает, когда ответ лежит на границе двух кусков одного раздела. Цена — один и тот же текст может вернуться дважды (В3 у стратегии С3 на воркшопе). Перекрытие действует только внутри раздела: заголовки каркас режет без него.

## 5. Docstrings бэкенда

Docstring — отдельный чанк вида «`main.py`, `health_check`: Проверка, что сервис жив.» Короткие англоязычные docstrings («Root endpoint.») поиск по русскому вопросу находит плохо — это ожидаемо, не ошибка нарезки. Ваши варианты (решение — в ADR 003): оставить как есть; не индексировать docstrings короче N слов; склеить docstrings одного файла в один чанк. Бэкенд ради этого не правится: docstrings меняют люди обычным PR в бэкенд.

Документация: [`ast.get_docstring`](https://docs.python.org/3/library/ast.html#ast.get_docstring) — 1 минута.

## 6. Как проверить, что нарезка стала лучше

1. Постройте индекс и снимите таблицу на своих вопросах — это базовая линия:

   ```bash
   python -m ai.tools.rag_pipeline build
   python -m ai.tools.rag_pipeline eval "<ваш посторонний вопрос>"
   ```

2. Поменяйте **одну** вещь (размер, перекрытие, правило для таблиц), снова `build` и `eval`.
3. Сравните столбец «Нужный: место 1–5 или нет» по пяти вопросам. Лучше — если нужный раздел поднялся выше или впервые попал в топ-3 (топ-5), а на остальных вопросах не опустился. Расстояние (`distance`) между разными нарезками напрямую не сравнивайте: важно место, а не число.
4. Изменение, которое ничего не дало, откатите: проще код — меньше ошибок.

Итог — одна-две строки в ADR 003: что пробовали, на сколько вопросов из пяти нужный раздел в топ-3 и в топ-5 до и после.
