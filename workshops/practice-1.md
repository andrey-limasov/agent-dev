# Практика 1. Первый Tool и переключаемая конфигурация LLM

**Длительность:** 180 минут (2 пары)
**Формат:** самостоятельная командная работа по этому руководству. Pair Programming в командах 3–4 человека, в конце — peer review с соседней командой.
**Роль преподавателя:** организационная. Он следит за временем, объявляет стоп-точки, фиксирует прогресс команд и назначает пары для peer review. Всё содержание занятия — в этом файле и по ссылкам из него.

> ⚠️ Руководство рассчитано на то, что вы дойдёте до конца сами. Если шаг не получается — сначала читайте блок «Если не получилось» у этого шага, потом таблицу Troubleshooting в конце файла, потом документацию по ссылке.

**Проверено на:** Windows 11, Python 3.12, `crewai==1.15.22`, `pydantic-settings==2.15.0`, Ollama с моделью `qwen3:4b-instruct` на CPU, OpenRouter (бесплатная модель с tools) — октябрь 2026. Yandex AI Studio, macOS и Linux на этой версии не проверялись. Если читаете заметно позже, сверьте с документацией CrewAI способ объявления Tool (`from crewai.tools import tool`) и параметры класса `LLM`: между мажорными версиями они менялись.

## Что вы сделаете сегодня

**Проблема.** Модель без доступа к вашим данным на вопрос «какие заявки в статусе `new`?» уверенно отвечает выдуманным. Дайте ей функцию — и она передаст в неё `urgent` вместо `new`, а необработанное исключение уронит весь процесс. Сегодня вы строите Tool, который модель вызывает по делу, а неверный вход возвращает ей текстом, по которому она может исправиться.

В конце занятия в вашем репозитории будет:

1. Ветка `feature/agent-tool-1` и Pull Request в базовую ветку с комментариями peer review от соседней команды.
2. `ai/config.py` — конфигурация AI-слоя на `pydantic-settings`, читающая `.env`.
3. `ai/llm_factory.py` — одна функция `get_llm()`, возвращающая LLM для локальной Ollama или для любого облачного провайдера с OpenAI-совместимым API. Переключение — правкой `.env`, без изменения кода.
4. `ai/tools/<ваш_инструмент>.py` — рабочий Tool по спецификации, которую ваша команда защитила на воркшопе 1: с валидацией входа и безопасным возвратом ошибки.
5. `ai/run_agent.py` и закоммиченные логи в `ai/traces/`, в которых видно, что агент **вызвал ваш Tool**, а не придумал ответ.
6. `docs/adr/ai-001-framework-and-first-tool.md` — ADR: выбор фреймворка и дизайн первого Tool.

**Базовая ветка** — та, в которую по регламенту вашей команды вливаются фичи: `main` (GitHub Flow или стратегия ещё не выбрана) или `develop` (GitFlow). Ниже она обозначена `<базовая>`. Pull Request открывается на любом хостинге команды: на GitHub и Gitea это Pull Request, на GitLab — Merge Request.

## Подготовка ДО занятия

Делается дома каждым участником и занимает 1,5–2 часа, из них около часа машина работает сама (установка библиотек и загрузка модели). На паре этого не успеть: одна только установка CrewAI на проверочных машинах шла 23–37 минут.

### 1. Python 3.11–3.13 в окружении проекта (10–20 мин)

CrewAI не устанавливается на Python 3.14 (у пакета ограничение `<3.14`), а установщик с python.org сейчас по умолчанию ставит именно 3.14. AI-слой живёт в том же виртуальном окружении, что и FastAPI-проект из курса «Конфигурирование»: в цикле 5 агент встраивается в приложение, и это один процесс.

В корне репозитория проекта, с активированным окружением, выполните `python --version`.

- `Python 3.11.x`, `3.12.x` или `3.13.x` — переходите к пункту 2.
- `Python 3.14.x` или окружения ещё нет — создайте окружение заново на 3.12. Старый каталог окружения (обычно `venv`) удаляется целиком: кроме установленных пакетов, в нём ничего нет. Если каталога нет, первую строку пропустите.

PowerShell (Windows):

```powershell
Remove-Item -Recurse -Force venv
py -3.12 -m venv venv
venv\Scripts\Activate.ps1
python --version
```

Git Bash (Windows):

```bash
rm -rf venv
py -3.12 -m venv venv
source venv/Scripts/activate
python --version
```

macOS / Linux: `rm -rf venv`, `python3.12 -m venv venv`, `source venv/bin/activate`.

Если команда ведёт проект на uv: `uv venv --python 3.12 --seed` (создаст `.venv`, нужный Python uv скачает сам), активация — `.venv\Scripts\Activate.ps1`, `source .venv/Scripts/activate` или `source .venv/bin/activate`, а пакеты в пункте 2 ставьте через `uv pip install` с теми же аргументами.

**Как понять, что получилось.** `python --version` печатает `Python 3.12.x` (годится 3.11–3.13), а `python -c "import sys; print(sys.prefix)"` — путь внутри вашего репозитория, оканчивающийся на `venv` или `.venv`.

**Если не получилось**

- `py -3.12` отвечает, что такой версии нет, — Python 3.12 не установлен. Если Python ставили через Python install manager (как в «Конфигурировании»), выполните `py install 3.12`; иначе установите 3.12 с python.org и откройте новый терминал.
- PowerShell не даёт выполнить `Activate.ps1` («выполнение сценариев отключено», `running scripts is disabled`) — выполните `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` и повторите активацию.
- `Remove-Item` / `rm` не удаляет каталог: «файл используется другим процессом» — окружение активно в другом окне терминала или в редакторе. Закройте их и повторите.

### 2. Зависимости проекта и AI-слоя (5 мин действий + 25–40 мин установки)

В том же окружении сначала зависимости приложения (если в репозитории уже есть `requirements.txt`), затем библиотеки AI-слоя с точными версиями:

```bash
pip install -r requirements.txt
pip install crewai==1.15.22 pydantic-settings==2.15.0
```

Вторая команда ставит около 140 пакетов и идёт 25–40 минут. Не прерывайте её. В её выводе может быть строка `Successfully uninstalled pydantic-2.14.0` (или другой версии 2.13+): CrewAI 1.15 работает только с `pydantic` ниже 2.13 и сам понижает версию, приложение FastAPI с ней работает. На паре вы закрепите это в `requirements.txt` (шаг 1.2). Если `requirements.txt` вы не ставили, этой строки не будет: pip сразу поставит подходящую `pydantic`.

Проверка (первый импорт идёт до полутора минут, ждите):

```bash
python -c "import crewai, pydantic_settings; print(crewai.__version__)"
```

**Как понять, что получилось.** Напечатано `1.15.22`, traceback нет.

**Если не получилось**

- `No matching distribution found for crewai==1.15.22` или `Could not find a version that satisfies the requirement crewai` — Python вне диапазона 3.11–3.13. Вернитесь к пункту 1.
- `pip install -r requirements.txt` падает с `RuntimeError: uvloop does not support Windows` — файл записан `pip freeze` на Linux или в Docker, а `uvloop` под Windows не ставится. Откройте `requirements.txt` и допишите к строке `uvloop==…` условие, версию не трогайте: `uvloop==0.23.0; sys_platform != "win32"`. Повторите команду: pip напишет `Ignoring uvloop: markers 'sys_platform != "win32"' don't match your environment` и поставит остальное. На Linux и в Docker `uvloop` по-прежнему ставится. Правку закоммитите на паре вместе с зависимостями (шаг 1.2, пункт 6).
- `ResolutionImpossible`, а выше в выводе есть `WARNING: Skipping page https://pypi.org/simple/… Content-Type: Unknown` — это сбой сети, а не конфликт версий. Повторите ту же команду.
- Установка оборвалась по таймауту или с `ReadTimeoutError` — повторите ту же команду: скачанное уже в кеше pip, второй заход быстрее.
- `ModuleNotFoundError` при проверке — пакеты ушли в другое окружение. `python -m pip --version` должен показать путь внутри вашего `venv`.

### 3. Путь А: локальная модель (10 мин + загрузка 2,5 ГБ)

Основной путь: локально и бесплатно. Модель весит 2,5 ГБ — качайте дома, на паре по общему каналу аудитории это не получится.

1. Установить Ollama: [ollama.com/download](https://ollama.com/download), 10 минут.
2. Скачать модель: `ollama pull qwen3:4b-instruct` (2,5 ГБ — [карточка модели](https://ollama.com/library/qwen3), тег `4b-instruct` виден на вкладке Tags). Нужно около 3 ГБ свободной оперативной памяти сверх занятой системой. Если машина мощная и хочется модель крупнее — `qwen2.5:7b` (4,7 ГБ, контекст 32K).
3. Проверить, что модель отвечает: `ollama run qwen3:4b-instruct "скажи привет"`. Ответ печатается, и команда завершается сама. Первый запуск на CPU может занять несколько минут: модель загружается в память.
4. ⚠️ **Проверить, что модель умеет вызывать инструменты.** Это главное требование сегодняшнего занятия, и ему удовлетворяет не каждая модель: у модели в Ollama должна быть возможность **tools** (на карточке модели она указана рядом с размерами). У `qwen2.5-coder` её нет — Ollama просто откажется принимать запрос с инструментами. Проверка (на Windows — в Git Bash):

```bash
curl -s http://localhost:11434/api/chat -d '{
  "model": "qwen3:4b-instruct",
  "stream": false,
  "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
  "tools": [{"type": "function", "function": {
    "name": "get_tasks", "description": "Возвращает задачи по приоритету",
    "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
    "required": ["priority"]}}}]}'
```

   Ожидаемый ответ — JSON, в котором есть `"tool_calls"` с именем `get_tasks`. Если вместо этого пришло `{"error":"... does not support tools"}` — модель для занятия не годится, берите другую с возможностью tools. `{"error":"model '...' not found"}` — модель не скачана, вернитесь к пункту 2. Если пришёл обычный текстовый ответ без `tool_calls` — модель инструменты принимает, но в этом запросе решила не вызывать; для занятия это допустимо, вернёмся к этому в шаге 3.2.

**Если не получилось.** `ollama pull` падает с `redirect target not allowed … resolves to non-public 198.18.x.x` — загрузку ломает VPN или прокси с подменой DNS (fake-IP). Отключите VPN или режим TUN на время загрузки либо скачайте модель в другой сети.

### 4. Путь Б: облачный провайдер (15–25 мин)

Запасной на занятии и обязательный для домашнего задания. Нужен ключ любого облачного сервиса с **OpenAI-совместимым API**, у которого модель умеет вызывать функции. Какой именно сервис — курсу всё равно: смысл задания в том, что провайдер меняется правкой `.env`, а не кода. Ключ нужен **минимум одному человеку в команде**; если путь А не завёлся ни у кого — каждому. Три рабочих варианта:

| Провайдер | Что нужно для регистрации | `CLOUD_BASE_URL` | `CLOUD_MODEL` | `CLOUD_PROJECT` |
|---|---|---|---|---|
| **OpenRouter** — самый простой | почта или вход через Google/GitHub, карта не нужна | `https://openrouter.ai/api/v1` | бесплатная модель **с поддержкой tools** со страницы моделей | пусто |
| **Yandex AI Studio** — российский, оплата рублями | аккаунт Yandex Cloud с платёжным аккаунтом, каталог, сервисный аккаунт и API-ключ | `https://ai.api.cloud.yandex.net/v1` | `gpt://<идентификатор_каталога>/yandexgpt-5.1` | идентификатор каталога |
| Свой или университетский эндпоинт (vLLM, LM Studio, корпоративный шлюз) | как договоритесь с владельцем | адрес шлюза | имя модели на шлюзе | пусто |

1. **Заведите ключ.**
   *OpenRouter:* зарегистрируйтесь на [openrouter.ai](https://openrouter.ai/docs/quickstart), создайте ключ в разделе Keys. На [странице моделей](https://openrouter.ai/models) включите фильтры бесплатных моделей и поддержки tools — бесплатных моделей много, но функции умеют не все. Бесплатные модели работают без покупки кредитов, действующие лимиты — 50 запросов в сутки и 20 в минуту ([Limits](https://openrouter.ai/docs/api-reference/limits)). Список меняется, поэтому имя модели берите со страницы в день работы.
   *Yandex AI Studio:* аккаунт, каталог, сервисный аккаунт и [API-ключ](https://yandex.cloud/ru/docs/iam/operations/authentication/manage-api-keys) с областью действия для языковых моделей — по документации Yandex Cloud. Специфично для курса одно: идентификатор каталога (`b1g...`) — это `CLOUD_PROJECT`, и он же стоит внутри имени модели `gpt://<каталог>/...`; без него запрос не уйдёт. Вызов функций в OpenAI-совместимом режиме — [документация](https://aistudio.yandex.ru/docs/ru/ai-studio/operations/generation/completions-function.html), список моделей — [страница моделей](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models).

2. **Ключ показывается один раз** — сохраните сразу.

3. **Проверьте ключ, адрес и модель дома, а не на паре** — той же проверкой на вызов функции, что и для локальной модели. Подставьте свои значения. Строка `OpenAI-Project` нужна **только Yandex AI Studio** (туда идёт идентификатор каталога); для остальных провайдеров удалите её целиком.

   Git Bash (ставится вместе с Git) / Linux / macOS:

```bash
curl -s <ВАШ_CLOUD_BASE_URL>/chat/completions \
  -H "Authorization: Bearer <ВАШ_КЛЮЧ>" -H "Content-Type: application/json" \
  -H "OpenAI-Project: <ВАШ_КАТАЛОГ>" \
  -d '{"model": "<ВАША_МОДЕЛЬ>",
       "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
       "tools": [{"type": "function", "function": {
         "name": "get_tasks", "description": "Возвращает задачи по приоритету",
         "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
         "required": ["priority"]}}}]}'
```

   PowerShell (5.1 и 7). JSON с кавычками PowerShell передаёт в `curl.exe` по-разному в разных версиях, поэтому тело запроса сначала пишется в файл `body.json` (UTF-8 без BOM), а `curl.exe` читает его через `@`. Пишите именно `curl.exe`: просто `curl` в Windows PowerShell 5.1 — другая команда.

```powershell
$body = @'
{"model": "<ВАША_МОДЕЛЬ>",
 "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
 "tools": [{"type": "function", "function": {
   "name": "get_tasks", "description": "Возвращает задачи по приоритету",
   "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
   "required": ["priority"]}}}]}
'@
[IO.File]::WriteAllText("$PWD\body.json", $body)
curl.exe -s <ВАШ_CLOUD_BASE_URL>/chat/completions `
  -H "Authorization: Bearer <ВАШ_КЛЮЧ>" -H "Content-Type: application/json" `
  -H "OpenAI-Project: <ВАШ_КАТАЛОГ>" `
  -d "@body.json"
Remove-Item body.json
```

   Ожидаемый ответ — JSON, в котором в `choices[0].message` есть `tool_calls` с именем `get_tasks`. Запишите работающую четвёрку «адрес — модель — ключ — каталог (если он нужен)»: на занятии она пойдёт в `.env`.
   Ответ пришёл, но `tool_calls` в нём нет, а есть обычный текст — модель инструменты приняла, но вызывать не стала: для занятия допустимо, вернёмся к этому в шаге 3.2.
   Ошибка вида `No endpoints found that support tool use` или `tools is not supported` — модель не умеет функции, берите другую.
   `429` / `rate-limited` — бесплатная модель перегружена у поставщика или исчерпан ваш лимит. Подождите минуту или возьмите другую бесплатную модель с tools.
   `model not found` — имя модели неверное или больше не обслуживается.
   `401` / `Unauthorized` — ключ скопирован с пробелом, отозван или не от этого адреса.

## Блок 2. Конфигурация и Tool (00:30–01:40)

### Шаг 2.1: `ai/config.py` (10 мин)

**Зачем это нужно.** Провайдер модели, имя модели и API-ключ не должны лежать в коде: в цикле 6 те же агенты поедут в CI, где Ollama нет.

**Что сделать.** Создайте `ai/config.py`:

```python
from typing import Literal

from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class AISettings(BaseSettings):
    """Конфигурация AI-слоя. Значения берутся из .env или переменных окружения."""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",  # в .env будут и переменные приложения (БД и др.)
    )

    llm_provider: Literal["ollama", "cloud"] = "ollama"

    ollama_model: str = "qwen3:4b-instruct"
    ollama_base_url: str = "http://localhost:11434"

    # cloud — любой провайдер с OpenAI-совместимым API
    cloud_model: str = ""
    cloud_base_url: str = "https://openrouter.ai/api/v1"
    cloud_api_key: SecretStr | None = None
    cloud_project: str = ""  # нужен только там, где провайдер требует каталог/проект

    llm_temperature: float = 0.1


settings = AISettings()
```

Три места, где обычно теряют час:

- `extra="ignore"` обязателен. По умолчанию `pydantic-settings` работает в режиме `extra="forbid"`, а в `.env` будут и переменные приложения (БД и др.), которые AI-слою не нужны: без `ignore` конфиг упадёт с ошибкой `Extra inputs are not permitted`.
- `Literal[...]` — опечатка `LLM_PROVIDER=olama` в `.env` упадёт сразу при старте с понятным текстом, а не через десять минут внутри агента.
- `SecretStr` вместо `str` для ключа. Обычная строка печатается в `repr` целиком — и уезжает в скриншот, в лог, в описание PR. `SecretStr` показывает звёздочки, а настоящее значение отдаёт только по явному `.get_secret_value()`.

**Как понять, что получилось**

```bash
python -c "from ai.config import settings; print(settings)"
```

Вывод: `llm_provider='ollama' ollama_model='qwen3:4b-instruct' ... cloud_api_key=None cloud_project='' llm_temperature=0.1`. Ключа в `.env` ещё нет, поэтому `None` — это правильно; после шага 2.2 с пустым `CLOUD_API_KEY=` здесь будет `SecretStr('')`, а когда впишете ключ — `SecretStr('**********')`. Если вместо звёздочек покажется сам ключ, значит остался тип `str`.

**Если не получилось.** `ModuleNotFoundError: No module named 'ai'` — запускайте из корня репозитория и проверьте `ai/__init__.py`. Остальные ошибки этого шага (`Extra inputs are not permitted`, `Input should be 'ollama' or 'cloud'`) разобраны в таблице Troubleshooting.

**Документация.** [pydantic-settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/) — раздел «Dotenv (.env) support», если непонятно, откуда берутся значения.

### Шаг 2.2: `.env`, `.env.example` и `.gitignore` (10 мин)

**Зачем это нужно.** `.env` с ключом в истории Git — это утечка, которую нельзя отменить `git revert`. А `.env.example` — единственный способ для нового человека узнать, какие переменные нужны.

**Что сделать**

1. Убедитесь, что `.env` игнорируется: `git check-ignore -v .env` печатает строку с правилом, например `.gitignore:27:.env	.env`. Файла `.env` для этой проверки может ещё не быть. Если не напечатано ничего — допишите строку `.env` в конец `.gitignore` (так же, как в шаге 1.3, пункт 2) и повторите.
2. Файл `.env` в корне репозитория: если его нет — создайте; если есть (с переменными приложения) — допишите блок в конец, чужие строки не трогайте. Сохраняйте в UTF-8.

```
LLM_PROVIDER=ollama
OLLAMA_MODEL=qwen3:4b-instruct
OLLAMA_BASE_URL=http://localhost:11434
CLOUD_BASE_URL=https://openrouter.ai/api/v1
CLOUD_MODEL=
CLOUD_API_KEY=
CLOUD_PROJECT=
LLM_TEMPERATURE=0.1
CREWAI_TRACING_ENABLED=false
```

   `OLLAMA_MODEL` — ваша модель с tools, та, что скачана и прошла проверку 6 (`qwen3:4b-instruct` или `qwen2.5:7b`).
   `CLOUD_*` — это ваша четвёрка из «Подготовки», путь Б; пока её нет, оставьте значения пустыми. У OpenRouter `CLOUD_PROJECT` остаётся пустым, у Yandex AI Studio туда идёт идентификатор каталога. Остальной файл и весь код от смены провайдера не меняются.
   `CREWAI_TRACING_ENABLED=false` CrewAI читает из `.env` сам. Без неё в конце каждого запуска агента он спрашивает `Share this execution trace with CrewAI? [y/N]` и ждёт ответа 20 секунд: выгружать промпты и данные на чужой сервис не нужно.

3. Файл `.env.example`: тот же блок **с пустыми `CLOUD_API_KEY` и `CLOUD_PROJECT`**. `OLLAMA_MODEL` в нём — модель, на которой работает команда (по ней новый участник поймёт, что качать); `CLOUD_BASE_URL` и `CLOUD_MODEL` можно оставить как в `.env`, это не секреты. Первой строкой — маркер, чтобы было видно, чей это блок:

```
# --- AI-слой (курс «Мульти-агентная разработка») ---
```

   Если `.env.example` уже есть — допишите блок в конец, не трогая чужие строки. Коммитится именно `.env.example`.

4. ⚠️ На будущее: когда в курсе «Конфигурирование» вас попросят создать `.env` из примера (`cp .env.example .env`), сначала сохраните свой `.env` или перенесите из него строки AI-слоя — копирование затрёт ключ и настройки.

**Как понять, что получилось.** `git status --short --ignored` показывает `!! .env` (файл игнорируется) и `?? .env.example` (или ` M .env.example`, если файл уже был). Строки с `.env` без `!!` быть не должно.

**Если не получилось**

- `.env` виден в `git status` без `!!` — файл был добавлен в индекс раньше: `git rm --cached .env`.
- Если `.env` с ключом уже попал в коммит — считайте ключ скомпрометированным: отзовите его в консоли провайдера и выпустите новый. Чистка истории делается отдельно и сегодня не нужна.

### Шаг 2.3: `ai/llm_factory.py` и smoke-тест (25 мин)

**Зачем это нужно.** Это единственная точка в проекте, которая знает, какая модель используется. Всё остальное просит `get_llm()` — благодаря этому в цикле 6 вы подмените LLM моком в тестах, не трогая агентов.

**Что сделать.** Создайте `ai/llm_factory.py`:

```python
from crewai import LLM

from ai.config import settings


def get_llm() -> LLM:
    """Возвращает LLM согласно .env. Единственная точка переключения провайдера."""
    if settings.llm_provider == "ollama":
        return LLM(
            model=f"ollama/{settings.ollama_model}",
            base_url=settings.ollama_base_url,
            temperature=settings.llm_temperature,
        )

    if not settings.cloud_api_key or not settings.cloud_model:
        raise RuntimeError(
            "LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст. Проверьте .env"
        )

    return LLM(
        model=f"openai/{settings.cloud_model}",
        base_url=settings.cloud_base_url,
        api_key=settings.cloud_api_key.get_secret_value(),
        project=settings.cloud_project or None,  # нужен, например, Yandex AI Studio
        temperature=settings.llm_temperature,
    )
```

Что здесь важно и не очевидно:

- Префикс в `model` (`ollama/`, `openai/`) — это то, как CrewAI выбирает провайдера. Без префикса он угадывает по имени модели и почти наверняка уйдёт в настоящий OpenAI.
- Префикс `openai/` вместе с явным `base_url` означает «говори по протоколу OpenAI вот с этим адресом». Так работает любой OpenAI-совместимый сервис: OpenRouter, Yandex AI Studio, ваш собственный vLLM. Именно поэтому смена провайдера — это правка `.env`, а не кода. У CrewAI есть и префиксы конкретных провайдеров (`openrouter/` и другие), но они привязывают код к провайдеру, а часть из них требует дополнительного пакета — нам нужно обратное.
- Модель у некоторых провайдеров содержит слеши и двоеточия (`qwen/qwen3-coder:free` — пример формы имени, такой бесплатной модели уже нет; `gpt://b1g…/yandexgpt-5.1`) — это нормально: всё, что после первого префикса `openai/`, уезжает провайдеру как есть.
- `project` передаётся, только если он заполнен. Yandex AI Studio без идентификатора каталога запрос не примет, OpenRouter про этот параметр ничего не знает — поэтому `or None`.
- Проверка ключа стоит **до** создания `LLM`: ваше сообщение понятнее, чем то, что выдаст библиотека.
- `temperature=0.1` — для агента, который вызывает инструменты, творчество вредно.

**Smoke-тест**

```bash
python -c "from ai.llm_factory import get_llm; print(get_llm().call('Ответь одним словом: работает?'))"
```

**Как понять, что получилось.** В консоли короткий ответ модели. Ждать придётся: импорт CrewAI занимает 35–90 секунд при каждом запуске, а на пути А, если модель ещё не в памяти, загрузка добавляет от десятков секунд до нескольких минут. Не прерывайте.

**Проверка переключения.** Если у вашей команды есть облачный ключ — поменяйте в `.env` `LLM_PROVIDER=cloud`, впишите свою четвёрку «адрес — модель — ключ — каталог» и запустите ту же команду ещё раз. Ответ должен прийти снова, **без единой правки в коде**; затем верните `LLM_PROVIDER=ollama`.
Если ключа нет — проверьте переключение наполовину: поставьте `LLM_PROVIDER=cloud` с пустым `CLOUD_API_KEY` и убедитесь, что `get_llm()` падает с **вашим** сообщением `LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст`, а не с ошибкой из недр библиотеки. Это подтверждает, что ветка провайдера выбирается конфигом. Полное переключение доделаете дома — оно входит в домашнее задание.

**Если не получилось**

- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=ollama` — сообщение обманчивое, речь не про OpenAI: не поднят сервер Ollama. Запустите `ollama serve` и повторите.
- `AuthenticationError: Error code: 401` — ключ неверный, отозван или не от этого адреса. Сверьте `CLOUD_API_KEY` и `CLOUD_BASE_URL`: ключ OpenRouter к адресу Yandex AI Studio не подойдёт.
- `NotFoundError` / `model not found` — имя модели неверное или больше не обслуживается. Возьмите актуальное со страницы моделей своего провайдера и впишите в `CLOUD_MODEL`.
- `429` / `rate-limited` при `LLM_PROVIDER=cloud` — бесплатная модель перегружена или исчерпан лимит. CrewAI сам повторяет запрос несколько раз, и каждый повтор списывается из суточного лимита. Подождите минуту или возьмите другую бесплатную модель; если кончился дневной лимит — работайте по пути А, облачную проверку доделайте дома.
- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=cloud` — адрес недоступен: опечатка в `CLOUD_BASE_URL` или сеть не выпускает запрос наружу.

**Документация.** [CrewAI: LLMs](https://docs.crewai.com/en/concepts/llms) — разделы «Ollama» и «Custom OpenAI-Compatible Endpoint» (во вкладке OpenAI), если непонятно, как CrewAI выбирает провайдера.

### Шаг 2.4: Ваш Tool (25 мин)

**Зачем это нужно.** Tool — это граница между вероятностной моделью и вашей детерминированной системой. Всё, что модель может испортить, должно останавливаться здесь и возвращаться агенту текстом, который он способен прочитать и исправить.

**Что сделать.** В файле `ai/tools/<имя>.py`, где лежит контракт, напишите Tool. Данные сегодня — словарь-заглушка прямо в модуле Tool: 3–5 записей, по которым можно проверить и успех, и пустой результат. Подключение к вашему FastAPI — в цикле 5, сигнатура Tool при этом не изменится. Ниже каркас; содержательная часть у каждой команды своя.

```python
import json

from crewai.tools import tool


def _fail(message: str) -> str:
    """Единый формат ошибки, который вернётся агенту."""
    return json.dumps({"status": "error", "message": message}, ensure_ascii=False)


@tool("имя_из_вашего_контракта")
def your_tool_name(param: str, limit: int = 10) -> str:
    """Одно предложение: что делает инструмент и когда его вызывать.

    Args:
        param: что это и какие значения допустимы (перечислите их явно).
        limit: что ограничивает, диапазон и значение по умолчанию.

    Returns:
        JSON-строка. При успехе: {"status": "ok", ...}.
        При ошибке: {"status": "error", "message": "<что не так и что делать>"}.
    """
    # 1. Валидация входа: каждое условие из контракта — отдельная проверка с _fail()

    # 2. Полезная работа — внутри try/except

    # 3. Успешный ответ: json.dumps({...}, ensure_ascii=False)
```

Пять требований, по которым это будут проверять на peer review:

1. **Docstring обязателен.** Это не стиль, которому договорились придерживаться в команде, а обязательная механика: `@tool` берёт описание для модели именно из docstring, а функция без него падает с `ValueError: Function must have a docstring` ещё на импорте. Пишите его для LLM: явно перечисляйте допустимые значения. Не ставьте в docstring конкретный пример идентификатора, похожий на настоящий: маленькая модель подставляет его, когда пользователь номер не назвал (это проверяет сценарий 2 шага 3.3).
2. **Имя, которое видит модель, — это аргумент декоратора**, а не имя функции. `@tool("get_ticket_status")` над `def your_tool_name(...)` даст модели инструмент `get_ticket_status`. Имя функции модель не видит вообще.
3. **Аннотации типов у всех параметров.** По ним CrewAI строит схему аргументов, которую видит модель.
4. **Безопасный возврат.** Из тела Tool не должно вылетать необработанное исключение. Любая ошибка — `return _fail("...")` с текстом, из которого понятно, **что именно** исправить: «priority должен быть 'high', 'medium' или 'low', получено 'urgent'» вместо «invalid input». Один случай не в вашей власти: если обязательный аргумент не передан или пришёл не того типа, CrewAI отклонит вызов по схеме ещё до вашего кода (`ValueError` со словами `arguments validation failed` и `Field required`). Это не провал вашего Tool.
5. **Одна строка на выходе.** Всегда `str` (JSON внутри строки), всегда одинаковая структура — и при успехе, и при ошибке.

*Пример одной команды (хелпдеск) для иллюстрации формы:*

```python
@tool("get_ticket_status")
def get_ticket_status(ticket_id: str) -> str:
    """Возвращает текущий статус тикета поддержки по его идентификатору.

    Вызывай, только если пользователь назвал номер тикета; не придумывай номер.

    Args:
        ticket_id: идентификатор вида 'HD-<номер>'. Префикс 'HD-' обязателен.

    Returns:
        JSON-строка: {"status": "ok", "ticket_id": ..., "state": ...}
        или {"status": "error", "message": ...}.
    """
    if not ticket_id.startswith("HD-"):
        return _fail(f"ticket_id должен начинаться с 'HD-', получено '{ticket_id}'")
    try:
        ...  # обращение к словарю-заглушке; в цикле 5 здесь будет вызов вашего FastAPI
    except Exception as exc:  # noqa: BLE001 — граница системы, наружу ничего не летит
        return _fail(f"не удалось получить тикет: {exc}")
```

**Как понять, что получилось.** Проверьте Tool напрямую, без агента, — LLM для этого не нужна. Создайте `ai/tools/_check.py` и поправьте строки под себя:

```python

print("name:", <имя_функции>.name)
print("ok  :", <имя_функции>.run(<корректные аргументы>))
print("err :", <имя_функции>.run(<заведомо неверные аргументы>))
```

Аргументы передаются по именам, например для хелпдеска: `get_ticket_status.run(ticket_id="HD-1")` и `get_ticket_status.run(ticket_id="XX-1")`. Тестировщик-документатор может добавить сюда ещё строки `err` — по одной на каждый краевой случай контракта. Вызовы без обязательного аргумента сюда не включайте: их отклоняет CrewAI (требование 4).

Запуск: `python -m ai.tools._check` (из-за импорта CrewAI — 35–90 секунд). Файл остаётся в репозитории и уезжает в PR — так и задумано: ревьюеры соседней команды запустят его сами.

Ожидаемый вывод: имя инструмента из аргумента декоратора, затем строка со `"status": "ok"`, затем строка со `"status": "error"` и понятным сообщением. Ни одного traceback.

**Если не получилось**

- `ValueError: Function must have a docstring` — у функции под `@tool` нет docstring.
- Traceback вместо строки с ошибкой — остался непокрытый путь. Оберните тело в `try/except Exception` и возвращайте `_fail()`.
- `ValueError` со словами `arguments validation failed` — вызов в `_check.py` не передал обязательный аргумент или передал не тот тип. Передайте все обязательные аргументы по именам.

## Блок 3. Агент и проверка на прочность (01:40–02:20)

### Шаг 3.1: `ai/run_agent.py` (15 мин)

**Зачем это нужно.** Сборка контура целиком: модель получает описание вашего Tool, решает вызвать его, получает результат и формулирует ответ.

**Что сделать.** Создайте `ai/run_agent.py`:

```python
from crewai import Agent, Crew, Task

from ai.llm_factory import get_llm
from ai.tools.<модуль> import <имя_инструмента>

agent = Agent(
    role="<роль из вашей предметной области>",
    goal="<чего агент добивается — одно предложение>",
    backstory="<кто он и как себя ведёт: например, всегда проверяет данные перед действием>",
    tools=[<имя_инструмента>],
    llm=get_llm(),
    verbose=True,
    max_iter=5,  # страховка от бесконечного цикла; по умолчанию 25
)

task = Task(
    description="<запрос пользователя, для которого нужен ваш инструмент>",
    expected_output="<в каком виде вы хотите финальный ответ>",
    agent=agent,
)

crew = Crew(agents=[agent], tasks=[task], verbose=True)

if __name__ == "__main__":
    print(crew.kickoff())
```

Запустите из корня репозитория и сохраните лог. Первая строка включает режим UTF-8 для Python: без неё на Windows при записи в `tee` / `Tee-Object` CrewAI молча теряет все панели с эмодзи, включая `Tool Execution`, и лог становится бесполезным. Переменная действует до закрытия окна терминала; в новом окне задайте её снова.

Git Bash (рекомендуется на Windows) / Linux / macOS:

```bash
export PYTHONUTF8=1
python -m ai.run_agent 2>&1 | tee ai/traces/run-01.log
```

PowerShell:

```powershell
$env:PYTHONUTF8 = "1"
[Console]::OutputEncoding = [Text.Encoding]::UTF8
python -m ai.run_agent 2>&1 | Tee-Object -FilePath ai\traces\run-01.log
```

`2>&1` нужен, чтобы в лог попали не только панели CrewAI, но и предупреждения с traceback, если что-то пойдёт не так. Вторая строка PowerShell заставляет его читать вывод Python как UTF-8. В Windows PowerShell 5.1 файл получится в кодировке UTF-16, а сообщения из stderr — красными блоками `NativeCommandError`; лог при этом читаемый, но если он мешает — запускайте из Git Bash, он у вас уже есть для curl.

Один запуск занимает 1–6 минут на CPU-машине: импорт CrewAI, загрузка модели, несколько обращений к ней. Не прерывайте.

```
╭──────────── ✅ Agent Final Answer ────────────╮
│  Final Answer:
│  Задач с приоритетом high не найдено.
```

У вас рамки и лишние строки могут отличаться: `┌` вместо `╭`, отдельная панель `Tool Output` после `Tool Execution Completed`, строки с цветовыми кодами вида `[32m`. Бывают и строки вне панелей: `Tool <имя> executed with result: …` (иногда вклинивается прямо в рамку или в заголовок панели) и `[Finalize] todos_count=0, todos_with_results=0`. Это служебный вывод CrewAI, не ошибка. Ещё две панели — не ошибка: `Update Available` (совет выполнить `uv sync --upgrade-package crewai` игнорируйте — версия закреплена в `requirements-ai.txt` намеренно) и `Tracing Status` со словами `Tracing is disabled` (так и задумано: ваша трасса — это сохранённый лог).

Минимум, который должен быть в вашем логе: панель `Tool Execution Started` с **именем вашего инструмента**, панель `Tool Execution Completed` с вашим JSON и `Agent Final Answer`, опирающийся на этот JSON.

**Если не получилось**

- Панелей `Tool Execution` нет, а финальный ответ есть — модель решила, что справится сама. Это разбирается в шаге 3.2, не чините наугад.
- В логе вместо панелей строки `Sync handler error … 'charmap' codec can't encode character` — в этом окне не задан `PYTHONUTF8=1`. Задайте и перезапустите.
- Выполнение упирается в `max_iter` — модель зациклилась на неверных аргументах. Посмотрите, какие `Args` она подставляет, и уточните формулировки в docstring.
- `ModuleNotFoundError: No module named 'ai'` — запускайте именно как `python -m ai.run_agent` из корня репозитория. Если вы работали двумя парами и не хватает половины кода — вернитесь к шагу сведения в конце 2.4.

**Документация.** [CrewAI: Agents](https://docs.crewai.com/en/concepts/agents) — таблица параметров; [CrewAI: Tasks](https://docs.crewai.com/en/concepts/tasks) — `description` и `expected_output`. Открывайте, если параметр ведёт себя не так, как ожидали.

### Шаг 3.2: Чтение трассы (10 мин)

**Зачем это нужно.** Отладка агента — это чтение его трассы: логика здесь не в вашем коде, а в последовательности решений модели.

**Что сделать.** Откройте `ai/traces/run-01.log` и ответьте письменно — сразу в черновик ADR, раздел «Наблюдения из трассы» (записывает тестировщик-документатор или вторая пара):

1. Сколько раз вызывался Tool? Если больше одного — почему? Посмотрите `Args` каждого вызова.
2. Какие именно аргументы подставила модель? Совпадают ли они с тем, что описано в вашем docstring?
3. Финальный ответ основан на `Output` инструмента или содержит факты, которых в `Output` не было?

Концептуально это цикл ReAct: рассуждение → действие → наблюдение. CrewAI 1.15 печатает его как панели `Agent Started` → `Tool Execution Started/Completed` → `Agent Final Answer`; отдельных строк `Thought:` в выводе может не быть, и это не признак поломки.

**Если агент не вызвал Tool и придумал ответ** — проверьте по порядку:

1. Описание в docstring не объясняет, **когда** вызывать инструмент. «Работает с задачами» модель не поймёт; «возвращает задачи с указанным приоритетом; используй, когда спрашивают о задачах по приоритету» — поймёт.
2. `Task.description` сформулирован так, что на него можно ответить без данных. Сделайте запрос конкретным: он должен требовать значения, которого у модели нет.
3. Локальная 4b слабее в function calling, чем облачная. Сначала убедитесь, что модель вообще принимает инструменты (проверка 6 из «Проверки окружения»), потом попробуйте `qwen2.5:7b` — только если она уже скачана (на паре 4,7 ГБ не качайте), а если в команде есть ключ — прогоните тот же сценарий по пути Б. Если там Tool вызывается, дело в размере модели, и это честный вывод для ADR.

**Документация.** [Prompt Engineering Guide: ReAct](https://www.promptingguide.ai/techniques/react) — если цикл «рассуждение → действие → наблюдение» в трассе не узнаётся.

### Шаг 3.3: Провокация ошибок (15 мин)

**Зачем это нужно.** Агент, который работает только на правильных данных, бесполезен. Паттерн «безопасный возврат» проверяется ровно одним способом: сломать вход специально.

**Что сделать.** Сценарий 1 обязателен, логи двух остальных доберёте дома, если не успеете на паре. Меняйте только `Task.description`, запускайте той же командой, что в шаге 3.1, логи сохраняйте как `run-02.log`, `run-03.log`, `run-04.log`. Модель отвечает не всегда одинаково: если результат кажется случайным, повторите запуск 2–3 раза.

1. **Недопустимое значение** (обязательно). Попросите то, чего в допустимых значениях нет («задачи с приоритетом `super-high`»).
2. **Пустой или отсутствующий вход.** Запрос без обязательного параметра («покажи статус тикета» без номера).
3. **Несуществующая сущность.** Идентификатор правильного формата, которого нет в данных.

**Как понять, что получилось.** В логе есть панель `Tool Execution Completed` с вашим `{"status": "error", ...}`, процесс **не падает**, и финальный ответ агента осмысленный: либо повторный вызов с исправленными аргументами, либо вежливое сообщение пользователю. Traceback в консоли — это провал сценария. В сценарии 2 хорош и третий исход: агент вообще не вызывает Tool и просит назвать недостающее значение.

Две находки, которые ожидаемы и вашей ошибкой не являются. Запишите их в ADR, раздел «Наблюдения из трассы», — это материал для воркшопа 2:

- **Сценарий 2: модель сама придумывает аргумент.** Номер пользователь не назвал, но Tool вызван с правдоподобным выдуманным значением (`RR-123`). Tool отвечает error «не найдена», и агент просит уточнить номер. На проверочных машинах так в 2 запусках из 2 вела себя `qwen2.5:7b`, хотя примера в docstring не было, а «не придумывай номер» было. `qwen3:4b-instruct` в том же сценарии Tool не вызывала и сразу просила номер. Модель, которая лучше вызывает инструменты (шаг 3.2, пункт 3), не обязательно аккуратнее с аргументами. Запишите, какая модель как себя вела.
- **Сценарий 3: агент пересказывает пользователю текст ошибки Tool.** Например, «уточните номер у пользователя»: фраза адресована агенту, а дошла до пользователя дословно. Значит, `message` из Tool модель может показать человеку как есть. Учитывайте это, когда пишете сообщения об ошибках.

Так выглядит успешная самокоррекция в реальном логе: первый вызов с неверным аргументом, ошибка от Tool, второй вызов с исправленным.

```
│  Tool: get_tasks_by_priority
│  Args: {'priority': 'urgent'}
│  Output: {"status": "error", "message": "priority должен быть 'high', 'medium' или 'low'"}
...
│  Tool: get_tasks_by_priority
│  Args: {'priority': 'high'}
│  Output: {"status": "ok", "count": 0, "items": []}
```

Перед коммитом верните в `run_agent.py` исходный `Task.description` из шага 3.1: в PR `run_agent.py` запускает основной сценарий, а провокации остаются в логах.

**Если не получилось**

- Упал traceback — где-то в Tool осталось необработанное исключение. Вернитесь к шагу 2.4, требование 4.
- Агент получил ошибку, но не исправился и сдался — текст `message` не подсказывает решение. Добавьте в него допустимые значения.
- Агент зациклился на одной ошибке до `max_iter` — противоречие между docstring и валидацией: вы принимаете не то, что обещаете. Сверьте оба места с контрактом из шага 1.3.
- Сценарий 2: Tool вызван с выдуманным аргументом, который **есть в ваших данных** (часто — тем, что стоит примером в docstring), вернул `"status": "ok"`, и агент уверенно отвечает про чужую запись. Сначала проверьте docstring: если в нём есть конкретный пример значения, уберите его, добавьте «вызывай, только если пользователь назвал …; не придумывай» и повторите запуск. Если примера нет, а модель всё равно подставляет значение, это свойство модели, а не ошибка вашего кода (см. находки выше). Запишите в ADR, какой была запись и что ответил агент: это ровно тот класс рисков, который разбирается на воркшопе 2.

> **Закончили раньше?** Не начинайте блок 4 досрочно — peer review стартует у всех одновременно. ## Troubleshooting

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=ollama` | Сервер Ollama не запущен (упоминание OpenAI обманчиво: CrewAI ходит в Ollama по OpenAI-совместимому протоколу) | `ollama serve` в отдельном окне; проверить `curl http://localhost:11434/api/tags` |
| `address already in use` при `ollama serve` | Ollama уже запущен фоном (приложение в трее) | Ничего не делать, сервер работает; проверить `curl` к 11434 |
| Порт 11434 занят другим приложением | Конфликт портов | Запустить Ollama на другом порту — Git Bash: `OLLAMA_HOST=127.0.0.1:11500 ollama serve`, PowerShell: `$env:OLLAMA_HOST="127.0.0.1:11500"; ollama serve` — и указать тот же адрес в `OLLAMA_BASE_URL` |
| `ollama pull` падает с `redirect target not allowed … resolves to non-public 198.18.x.x` | VPN или прокси с подменой DNS (fake-IP) не пускает загрузку модели | Отключить VPN или режим TUN на время загрузки либо скачать модель в другой сети |
| `... does not support tools` (HTTP 400) при запуске агента | У модели в Ollama нет возможности tools. `qwen2.5-coder` любого размера сюда не годится: он умеет писать код, но не вызывать функции | Взять модель с возможностью tools: `qwen3:4b-instruct` (2,5 ГБ) или `qwen2.5:7b` (4,7 ГБ), поправить `OLLAMA_MODEL` в `.env` |
| `model '...' not found` | Модель не скачана в этом профиле пользователя | `ollama pull qwen3:4b-instruct` дома либо путь Б на паре |
| Повторные ответы модели идут минутами, машина уходит в своп | Не хватает RAM (4b нужно ~3 ГБ свободных, 7b — ~5 ГБ). Медленный **первый** ответ после запуска — это загрузка модели, а не нехватка памяти | Закрыть тяжёлые приложения; путь Б |
| `AuthenticationError: Error code: 401` при `LLM_PROVIDER=cloud` | Ключ неверный, отозван или не от этого адреса (ключ одного провайдера к адресу другого) | Сверить `CLOUD_API_KEY` и `CLOUD_BASE_URL`, проверить пробелы и кавычки в `.env` |
| `NotFoundError` / `model not found` при `LLM_PROVIDER=cloud` | Имя модели неверное или больше не обслуживается (у бесплатных моделей список меняется) | Взять актуальное имя со страницы моделей провайдера и вписать в `CLOUD_MODEL` |
| `No endpoints found that support tool use` / `tools is not supported` | Облачная модель не умеет вызывать функции — та же беда, что и с локальной моделью без tools | Взять модель с поддержкой функций (на OpenRouter это фильтр на странице моделей) |
| Yandex AI Studio отвечает 400 или «folder not specified» | Не заполнен `CLOUD_PROJECT` — идентификатор каталога | Вписать `b1g…` в `CLOUD_PROJECT`; он же должен быть внутри `gpt://<каталог>/…` в `CLOUD_MODEL` |
| `429` / `rate limit` у бесплатной модели | Исчерпан дневной или минутный лимит бесплатного тарифа либо модель перегружена у поставщика. CrewAI повторяет запрос сам, и повторы тоже расходуют лимит | Подождать минуту или взять другую бесплатную модель; если кончился дневной лимит — работать по пути А, а облачную проверку доделать дома |
| Облачный провайдер не отвечает, таймаут соединения | Сеть аудитории не выпускает запросы на его адрес | Проверить `curl` из «Подготовки», путь Б; перейти на путь А или на мобильный интернет |
| `ValidationError: Extra inputs are not permitted` при импорте конфига | В `.env` есть переменные, которых нет в `AISettings`, а режим по умолчанию — `extra="forbid"` | Добавить `extra="ignore"` в `SettingsConfigDict` |
| `ValidationError: Input should be 'ollama' or 'cloud'` | Опечатка в `LLM_PROVIDER` | Исправить значение в `.env`; конфиг отработал правильно |
| `ValueError: Function must have a docstring` | У функции под `@tool` нет docstring | Написать docstring: он же является описанием инструмента для модели |
| `ValueError` со словами `arguments validation failed` и `Field required` | Обязательный аргумент не передан или не того типа: CrewAI отклоняет вызов по схеме до кода Tool | В `_check.py` передавать все обязательные аргументы по именам; это не нарушение безопасного возврата |
| Агент не вызывает Tool, выдумывает ответ | Описание не объясняет, когда вызывать; задача решается без данных; модель слишком мала | См. шаг 3.2 |
| Агент вызывает Tool с выдуманным аргументом (часто — примером из docstring) | Пользователь значение не назвал, а docstring подсказал «образец». Некоторые модели (например, `qwen2.5:7b`) делают так и без примера | Убрать пример значения из docstring, добавить «вызывай, только если пользователь назвал …». Если не помогло — это свойство модели: записать в ADR как находку; см. шаг 3.3 |
| Traceback из Tool роняет запуск | Непокрытый путь выполнения | Обернуть тело в `try/except Exception` и вернуть `_fail(...)` |
| Агент крутится до `max_iter` и сдаётся | Docstring обещает одно, валидация требует другого | Сверить docstring, валидацию и контракт из шага 1.3 |
| В конце запуска вопрос `Share this execution trace with CrewAI? [y/N] (20s timeout)` | Не отключена облачная трассировка CrewAI | Добавить `CREWAI_TRACING_ENABLED=false` в `.env` (шаг 2.2) |
| В логе `Sync handler error … 'charmap' codec can't encode`, панелей `Tool Execution` нет; или кракозябры вместо кириллицы (Windows) | Python пишет в канал в кодировке Windows, а не UTF-8 | Перед запуском: Git Bash — `export PYTHONUTF8=1`; PowerShell — `$env:PYTHONUTF8 = "1"` и `[Console]::OutputEncoding = [Text.Encoding]::UTF8`. Перезапустить и перезаписать лог |
| Логов `ai/traces/*.log` нет в `git status` и в Files changed | Правило `*.log` в `.gitignore` проекта | `git check-ignore -v ai/traces/run-01.log`; добавить исключение из шага 1.3, пункт 2, и закоммитить логи |

### Вторая машина завела свои файлы

Сохраните свою работу, встаньте на опубликованную ветку, сравните свою работу с опубликованной и верните своё. **Внимание:** `git clean` удаляет все неотслеживаемые файлы в `ai/` и `docs/`, не только Tool, — например, черновик `ai/config.py`. Поэтому первые две команды копируют весь `ai/` в `../ai-backup`; не пропускайте их. Перед `git restore .gitignore` посмотрите `git diff .gitignore`: свои строки, кроме `!ai/traces/*.log`, после рецепта перенесите вручную. Вместо `<базовая>` — `main` или `develop`.

Git Bash:

```bash
rm -rf ../ai-backup
cp -r ai ../ai-backup
git fetch
git switch <базовая>
git branch -D feature/agent-tool-1
git restore .gitignore
git clean -fd -- ai docs requirements-ai.txt
git switch feature/agent-tool-1
git diff --no-index --name-status ai/tools ../ai-backup/tools
```

PowerShell:

```powershell
Remove-Item -Recurse -Force ../ai-backup -ErrorAction SilentlyContinue
Copy-Item -Recurse ai ../ai-backup
git fetch
git switch <базовая>
git branch -D feature/agent-tool-1
git restore .gitignore
git clean -fd -- ai docs requirements-ai.txt
git switch feature/agent-tool-1
git diff --no-index --name-status ai/tools ../ai-backup/tools
```

`git branch -D` может ответить `error: branch 'feature/agent-tool-1' not found` — значит, своей локальной ветки у вас не было. Это безвредно, продолжайте.

Последняя команда ничего не меняет: она сравнивает опубликованные файлы Tool с вашей копией. Строки в её выводе означают:

- `A	../ai-backup/tools/<файл>` — файл есть только у вас. Верните его: `cp ../ai-backup/tools/<файл> ai/tools/` (PowerShell: `Copy-Item ../ai-backup/tools/<файл> ai/tools/`). Строки про `__pycache__` пропускайте.
- `M	ai/tools/<файл>` — файл с тем же именем уже опубликован, обычно с контрактом из шага 1.3. **Не копируйте его поверх вслепую:** копия перезапишет опубликованный файл. Сначала посмотрите разницу: `git diff --no-index ai/tools/<файл> ../ai-backup/tools/<файл>`. Если опубликованный файл — каркас с контрактом, перенесите в него свой код вручную, контракт оставьте. Если ваш вариант полнее, скопируйте его и верните в начало контракт из опубликованной версии.
- Вывода нет — ваша копия совпадает с опубликованной, возвращать нечего.

Если в копии были файлы вне `ai/tools` (например, `ai/config.py`), разберите их так же: `git diff --no-index --name-status ai ../ai-backup`, затем `A` — скопировать, `M` — сравнить и перенести вручную. Строки `D` и уже разобранные строки из `ai/tools` пропускайте: `D` значит, что файла нет в копии, удалять его не нужно (`ai/traces/.gitkeep` нужен для логов).

Проверка: `git status` печатает `On branch feature/agent-tool-1`, а в `ai/tools/` лежит ваш код Tool и контракт из шага 1.3, а не пустой каркас.

## Домашнее задание (СРС, 2–3 часа)

Ведёт в цикл 2 — «Инструменты агентов»: function calling и инструменты для работы с кодом (`search_codebase`, `read_file`, `run_linter`, безопасное выполнение кода).

**Порядок и сроки.** До воркшопа 2 у вас один день, поэтому начните с пунктов **5 и 6 — к началу воркшопа 2, обязательно** (около 45 минут): это входной билет, без него на воркшопе атакуют чужую спецификацию, а не вашу. Пункты 1–4 — до практики 2.

**1. Доработка и хвосты с пары (40–60 мин).**
Закройте замечания peer review и доделайте всё, что не успели: `run_agent.py`, логи, ADR. На каждое замечание — ответ в ветке комментария: исправлено или почему решили иначе. PR должен быть готов к слиянию. Если к этому времени команда перешла на GitFlow, цель PR — `develop`.

**2. Полное переключение провайдера (20–30 мин).**
Если на паре вы проверили переключение только наполовину — доведите до конца: `LLM_PROVIDER=cloud`, своя четвёрка «адрес — модель — ключ — каталог» в `.env`, тот же smoke-тест и тот же `run_agent.py` без единой правки кода. Сохраните лог как `ai/traces/run-cloud.log` (той же командой, что в шаге 3.1, с `PYTHONUTF8=1`) и допишите в ADR, чем отличалось поведение локальной модели и облачной. Если успели на паре — прогоните оставшиеся сценарии из шага 3.3.

**3. Function calling — механика (30 мин).**
[Prompt Engineering Guide: Function Calling](https://www.promptingguide.ai/applications/function_calling). Читайте с одним вопросом: что именно модель получает на вход, когда «видит» ваш инструмент, и в каком виде сообщает о желании его вызвать.

**4. Разведка своего репозитория (15 мин).**
Запустите линтер и сохраните машиночитаемый вывод (команда одинакова в Git Bash и PowerShell):

```bash
ruff check --output-format=json --output-file docs/lint-report.json
```

Запускайте в корне репозитория, ветка любая; удобнее `feature/agent-tool-1`, там ruff проверит и код `ai/`. Если `ruff` в проекте не настроен — поставьте его в окружение (`pip install ruff`) и запустите как есть ([Ruff: The Linter](https://docs.astral.sh/ruff/linter/), 5 минут). Найденные замечания — это нормально: ruff при этом завершается с кодом 1. Если в файле только `[]`, а код выхода 0, тоже всё в порядке: с правилами по умолчанию ruff проверяет немногое, и в чистом проекте замечаний может не быть. Тогда посмотрите, как выглядит одно замечание, на заведомо плохой строке. Команда ничего не записывает в репозиторий и печатает JSON с замечанием `F401` (неиспользуемый импорт):

```bash
echo "import os" | ruff check --output-format=json --stdin-filename demo.py -
```

В PowerShell: `'import os' | ruff check --output-format=json --stdin-filename demo.py -`.

Посмотрите структуру JSON: именно её на практике 2 будет разбирать Tool `run_linter`, и именно из неё агенту придётся понять, что чинить.

`docs/lint-report.json` не коммитьте. Это снимок вашей машины: в поле `filename` лежат абсолютные пути вида `C:\Users\<вы>\…`. На воркшопе 2 он нужен вам локально, а на практике 2 такой же JSON будет получать сам Tool. Неотслеживаемый файл переходит с вами из ветки в ветку, поэтому при коммитах указывайте файлы в `docs/` по имени, как в пункте 5, а не `git add docs/`.

**5. Спецификации двух инструментов для работы с кодом (25–35 мин). Срок — до начала воркшопа 2.**
По форме воркшопа 1 (имя, назначение для LLM, параметры с допустимыми значениями, формат возврата, краевые случаи) спроектируйте:

- инструмент поиска по кодовой базе — что принимает и что возвращает, чтобы результат влезал в контекст модели;
- инструмент чтения файла — как ограничить его так, чтобы агент не мог прочитать `.env` или что-либо за пределами репозитория.

Запишите в `docs/tools-spec-cycle2.md`. Ограничения доступа продумайте письменно: на воркшопе 2 вы будете защищать именно их.

Файл живёт в отдельной ветке `feature/code-tools` от базовой — в неё же после воркшопа 2 уйдёт версия v2. Создайте ветку **до** того, как запишете файл:

```bash
git switch <базовая>
git pull
git switch -c feature/code-tools
```

Когда файл готов (вместе с абзацем из пункта 6):

```bash
git add docs/tools-spec-cycle2.md
git commit -m "docs: add tools spec for cycle 2"
git push -u origin feature/code-tools
```

Ссылку на файл в этой ветке отправьте в общий чат курса до начала воркшопа 2.

**6. Один вопрос к обсуждению (10 мин). Срок — до начала воркшопа 2.**
Сформулируйте письменно: какой инструмент в вашем проекте опаснее всего давать агенту и почему. Одного абзаца достаточно — допишите его в конец `docs/tools-spec-cycle2.md` до коммита из пункта 5.
