# Практика 1. Первый Tool и переключаемая конфигурация LLM

**Длительность:** 180 минут (2 пары)
**Формат:** самостоятельная командная работа по этому руководству. Pair Programming в командах 3–4 человека, в конце — peer review с соседней командой.
**Роль преподавателя:** организационная. Он следит за временем, объявляет стоп-точки, фиксирует прогресс команд и назначает пары для peer review. Всё содержание занятия — в этом файле и по ссылкам из него.

> ⚠️ Руководство рассчитано на то, что вы дойдёте до конца сами. Если шаг не получается — сначала читайте блок «Если не получилось» у этого шага, потом таблицу Troubleshooting в конце файла, потом документацию по ссылке.

**Проверено на:** Windows 11, Python 3.12, `crewai==1.15.22`, `pydantic-settings==2.15.0`, Ollama с моделью `qwen3:4b-instruct` на CPU, OpenRouter (бесплатная модель с tools), `ruff 0.17.0` (ДЗ, п. 4) — октябрь 2026. Эталонный Tool `find_endpoint` проверен на бэкенде недели 2 «Конфигурирования» и на учебном бэкенде курса `templates/sample-backend/` с `qwen3:4b-instruct` и `qwen2.5:7b`. Yandex AI Studio, macOS и Linux на этой версии не проверялись. Если читаете заметно позже, сверьте с документацией CrewAI способ объявления Tool (`from crewai.tools import tool`) и параметры класса `LLM`: между мажорными версиями они менялись.

## Что вы сделаете сегодня

**Проблема.** Попросите модель без доступа к коду написать тест к эндпоинту вашего бэкенда — она уверенно напишет тест к эндпоинту, которого нет. Дайте ей функцию поиска по коду — и она передаст в неё `FETCH` вместо `GET` или путь без `/`, а необработанное исключение уронит весь процесс. Сегодня вы строите первый Tool помощника вашей команды: модель вызывает его по делу, а неверный вход он возвращает ей текстом, по которому она может исправиться.

**Что такое помощник.** Мульти-агентная система курса — помощник вашей команды разработчиков бэкенда из курса «Конфигурирование»: он анализирует код, генерирует код и тесты, делает ревью. Помощник живёт в **отдельном репозитории** `<проект>-assistant` рядом с клоном бэкенда, со своим окружением, `.env` и зависимостями. Бэкенд помощник только читает, путь к нему задаётся в `.env`. В репозитории бэкенда на этом занятии не меняется ничего.

В конце занятия в репозитории помощника будет:

1. Ветка `feature/agent-tool-1` и Pull Request в `main` с комментариями peer review от соседней команды.
2. `ai/config.py` — конфигурация помощника на `pydantic-settings`, читающая `.env`: где лежит бэкенд (`AI_REPO_ROOT`) и какая модель работает.
3. `ai/llm_factory.py` — одна функция `get_llm()`, возвращающая LLM для локальной Ollama или для любого облачного провайдера с OpenAI-совместимым API. Переключение — правкой `.env`, без изменения кода.
4. `ai/tools/<ваш_инструмент>.py` — рабочий Tool над кодом бэкенда по спецификации, которую ваша команда защитила на воркшопе 1 (или эталонный `find_endpoint`, если спецификация не подошла — шаг 1.3): с валидацией входа и безопасным возвратом ошибки.
5. `ai/run_agent.py` и закоммиченные логи в `ai/traces/`, в которых видно, что агент **вызвал ваш Tool**, а не придумал ответ.
6. `docs/adr/001-framework-and-first-tool.md` — ADR: выбор фреймворка и дизайн первого Tool.

**Базовая ветка** репозитория помощника — `main`: фичи вливаются в неё через Pull Request. Pull Request открывается на том же хостинге, где бэкенд: на GitHub и Gitea это Pull Request, на GitLab — Merge Request.

## Подготовка ДО занятия

Делается дома каждым участником и занимает 1,5–2 часа, из них около часа машина работает сама (установка библиотек и загрузка модели). На паре этого не успеть: одна только установка CrewAI на проверочных машинах шла 23–37 минут. Пункт 0 почти целиком делает один человек на команду, остальные — только его часть «Все остальные».

### 0. Репозиторий помощника (один участник — 10 мин, остальные — 2 мин)

Помощник — отдельный репозиторий команды на том же хостинге, где бэкенд «Конфигурирования». Его клон лежит **рядом** с клоном бэкенда, в одном родительском каталоге:

```
<родительский каталог>/
├── <проект>/             ← репозиторий бэкенда («Конфигурирование»), помощник его только читает
└── <проект>-assistant/   ← репозиторий помощника: venv/, ai/, docs/, .env
```

Вместо `<проект>` везде ниже — имя каталога, в который склонирован ваш бэкенд. Создать репозиторий нужно до занятия: окружение с CrewAI (пункты 1–2) ставится **внутрь** каталога помощника, а `git clone` в непустой каталог не работает. `.gitignore` тоже должен появиться до первого `git add`, иначе в коммит уедет `venv/`.

**Один участник** (обычно тот, кто создавал репозиторий бэкенда):

1. На хостинге создайте **пустой** репозиторий `<проект>-assistant`: без README, `.gitignore` и лицензии из мастера создания. Дайте сокомандникам права на запись так же, как в репозитории бэкенда.
2. В родительском каталоге клона бэкенда (если бэкенда ещё нет — в любом рабочем каталоге, см. абзац «Своего бэкенда с `main.py` ещё нет» ниже) склонируйте его и создайте первый коммит. Адрес возьмите на странице репозитория (кнопка Clone / Code). Предупреждение `You appear to have cloned an empty repository` ожидаемо.

   Git Bash / Linux / macOS:

```bash
git clone <адрес репозитория помощника>
cd <проект>-assistant
printf 'venv/\n.venv/\n__pycache__/\n.env\ndocs/lint-report.json\n' > .gitignore
echo "# <проект>-assistant" > README.md
git add .gitignore README.md
git commit -m "chore: initial commit"
git branch -M main
git push -u origin main
```

   PowerShell:

```powershell
git clone <адрес репозитория помощника>
cd <проект>-assistant
Set-Content .gitignore "venv/", ".venv/", "__pycache__/", ".env", "docs/lint-report.json"
Set-Content README.md "# <проект>-assistant"
git add .gitignore README.md
git commit -m "chore: initial commit"
git branch -M main
git push -u origin main
```

   Правила `*.log` в этом `.gitignore` нет намеренно: логи трассы из `ai/traces/` — главное доказательство вашей работы, они коммитятся. `docs/lint-report.json` — отчёт линтера из домашнего задания, п. 4, он не коммитится. `git branch -M main` называет ветку `main` независимо от настроек вашего git.

   **Как понять, что получилось.** `git push` печатает `* [new branch]      main -> main` и `branch 'main' set up to track 'origin/main'`; на странице репозитория видны `.gitignore` и `README.md`.

**Все остальные** — после того как первый участник выполнил `git push`, в том же родительском каталоге, где лежит ваш клон бэкенда:

```bash
git clone <адрес репозитория помощника>
cd <проект>-assistant
```

**Своего бэкенда с `main.py` ещё нет** (например, практика «Конфигурирования», на которой он создаётся, у вас позже на этой неделе) — работайте с учебным бэкендом курса. Это каталог [`templates/sample-backend/`](../templates/sample-backend/) в репозитории курса: FastAPI-приложение в одном `main.py` с `GET /`, `GET /health` и двумя эндпоинтами других методов. Репозиторий помощника всё равно назовите `<проект>-assistant` по имени будущего репозитория бэкенда и создайте на том хостинге, где он будет. Затем скопируйте учебный бэкенд в родительский каталог, рядом с помощником, под именем `sample-backend`. Из корня помощника, где `<клон курса>` — путь к вашему клону репозитория курса (или к каталогу, куда вы скачали его архив):

```bash
cp -r <клон курса>/templates/sample-backend ../sample-backend
ls ../sample-backend/main.py
```

PowerShell:

```powershell
Copy-Item -Recurse <клон курса>\templates\sample-backend ..\sample-backend
Test-Path ../sample-backend/main.py
```

Дальше везде, где написано `../<проект>`, у вас `../sample-backend`, а `git -C ../<проект> pull` пропускайте: копия — не git-репозиторий. Когда появится свой бэкенд, склонируйте его рядом и поменяйте **одну строку** в `.env` помощника: `AI_REPO_ROOT=../<проект>` (и ту же строку в `.env.example`, шаг 2.2). Правку `.env.example` закоммитьте в ветку, в которой сейчас работаете, или отдельным маленьким PR в `main`. Код помощника от этого не меняется. Если эндпоинты своего бэкенда объявлены не в `main.py` в корне, поправьте и `AI_ENDPOINT_FILES` (шаг 1.3).

**Как понять, что получилось** (у каждого). В каталоге помощника `git status` печатает `On branch main` и `nothing to commit`, а `ls ../<проект>/main.py` (PowerShell: `Test-Path ../<проект>/main.py`) находит файл приложения бэкенда (`True` в PowerShell); на учебном бэкенде — `ls ../sample-backend/main.py`.

**Если не получилось**

- `../<проект>/main.py` не найден — клон помощника лежит не рядом с клоном бэкенда (перенесите каталог помощника целиком) или в клоне бэкенда выбрана ветка без кода приложения. Посмотрите ветки: `git -C ../<проект> branch -a`. Переключитесь на ту, где есть `main.py`: `main`, если PR с приложением уже влит, иначе ветку этого PR (`git -C ../<проект> switch <ветка>`). Помощник читает те файлы бэкенда, что лежат на диске, ветка ему не важна. Если `main.py` у вас в другом месте (например, `app/main.py`), запомните путь: он понадобится в шаге 1.3. Если `main.py` нет ни в одной ветке — бэкенд ещё не создан: возьмите учебный (абзац «Своего бэкенда с `main.py` ещё нет» выше).
- `Repository not found` или `Permission denied` при `git clone` — вам не выдали доступ. Попросите участника, создавшего репозиторий.
- `git push` отвечает `rejected` — на хостинге при создании репозитория добавили README или `.gitignore`. Удалите репозиторий на хостинге и локальный клон и создайте его заново, пустым.

### 1. Python 3.11–3.13 в окружении помощника (10–20 мин)

CrewAI не устанавливается на Python 3.14 (у пакета ограничение `<3.14`), а установщик с python.org сейчас по умолчанию ставит именно 3.14. У помощника своё окружение, в каталоге его репозитория. Окружение бэкенда из «Конфигурирования» вы не трогаете: в нём другие зависимости, и помощник код бэкенда не импортирует.

В корне репозитория помощника, с активированным окружением, если оно уже есть, выполните `python --version`.

- `Python 3.11.x`, `3.12.x` или `3.13.x` — переходите к пункту 2.
- `Python 3.14.x` или окружения ещё нет — создайте окружение заново на 3.12. Старый каталог окружения (обычно `venv`) удаляется целиком: кроме установленных пакетов, в нём ничего нет. Если каталога нет, первую строку пропустите.

PowerShell (Windows):

```powershell
Remove-Item -Recurse -Force venv
py -3.12 -m venv venv
venv\Scripts\Activate.ps1
python --version
```

Git Bash (Windows):

```bash
rm -rf venv
py -3.12 -m venv venv
source venv/Scripts/activate
python --version
```

macOS / Linux: `rm -rf venv`, `python3.12 -m venv venv`, `source venv/bin/activate`.

Если команда ведёт проект на uv: `uv venv --python 3.12 --seed` (создаст `.venv`, нужный Python uv скачает сам), активация — `.venv\Scripts\Activate.ps1`, `source .venv/Scripts/activate` или `source .venv/bin/activate`, а пакеты в пункте 2 ставьте через `uv pip install` с теми же аргументами.

**Как понять, что получилось.** `python --version` печатает `Python 3.12.x` (годится 3.11–3.13), а `python -c "import sys; print(sys.prefix)"` — путь внутри каталога `<проект>-assistant`, оканчивающийся на `venv` или `.venv`. `git status` не показывает `venv/`: каталог игнорируется (пункт 0).

**Если не получилось**

- `py -3.12` отвечает, что такой версии нет, — Python 3.12 не установлен. Если Python ставили через Python install manager (как в «Конфигурировании»), выполните `py install 3.12`; иначе установите 3.12 с python.org и откройте новый терминал.
- PowerShell не даёт выполнить `Activate.ps1` («выполнение сценариев отключено», `running scripts is disabled`) — выполните `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` и повторите активацию.
- `Remove-Item` / `rm` не удаляет каталог: «файл используется другим процессом» — окружение активно в другом окне терминала или в редакторе. Закройте их и повторите.

### 2. Библиотеки помощника (5 мин действий + 25–40 мин установки)

В окружении помощника поставьте библиотеки с точными версиями:

```bash
pip install crewai==1.15.22 pydantic-settings==2.15.0
```

Команда ставит около 140 пакетов и идёт 25–40 минут. Не прерывайте её. На паре вы зафиксируете эти версии в `requirements.txt` помощника (шаг 1.2).

Проверка (первый импорт идёт до полутора минут, ждите):

```bash
python -c "import crewai, pydantic_settings; print(crewai.__version__)"
```

**Как понять, что получилось.** Напечатано `1.15.22`, traceback нет.

**Если не получилось**

- `No matching distribution found for crewai==1.15.22` или `Could not find a version that satisfies the requirement crewai` — Python вне диапазона 3.11–3.13. Вернитесь к пункту 1.
- `ResolutionImpossible`, а выше в выводе есть `WARNING: Skipping page https://pypi.org/simple/… Content-Type: Unknown` — это сбой сети, а не конфликт версий. Повторите ту же команду.
- Установка оборвалась по таймауту или с `ReadTimeoutError` — повторите ту же команду: скачанное уже в кеше pip, второй заход быстрее.
- `ModuleNotFoundError` при проверке — пакеты ушли в другое окружение. `python -m pip --version` должен показать путь внутри вашего `venv`.

### 3. Путь А: локальная модель (10 мин + загрузка 2,5 ГБ)

Основной путь: локально и бесплатно. Модель весит 2,5 ГБ — качайте дома, на паре по общему каналу аудитории это не получится.

1. Установить Ollama: [ollama.com/download](https://ollama.com/download), 10 минут.
2. Скачать модель: `ollama pull qwen3:4b-instruct` (2,5 ГБ — [карточка модели](https://ollama.com/library/qwen3), тег `4b-instruct` виден на вкладке Tags). Нужно около 3 ГБ свободной оперативной памяти сверх занятой системой. Если машина мощная и хочется модель крупнее — `qwen2.5:7b` (4,7 ГБ, контекст 32K).
3. Проверить, что модель отвечает: `ollama run qwen3:4b-instruct "скажи привет"`. Ответ печатается, и команда завершается сама. Первый запуск на CPU может занять несколько минут: модель загружается в память.
4. ⚠️ **Проверить, что модель умеет вызывать инструменты.** Это главное требование сегодняшнего занятия, и ему удовлетворяет не каждая модель: у модели в Ollama должна быть возможность **tools** (на карточке модели она указана рядом с размерами). У `qwen2.5-coder` её нет — Ollama просто откажется принимать запрос с инструментами. Проверка (на Windows — в Git Bash):

```bash
curl -s http://localhost:11434/api/chat -d '{
  "model": "qwen3:4b-instruct",
  "stream": false,
  "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
  "tools": [{"type": "function", "function": {
    "name": "get_tasks", "description": "Возвращает задачи по приоритету",
    "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
    "required": ["priority"]}}}]}'
```

   Ожидаемый ответ — JSON, в котором есть `"tool_calls"` с именем `get_tasks`. Если вместо этого пришло `{"error":"... does not support tools"}` — модель для занятия не годится, берите другую с возможностью tools. `{"error":"model '...' not found"}` — модель не скачана, вернитесь к пункту 2. Если пришёл обычный текстовый ответ без `tool_calls` — модель инструменты принимает, но в этом запросе решила не вызывать; для занятия это допустимо, вернёмся к этому в шаге 3.2.

**Если не получилось.** `ollama pull` падает с `redirect target not allowed … resolves to non-public 198.18.x.x` — загрузку ломает VPN или прокси с подменой DNS (fake-IP). Отключите VPN или режим TUN на время загрузки либо скачайте модель в другой сети.

### 4. Путь Б: облачный провайдер (15–25 мин)

Запасной на занятии и обязательный для домашнего задания. Нужен ключ любого облачного сервиса с **OpenAI-совместимым API**, у которого модель умеет вызывать функции. Какой именно сервис — курсу всё равно: смысл задания в том, что провайдер меняется правкой `.env`, а не кода. Ключ нужен **минимум одному человеку в команде**; если путь А не завёлся ни у кого — каждому. Три рабочих варианта:

| Провайдер | Что нужно для регистрации | `CLOUD_BASE_URL` | `CLOUD_MODEL` | `CLOUD_PROJECT` |
|---|---|---|---|---|

   PowerShell (5.1 и 7). JSON с кавычками PowerShell передаёт в `curl.exe` по-разному в разных версиях, поэтому тело запроса сначала пишется в файл `body.json` (UTF-8 без BOM), а `curl.exe` читает его через `@`. Пишите именно `curl.exe`: просто `curl` в Windows PowerShell 5.1 — другая команда.

```powershell
   "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},

  -H "Authorization: Bearer <ВАШ_КЛЮЧ>" -H "Content-Type: application/json" `
  -H "OpenAI-Project: <ВАШ_КАТАЛОГ>" `

```

   Ответ пришёл, но `tool_calls` в нём нет, а есть обычный текст — модель инструменты приняла, но вызывать не стала: для занятия допустимо, вернёмся к этому в шаге 3.2.

### Шаг 1.2: Зависимости помощника в репозитории (5 мин)

**Зачем это нужно.** Версии фиксируем явно: CrewAI меняет API между мажорными версиями, и «у меня работало» без пина превращается в сломанный CI у всей команды. Помощник должен ставиться одной командой `pip install -r requirements.txt` — так его поставят новый участник и CI.

**Что сделать**

1. Убедитесь, что CrewAI уже установлен на подготовке (импорт идёт до полутора минут):

```bash
python -c "import crewai, pydantic_settings; print(crewai.__version__)"
```

   Напечатано `1.15.22` — дальше. `ModuleNotFoundError` — см. «Если не получилось».

2. Создайте в корне репозитория помощника `requirements.txt`:

```
crewai==1.15.22
pydantic-settings==2.15.0
```

3. Проверьте, что файл ставится и зависимости не конфликтуют (на uv: `uv pip install -r requirements.txt` и `uv pip check`):

```bash
pip install -r requirements.txt
pip check
```

   Ожидаемо: строки `Requirement already satisfied`, ничего не скачивается, в конце нет `ERROR`; `pip check` печатает `No broken requirements found.`

4. Закоммитьте. Здесь и во всех коммитах занятия тип и формат сообщения — как в `CONTRIBUTING.md` бэкенда вашей команды: помощник — проект той же команды. Сообщения ниже — только примеры по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/) с самыми распространёнными типами `feat`, `chore` и `docs`. Если ваш формат требует область (`feat(ai): …`) или другие типы, пишите по нему.

```bash
git add requirements.txt
git commit -m "chore: add assistant dependencies"
```

**Как понять, что получилось.** Напечатано `1.15.22`, `pip check` — `No broken requirements found.`, `git log --oneline -1` показывает ваш коммит.

**Если не получилось**

- `ModuleNotFoundError: No module named 'crewai'` в пункте 1 — подготовка не сделана или активно окружение бэкенда, а не помощника. ### Шаг 1.3: Каталоги, путь к бэкенду и контракт вашего Tool (10 мин)

**Зачем это нужно.** Контракт, записанный в одном месте, не даёт Driver и Navigator реализовывать разное. Каталоги и путь к бэкенду задаём сейчас: Tool будет читать бэкенд, а пара, которая пишет Tool, должна получить настройку пути вместе с каркасом.

**Что сделать**

1. Создайте структуру. Linux / macOS / Git Bash:

```bash
mkdir -p ai/tools ai/traces docs
touch ai/__init__.py ai/tools/__init__.py ai/traces/.gitkeep docs/.gitkeep
```

   PowerShell:

```powershell
New-Item -ItemType Directory -Force ai\tools, ai\traces, docs
New-Item -ItemType File -Force ai\__init__.py, ai\tools\__init__.py, ai\traces\.gitkeep, docs\.gitkeep
```

   Пустые файлы `.gitkeep` нужны потому, что git не хранит пустые каталоги: без них на второй машине команды не окажется `ai/traces/` и `docs/`, и запись логов в блоке 3 упадёт.

2. Укажите помощнику, где лежит бэкенд. Создайте в корне репозитория помощника файл `.env` (UTF-8) с одной строкой — путём к клону бэкенда относительно каталога помощника:

```
AI_REPO_ROOT=../<проект>
```

   В PowerShell создавайте файл так: `Set-Content -Encoding utf8 .env "AI_REPO_ROOT=../<проект>"`. Не используйте `echo … > .env`: Windows PowerShell 5.1 запишет файл в UTF-16, и конфигурация упадёт с `UnicodeDecodeError`. На учебном бэкенде строка такая: `AI_REPO_ROOT=../sample-backend` («Подготовка», п. 0); когда появится свой бэкенд, поменяете только её. Если эндпоинты бэкенда объявлены не в `main.py` в корне (например, в `app/main.py`), добавьте строку `AI_ENDPOINT_FILES=app/main.py`; несколько файлов перечисляются через запятую. `.env` уже игнорируется (`.gitignore` из «Подготовки», п. 0): путь у каждого участника свой, в git он не попадает.

   Создайте `ai/config.py` — первую версию конфигурации: пока в ней только бэкенд, настройки модели вы допишете в шаге 2.1.

```python
from pydantic import DirectoryPath
from pydantic_settings import BaseSettings, SettingsConfigDict


class AISettings(BaseSettings):
    """Конфигурация помощника. Значения берутся из .env или переменных окружения."""

    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    ai_repo_root: DirectoryPath  # путь к клону бэкенда; обязателен, задаётся в .env
    ai_endpoint_files: str = "main.py"  # файлы с эндпоинтами через запятую, от AI_REPO_ROOT


settings = AISettings()
```

   `DirectoryPath` проверяет при старте, что каталог существует: опечатка в пути остановит программу сразу, с понятным сообщением, а не посреди работы агента. Относительный путь считается от каталога, из которого вы запускаете Python, поэтому все команды занятия запускаются из корня репозитория помощника. `ai_endpoint_files` нужен эталонному Tool `find_endpoint` (пункт 3); если ваш Tool читает другие файлы бэкенда, заведите для них свою настройку по тому же принципу: какие файлы читать, решает конфигурация, а не модель.

   Проверка (импорт идёт несколько секунд):

```bash
python -c "from ai.config import settings; print(settings.ai_repo_root.resolve())"
```

   Напечатан абсолютный путь к клону бэкенда, например `C:\Users\<вы>\projects\<проект>`. `Path does not point to a directory` — путь в `.env` неверный; `Field required` — нет `.env` или запуск не из корня помощника.

3. Выберите Tool. Реализуется Tool, который ваша команда спроектировала на воркшопе 1, если он отвечает четырём условиям:
   - только читает код бэкенда из `AI_REPO_ROOT`;
   - не принимает от модели путь к файлу и не обходит дерево каталогов: какие файлы читать, задаёт конфигурация;
   - не запускает ни код бэкенда, ни другие программы (линтер, тесты, `git`) — это темы цикла 2;
   - к практике 1 в бэкенде уже есть то, что Tool ищет (`main.py` с `GET /` и `GET /health`; в учебном бэкенде это тоже есть), и на этих данных он возвращает успешный ответ: без этого `_check.py` в шаге 2.4 не получит строку `ok`.

   Если хотя бы одно условие не выполняется или спецификации нет, реализуйте эталон курса — `find_endpoint` по контракту ниже, а свою спецификацию сравните с ним в ADR (шаг 4.3).

   Создайте `ai/tools/<имя_вашего_инструмента>.py` и запишите в начало контракт с воркшопа 1:

```python
# Контракт Tool (воркшоп 1)
# Имя:        ...
# Назначение: одно предложение, которое прочитает LLM
# Вход:       имя: тип — обязателен/нет, допустимые значения
#             (параметров нет — «нет» и какая настройка задаёт, что читать)
# Выход:      JSON-строка; поля при успехе / поля при ошибке
# Краевые случаи: что считаем ошибкой и какой текст возвращаем
```

   Контракт эталона — для файла `ai/tools/find_endpoint.py`:

```python
# Контракт Tool (эталон курса)
# Имя:        find_endpoint
# Назначение: найти в коде бэкенда обработчик HTTP-эндпоинта по методу и пути
# Вход:       path: str — обязателен, начинается с "/";
#             method: str — одно из GET, POST, PUT, PATCH, DELETE, по умолчанию GET
# Выход:      JSON-строка; ok: status, method, path, function, file, line;
#             error: status, message (+ known — список найденных эндпоинтов)
# Краевые случаи: неверный метод; путь без "/"; эндпоинт не найден (error + known);
#             файл из AI_ENDPOINT_FILES не найден или не разбирается (error с именем файла)
```

4. Проверьте контракт по трём вопросам:
   - Все ли параметры имеют тип и явный список допустимых значений? «Строка» недостаточно, нужно «одно из `GET`, `POST`, `PUT`, `PATCH`, `DELETE`». Если параметров у Tool нет, в строке «Вход» записано «нет» и названа настройка, которая задаёт, что читать (например, `AI_ENDPOINT_FILES`); тогда краевые случаи вашего Tool — ошибки конфигурации и данных (файла нет, файл не разбирается), и проверять их вы будете через конфигурацию (шаг 2.4).
   - Можно ли по одному предложению назначения понять, **когда** этот Tool вызывать, а когда нет? Это описание читает не человек, а модель.
   - Что возвращается, если данных нет? Ответ зависит от того, что ищет Tool. Если Tool ищет **список** (все эндпоинты с методом `POST`), пустой список — это успех, а не ошибка; так и запишите. Если Tool ищет **одну сущность** (обработчик `GET /health`), «не найден» — это `"status": "error"` с сообщением, чего нет, и полезно вернуть, что есть: у `find_endpoint` это поле `known`, по нему агент может исправиться.

### Шаг 2.1: `ai/config.py` (10 мин)

**Зачем это нужно.** Провайдер модели, имя модели и API-ключ не должны лежать в коде: в цикле 6 те же агенты поедут в CI, где Ollama нет.

**Что сделать.** Допишите в `ai/config.py` из шага 1.3 настройки модели. Итоговый файл целиком:

```python
from typing import Literal

from pydantic import DirectoryPath, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class AISettings(BaseSettings):
    """Конфигурация помощника. Значения берутся из .env или переменных окружения."""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",  # в .env лежат и переменные библиотек (CREWAI_TRACING_ENABLED)
    )

    llm_provider: Literal["ollama", "cloud"] = "ollama"

    ollama_model: str = "qwen3:4b-instruct"
    ollama_base_url: str = "http://localhost:11434"

    # cloud — любой провайдер с OpenAI-совместимым API
    cloud_model: str = ""
    cloud_base_url: str = "https://openrouter.ai/api/v1"
    cloud_api_key: SecretStr | None = None
    cloud_project: str = ""  # нужен только там, где провайдер требует каталог/проект

    llm_temperature: float = 0.1

    # бэкенд, с которым работает помощник (шаг 1.3)
    ai_repo_root: DirectoryPath  # путь к клону бэкенда; обязателен, задаётся в .env
    ai_endpoint_files: str = "main.py"  # файлы с эндпоинтами через запятую, от AI_REPO_ROOT


settings = AISettings()
```

Три места, где обычно теряют час:

- `extra="ignore"` обязателен. По умолчанию `pydantic-settings` работает в режиме `extra="forbid"`, а в `.env` будут и переменные, которые читает не `AISettings`, а библиотеки: в шаге 2.2 туда ляжет `CREWAI_TRACING_ENABLED` для CrewAI. Без `ignore` конфиг упадёт с ошибкой `Extra inputs are not permitted`.
- `Literal[...]` — опечатка `LLM_PROVIDER=olama` в `.env` упадёт сразу при старте с понятным текстом, а не через десять минут внутри агента.
- `SecretStr` вместо `str` для ключа. Обычная строка печатается в `repr` целиком — и уезжает в скриншот, в лог, в описание PR. `SecretStr` показывает звёздочки, а настоящее значение отдаёт только по явному `.get_secret_value()`.

**Как понять, что получилось**

```bash
python -c "from ai.config import settings; print(settings)"
```

Вывод: `llm_provider='ollama' ollama_model='qwen3:4b-instruct' ... cloud_api_key=None cloud_project='' llm_temperature=0.1 ai_repo_root=WindowsPath('../<проект>') ai_endpoint_files='main.py'` (на macOS и Linux — `PosixPath`). Ключа в `.env` ещё нет, поэтому `None` — это правильно; после шага 2.2 с пустым `CLOUD_API_KEY=` здесь будет `SecretStr('')`, а когда впишете ключ — `SecretStr('**********')`. Если вместо звёздочек покажется сам ключ, значит остался тип `str`.

**Если не получилось.** `ModuleNotFoundError: No module named 'ai'` — запускайте из корня репозитория помощника и проверьте `ai/__init__.py`. Остальные ошибки этого шага (`Extra inputs are not permitted`, `Input should be 'ollama' or 'cloud'`, `ai_repo_root` с `Field required` или `Path does not point to a directory`) разобраны в таблице Troubleshooting.

**Документация.** [pydantic-settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/) — раздел «Dotenv (.env) support», если непонятно, откуда берутся значения.

### Шаг 2.2: `.env`, `.env.example` и `.gitignore` (10 мин)

**Зачем это нужно.** `.env` с ключом в истории Git — это утечка, которую нельзя отменить `git revert`. А `.env.example` — единственный способ для нового человека узнать, какие переменные нужны.

**Что сделать**

1. Убедитесь, что `.env` игнорируется: `git check-ignore -v .env` печатает строку с правилом — `.gitignore:4:.env	.env`, если `.gitignore` создан по «Подготовке», п. 0. Если не напечатано ничего — допишите строку `.env` в конец `.gitignore`, закоммитьте его и повторите.
2. Допишите в конец `.env` из шага 1.3 (строка `AI_REPO_ROOT` остаётся) блок настроек модели. Сохраняйте в UTF-8.

```
LLM_PROVIDER=ollama
OLLAMA_MODEL=qwen3:4b-instruct
OLLAMA_BASE_URL=http://localhost:11434
CLOUD_BASE_URL=https://openrouter.ai/api/v1
CLOUD_MODEL=
CLOUD_API_KEY=
CLOUD_PROJECT=
LLM_TEMPERATURE=0.1
CREWAI_TRACING_ENABLED=false
```

   `OLLAMA_MODEL` — ваша модель с tools, та, что скачана и прошла проверку 6 (`qwen3:4b-instruct` или `qwen2.5:7b`).
   `CLOUD_*` — это ваша четвёрка из «Подготовки», путь Б; пока её нет, оставьте значения пустыми. У OpenRouter `CLOUD_PROJECT` остаётся пустым, у Yandex AI Studio туда идёт идентификатор каталога. Остальной файл и весь код от смены провайдера не меняются.
   `CREWAI_TRACING_ENABLED=false` CrewAI читает из `.env` сам. Без неё в конце каждого запуска агента он спрашивает `Share this execution trace with CrewAI? [y/N]` и ждёт ответа 20 секунд: выгружать промпты и данные на чужой сервис не нужно.

3. Создайте в корне репозитория помощника `.env.example`: все строки `.env` **с пустыми `CLOUD_API_KEY` и `CLOUD_PROJECT`**, плюс строка `AI_ENDPOINT_FILES=main.py`, если в `.env` её нет. В `.env.example` перечисляются все переменные из `config.py`, даже те, у которых есть значение по умолчанию: так новый участник видит, что вообще можно настроить. `AI_REPO_ROOT=../<проект>` в нём — с настоящим именем каталога бэкенда: по нему новый участник поймёт, куда класть клон (на учебном бэкенде — `../sample-backend`, поменяете вместе с `.env`). `OLLAMA_MODEL` — модель, на которой работает команда (по ней новый участник поймёт, что качать); `CLOUD_BASE_URL` и `CLOUD_MODEL` можно оставить как в `.env`, это не секреты. Коммитится именно `.env.example`.

**Как понять, что получилось.** `git status --short --ignored` показывает `!! .env` (файл игнорируется) и `?? .env.example`; строки `!! venv/` и `!! ai/__pycache__/` тоже нормальны. Строки с `.env` без `!!` быть не должно. `python -c "from ai.config import settings; print(settings)"` печатает те же поля, что в шаге 2.1, но с `cloud_api_key=SecretStr('')`.

**Если не получилось**

- `.env` виден в `git status` без `!!` — файл был добавлен в индекс раньше: `git rm --cached .env`.
- Если `.env` с ключом уже попал в коммит — считайте ключ скомпрометированным: отзовите его в консоли провайдера и выпустите новый. Чистка истории делается отдельно и сегодня не нужна.

### Шаг 2.3: `ai/llm_factory.py` и smoke-тест (25 мин)

**Зачем это нужно.** Это единственная точка в проекте, которая знает, какая модель используется. Всё остальное просит `get_llm()` — благодаря этому в цикле 6 вы подмените LLM моком в тестах, не трогая агентов.

**Что сделать.** Создайте `ai/llm_factory.py`:

```python
from crewai import LLM

from ai.config import settings


def get_llm() -> LLM:
    """Возвращает LLM согласно .env. Единственная точка переключения провайдера."""
    if settings.llm_provider == "ollama":
        return LLM(
            model=f"ollama/{settings.ollama_model}",
            base_url=settings.ollama_base_url,
            temperature=settings.llm_temperature,
        )

    if not settings.cloud_api_key or not settings.cloud_model:
        raise RuntimeError(
            "LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст. Проверьте .env"
        )

    return LLM(
        model=f"openai/{settings.cloud_model}",
        base_url=settings.cloud_base_url,
        api_key=settings.cloud_api_key.get_secret_value(),
        project=settings.cloud_project or None,  # нужен, например, Yandex AI Studio
        temperature=settings.llm_temperature,
    )
```

Что здесь важно и не очевидно:

- Префикс в `model` (`ollama/`, `openai/`) — это то, как CrewAI выбирает провайдера. Без префикса он угадывает по имени модели и почти наверняка уйдёт в настоящий OpenAI.
- Префикс `openai/` вместе с явным `base_url` означает «говори по протоколу OpenAI вот с этим адресом». Так работает любой OpenAI-совместимый сервис: OpenRouter, Yandex AI Studio, ваш собственный vLLM. Именно поэтому смена провайдера — это правка `.env`, а не кода. У CrewAI есть и префиксы конкретных провайдеров (`openrouter/` и другие), но они привязывают код к провайдеру, а часть из них требует дополнительного пакета — нам нужно обратное.
- Модель у некоторых провайдеров содержит слеши и двоеточия (`qwen/qwen3-coder:free` — пример формы имени, такой бесплатной модели уже нет; `gpt://b1g…/yandexgpt-5.1`) — это нормально: всё, что после первого префикса `openai/`, уезжает провайдеру как есть.
- `project` передаётся, только если он заполнен. Yandex AI Studio без идентификатора каталога запрос не примет, OpenRouter про этот параметр ничего не знает — поэтому `or None`.
- Проверка ключа стоит **до** создания `LLM`: ваше сообщение понятнее, чем то, что выдаст библиотека.
- `temperature=0.1` — для агента, который вызывает инструменты, творчество вредно.

**Smoke-тест**

```bash
python -c "from ai.llm_factory import get_llm; print(get_llm().call('Ответь одним словом: работает?'))"
```

**Как понять, что получилось.** В консоли короткий ответ модели. Ждать придётся: импорт CrewAI занимает от 10 секунд до полутора минут при каждом запуске, а на пути А, если модель ещё не в памяти, загрузка добавляет от десятков секунд до нескольких минут. Не прерывайте.

**Проверка переключения.** Если у вашей команды есть облачный ключ — поменяйте в `.env` `LLM_PROVIDER=cloud`, впишите свою четвёрку «адрес — модель — ключ — каталог» и запустите ту же команду ещё раз. Ответ должен прийти снова, **без единой правки в коде**; затем верните `LLM_PROVIDER=ollama`.
Если ключа нет — проверьте переключение наполовину: поставьте `LLM_PROVIDER=cloud` с пустым `CLOUD_API_KEY` и убедитесь, что `get_llm()` падает с **вашим** сообщением `LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст`, а не с ошибкой из недр библиотеки. Это подтверждает, что ветка провайдера выбирается конфигом. Полное переключение доделаете дома — оно входит в домашнее задание.

**Если не получилось**

- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=ollama` — сообщение обманчивое, речь не про OpenAI: не поднят сервер Ollama. Запустите `ollama serve` и повторите.
- `AuthenticationError: Error code: 401` — ключ неверный, отозван или не от этого адреса. Сверьте `CLOUD_API_KEY` и `CLOUD_BASE_URL`: ключ OpenRouter к адресу Yandex AI Studio не подойдёт.
- `NotFoundError` / `model not found` — имя модели неверное или больше не обслуживается. Возьмите актуальное со страницы моделей своего провайдера и впишите в `CLOUD_MODEL`.
- `429` / `rate-limited` при `LLM_PROVIDER=cloud` — бесплатная модель перегружена или исчерпан лимит. CrewAI сам повторяет запрос несколько раз, и каждый повтор списывается из суточного лимита. Подождите минуту или возьмите другую бесплатную модель; если кончился дневной лимит — работайте по пути А, облачную проверку доделайте дома.
- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=cloud` — адрес недоступен: опечатка в `CLOUD_BASE_URL` или сеть не выпускает запрос наружу.

**Документация.** [CrewAI: LLMs](https://docs.crewai.com/en/concepts/llms) — разделы «Ollama» и «Custom OpenAI-Compatible Endpoint» (во вкладке OpenAI), если непонятно, как CrewAI выбирает провайдера.

### Шаг 2.4: Ваш Tool (25 мин)

**Зачем это нужно.** Tool — это граница между вероятностной моделью и вашей детерминированной системой. Всё, что модель может испортить, должно останавливаться здесь и возвращаться агенту текстом, который он способен прочитать и исправить.

**Что сделать.** В файле `ai/tools/<имя>.py`, где лежит контракт, напишите Tool. Данные — код бэкенда: Tool читает файлы из `settings.ai_repo_root`, ничего в них не меняет, код бэкенда не импортирует и не запускает (у помощника другое окружение, зависимостей бэкенда в нём нет). Ниже каркас; содержательная часть у каждой команды своя.

```python
import json

from crewai.tools import tool
```

Пять требований, по которым это будут проверять на peer review:

1. **Docstring обязателен.** Это не стиль, которому договорились придерживаться в команде, а обязательная механика: `@tool` берёт описание для модели именно из docstring, а функция без него падает с `ValueError: Function must have a docstring` ещё на импорте. Пишите его для LLM: явно перечисляйте допустимые значения. Не ставьте в docstring конкретный пример значения, похожий на настоящий (путь эндпоинта, имя файла): маленькая модель подставляет его, когда пользователь значение не назвал (это проверяет сценарий 2 шага 3.3).
2. **Имя, которое видит модель, — это аргумент декоратора**, а не имя функции. `@tool("find_endpoint")` над `def your_tool_name(...)` даст модели инструмент `find_endpoint`. Имя функции модель не видит вообще.
3. **Аннотации типов у всех параметров.** По ним CrewAI строит схему аргументов, которую видит модель.
4. **Безопасный возврат.** Из тела Tool не должно вылетать необработанное исключение. Любая ошибка — `return _fail("...")` с текстом, из которого понятно, **что именно** исправить: «method должен быть одним из GET, POST, PUT, PATCH, DELETE, получено 'FETCH'» вместо «invalid input». Один случай не в вашей власти: если обязательный аргумент не передан или пришёл не того типа, CrewAI отклонит вызов по схеме ещё до вашего кода (`ValueError` со словами `arguments validation failed` и `Field required`). У Tool без параметров то же с лишним аргументом: вызов `.run(method="FETCH")` падает с `TypeError: … got an unexpected keyword argument 'method'` при входе в функцию, до первой строки вашего кода. Это не провал вашего Tool, и в `_check.py` такие вызовы не включайте.
5. **Одна строка на выходе.** Всегда `str` (JSON внутри строки), всегда одинаковая структура — и при успехе, и при ошибке.

Остальным — образец формы. `_fail` здесь принимает дополнительные поля (`known`), формат ошибки тот же: `status` и `message`.

```python
import ast
import json

from crewai.tools import tool

from ai.config import settings

METHODS = ("GET", "POST", "PUT", "PATCH", "DELETE")


def _fail(message: str, **extra) -> str:
    """Единый формат ошибки, который вернётся агенту."""
    return json.dumps({"status": "error", "message": message, **extra}, ensure_ascii=False)


def _collect_endpoints() -> list[dict]:
    """Разбирает файлы бэкенда через ast. Код бэкенда не импортируется и не запускается."""
    found = []
    for name in settings.ai_endpoint_files.split(","):
        name = name.strip()
        source = (settings.ai_repo_root / name).read_text(encoding="utf-8")
        for node in ast.walk(ast.parse(source, filename=name)):
            if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
                continue
            for dec in node.decorator_list:
                # ищем декораторы вида @app.get("/путь") или @router.post("/путь")
                if (
                    isinstance(dec, ast.Call)
                    and isinstance(dec.func, ast.Attribute)
                    and dec.func.attr.upper() in METHODS
                    and dec.args
                    and isinstance(dec.args[0], ast.Constant)
                    and isinstance(dec.args[0].value, str)
                ):
                    found.append({
                        "method": dec.func.attr.upper(),
                        "path": dec.args[0].value,
                        "function": node.name,
                        "file": name,
                        "line": node.lineno,
                    })
    return found


@tool("find_endpoint")
def find_endpoint(path: str, method: str = "GET") -> str:
    """Ищет в коде бэкенда обработчик HTTP-эндпоинта по методу и пути и возвращает
    имя функции, файл и строку. Вызывай, когда нужно убедиться, что эндпоинт
    существует, перед тем как писать к нему код или тест. Путь бери у пользователя,
    не придумывай его.

    Args:
        path: путь эндпоинта, обязательно начинается с "/".
        method: HTTP-метод, одно из GET, POST, PUT, PATCH, DELETE. По умолчанию GET.

    Returns:
        JSON-строка. При успехе: {"status": "ok", "method", "path", "function", "file", "line"}.
        При ошибке: {"status": "error", "message": ..., "known": [...]}.
    """
    method = method.strip().upper()
    if method not in METHODS:
        return _fail(f"method должен быть одним из {', '.join(METHODS)}, получено '{method}'")
    if not path.startswith("/"):
        return _fail(f"path должен начинаться с '/', получено '{path}'")

    try:
        endpoints = _collect_endpoints()
    except (OSError, SyntaxError, ValueError) as exc:  # ValueError — в т. ч. UnicodeDecodeError
        return _fail(f"не удалось разобрать файлы бэкенда из AI_ENDPOINT_FILES: {exc}")

    for ep in endpoints:
        if ep["method"] == method and ep["path"] == path:
            return json.dumps({"status": "ok", **ep}, ensure_ascii=False)

    known = [f'{ep["method"]} {ep["path"]}' for ep in endpoints]
    return _fail(f"эндпоинт {method} {path} не найден в бэкенде", known=known)
```

## Блок 3. Агент и проверка на прочность (01:40–02:20)

### Шаг 3.1: `ai/run_agent.py` (15 мин)

**Зачем это нужно.** Сборка контура целиком: модель получает описание вашего Tool, решает вызвать его, получает результат и формулирует ответ.

**Что сделать.** Создайте `ai/run_agent.py`:

```python
from crewai import Agent, Crew, Task

from ai.llm_factory import get_llm
from ai.tools.<модуль> import <имя_инструмента>

agent = Agent(
    role="<роль помощника: например, Помощник разработчика бэкенда>",
    goal="<чего агент добивается — одно предложение>",
    backstory="<кто он и как себя ведёт: например, прежде чем что-то утверждать о коде, проверяет это инструментом>",
    tools=[<имя_инструмента>],
    llm=get_llm(),
    verbose=True,
    max_iter=5,  # страховка от бесконечного цикла; по умолчанию 25
)

task = Task(
    description="<запрос пользователя, для которого нужен ваш инструмент>",
    expected_output="<в каком виде вы хотите финальный ответ>",
    agent=agent,
)

crew = Crew(agents=[agent], tasks=[task], verbose=True)

if __name__ == "__main__":
    print(crew.kickoff())
```

Запустите из корня репозитория и сохраните лог. Первая строка включает режим UTF-8 для Python: без неё на Windows при записи в `tee` / `Tee-Object` CrewAI молча теряет все панели с эмодзи, включая `Tool Execution`, и лог становится бесполезным. Переменная действует до закрытия окна терминала; в новом окне задайте её снова.

### Шаг 3.2: Чтение трассы (10 мин)

**Зачем это нужно.** Отладка агента — это чтение его трассы: логика здесь не в вашем коде, а в последовательности решений модели.

**Что сделать.** Откройте `ai/traces/run-01.log` и ответьте письменно — сразу в черновик ADR, раздел «Наблюдения из трассы» (записывает тестировщик-документатор или вторая пара):

1. Сколько раз вызывался Tool? Если больше одного — почему? Посмотрите `Args` каждого вызова.
2. Какие именно аргументы подставила модель? Совпадают ли они с тем, что описано в вашем docstring? (У Tool без параметров вопрос пропустите.)
3. Финальный ответ основан на `Output` инструмента или содержит факты, которых в `Output` не было?

Концептуально это цикл ReAct: рассуждение → действие → наблюдение. CrewAI 1.15 печатает его как панели `Agent Started` → `Tool Execution Started/Completed` → `Agent Final Answer`; отдельных строк `Thought:` в выводе может не быть, и это не признак поломки.

**Если агент не вызвал Tool и придумал ответ** — проверьте по порядку:

1. Описание в docstring не объясняет, **когда** вызывать инструмент. «Работает с эндпоинтами» модель не поймёт; «ищет обработчик эндпоинта по методу и пути; вызывай, когда нужно убедиться, что эндпоинт существует» — поймёт.
2. `Task.description` сформулирован так, что на него можно ответить без данных. Сделайте запрос конкретным: он должен требовать значения, которого у модели нет.
3. Локальная 4b слабее в function calling, чем облачная. Сначала убедитесь, что модель вообще принимает инструменты (проверка 6 из «Проверки окружения»), потом попробуйте `qwen2.5:7b` — только если она уже скачана (на паре 4,7 ГБ не качайте), а если в команде есть ключ — прогоните тот же сценарий по пути Б. ### Шаг 3.3: Провокация ошибок (15 мин)

**Зачем это нужно.** Агент, который работает только на правильных данных, бесполезен. Паттерн «безопасный возврат» проверяется ровно одним способом: сломать вход специально.

**Что сделать.** Сценарий 1 обязателен, логи двух остальных доберёте дома, если не успеете на паре. На время всех провокаций (включая запуск с ошибкой конфигурации ниже) замените `expected_output` на нейтральное «Короткий ответ на вопрос пользователя; если инструмент вернул ошибку — перескажи её», иначе модель подгоняет ответ под форму основного сценария. Дальше меняйте только `Task.description`, запускайте той же командой, что в шаге 3.1, логи сохраняйте как `run-02.log`, `run-03.log`, `run-04.log`. Модель отвечает не всегда одинаково: если результат кажется случайным, повторите запуск 2–3 раза, а повторы сохраняйте под своими именами — `run-02-2.log`, `run-02-3.log` и т. п., не перезаписывая первый.

1. **Недопустимое значение** (обязательно). Попросите то, чего в допустимых значениях вашего контракта нет, и назовите это значение явно. Для `find_endpoint`: «Проверь, есть ли в бэкенде обработчик для запроса методом `FETCH` по пути `/health`» или путь без `/` («обработчик `GET health`»).
2. **Пустой или отсутствующий вход.** Запрос без обязательного параметра. Для `find_endpoint`: «Найди в бэкенде обработчик эндпоинта, к которому мне нужно написать тест» — путь не назван.
3. **Несуществующая сущность.** Значение правильного формата, которого нет в бэкенде. Для `find_endpoint`: «Есть ли в бэкенде эндпоинт `GET /tickets/export`?»

**Как понять, что получилось.** В логе есть панель `Tool Execution Completed` с вашим `{"status": "error", ...}`, процесс **не падает**, и финальный ответ агента осмысленный: либо повторный вызов с исправленными аргументами, либо вежливое сообщение пользователю. Traceback в консоли — это провал сценария. В сценарии 2 хорош и третий исход: агент вообще не вызывает Tool и просит назвать недостающее значение. Если в сценарии 1 Tool ответил `ok`, посмотрите `Args`: модель могла сама заменить ваше значение допустимым (`FETCH` → `GET`) или дописать `/`. Это находка (ниже); лог с `error` тогда возьмите из сценария 3.

**Если у вашего Tool нет параметров**, ни один из трёх сценариев не даст `error` в трассе: Tool вернёт `ok`, и это правильно. Сценарии всё равно прогоните — они проверяют, как агент обходится с данными Tool. Лог с `error` получите ошибкой конфигурации (командам с `find_endpoint` и другим Tool с параметрами этот запуск — по желанию): запустите основной сценарий с неверным `AI_ENDPOINT_FILES` в переменной окружения (она важнее строки в `.env`, а `.env` не меняется).

Git Bash:

```bash
AI_ENDPOINT_FILES=no_such_file.py python -m ai.run_agent 2>&1 | tee ai/traces/run-05-config-error.log
```

PowerShell (в том же окне, где заданы `PYTHONUTF8` и кодировка из шага 3.1):

```powershell
$env:AI_ENDPOINT_FILES = "no_such_file.py"
python -m ai.run_agent 2>&1 | Tee-Object -FilePath ai\traces\run-05-config-error.log
Remove-Item Env:AI_ENDPOINT_FILES
```

Ожидаемо: в панели `Tool Execution Completed` — `{"status": "error", …No such file…}`, traceback нет, агент сообщает пользователю, что не смог прочитать файлы бэкенда.

Четыре находки, которые ожидаемы и вашей ошибкой не являются. Запишите их в ADR, раздел «Наблюдения из трассы», — это материал для воркшопа 2:

- **Сценарий 1: модель молча исправляет вход.** В проверочных запусках с `find_endpoint` на вопрос «Есть ли в бэкенде эндпоинт `FETCH /health`? Если есть — назови функцию» обе модели (`qwen3:4b-instruct`, `qwen2.5:7b`) передали в Tool `GET` и ответили «есть». Пользователь спрашивал про другой метод, а получил уверенное «да». Когда значение названо явно («запрос методом `FETCH`»), обе модели передали `FETCH` и пересказали ошибку Tool. Запишите, что сделала ваша модель.
- **Сценарий 2: два возможных исхода.** Путь пользователь не назвал. В проверочных запусках с `expected_output` основного сценария модель выдумывала правдоподобный путь: `qwen3:4b-instruct` подставила `/api/v1/users`, `qwen2.5:7b` — `/users`, хотя в docstring сказано «не придумывай»; Tool вернул error со списком `known`, и агент ответил «не найден». С нейтральным `expected_output` `qwen3:4b-instruct` 3 раза из 3 Tool не вызвала и попросила назвать путь (2 раза из 3 — по-английски). У вас может выйти любой из исходов. Запишите, какая модель как себя вела и с каким `expected_output`.
- **Сценарий 3: агент не всегда пользуется тем, что вернул Tool.** В проверочных запусках на несуществующий путь агент ответил коротким «нет» и не назвал эндпоинты из `known`, хотя они были в `Output`. Текст `message` модель, наоборот, может передать пользователю дословно. Учитывайте и то и другое, когда решаете, что Tool возвращает при ошибке.
- **Ошибка конфигурации: агент маскирует её под «нет».** В проверочных запусках с неверным `AI_ENDPOINT_FILES` и `expected_output` основного сценария агент 3 раза из 3 ответил голым «Нет.»: пользователь решит, что эндпоинта нет, хотя помощник просто не прочитал бэкенд. С нейтральным `expected_output` маскировка ослабевает, но не исчезает: 3 раза из 3 ответ «Нет, не найден…», и только за ним — пересказ ошибки чтения файла. Запишите, что ответила ваша модель.

Так выглядит сценарий 2 в проверочном логе (`qwen3:4b-instruct`, `expected_output` основного сценария, сокращено): аргумент придуман, Tool вернул ошибку со списком известных эндпоинтов, процесс не упал.

```

│  тест.
┌──────────── 🔧 Tool Execution Started (#1) ────────────┐
│  Tool: find_endpoint
│  Args: {'path': '/api/v1/users', 'method': 'GET'}
┌──────────── ✅ Tool Execution Completed (#1) ────────────┐
│  Output: {"status": "error", "message": "эндпоинт GET /api/v1/users не
│  найден в бэкенде", "known": ["GET /", "GET /health"]}
┌──────────── ✅ Agent Final Answer ────────────┐
```

Перед коммитом верните в `run_agent.py` исходные `Task.description` и `expected_output` из шага 3.1: в PR `run_agent.py` запускает основной сценарий, а провокации остаются в логах.

**Если не получилось**

- Упал traceback — где-то в Tool осталось необработанное исключение. Вернитесь к шагу 2.4, требование 4.
- Агент получил ошибку, но не исправился и сдался — текст `message` не подсказывает решение. Добавьте в него допустимые значения.
- Агент зациклился на одной ошибке до `max_iter` — противоречие между docstring и валидацией: вы принимаете не то, что обещаете. Сверьте оба места с контрактом из шага 1.3.
- Сценарий 2: Tool вызван с выдуманным аргументом, который **есть в бэкенде** (часто — тем, что стоит примером в docstring), вернул `"status": "ok"`, и агент уверенно отвечает про эндпоинт, о котором его не спрашивали. Если примера нет, а модель всё равно подставляет значение, это свойство модели, а не ошибка вашего кода (см. находки выше). Запишите в ADR, какое значение подставила модель и что ответил агент: это ровно тот класс рисков, который разбирается на воркшопе 2.

### Вторая машина завела свои файлы

Сохраните свою работу, встаньте на опубликованную ветку, сравните свою работу с опубликованной и верните своё. **Внимание:** `git clean` удаляет все неотслеживаемые файлы в `ai/` и `docs/`, не только Tool, — например, черновик `ai/config.py`. Поэтому первые две команды копируют весь `ai/` в `../ai-backup`; не пропускайте их. `.env` рецепт не трогает: игнорируемые файлы `git clean -fd` не удаляет.

Git Bash:

```bash
rm -rf ../ai-backup
cp -r ai ../ai-backup
git fetch
git switch -f main
git branch -D feature/agent-tool-1
git clean -fd -- ai docs requirements.txt
git switch feature/agent-tool-1
git diff --no-index --name-status ai/tools ../ai-backup/tools
```

PowerShell:

```powershell
Remove-Item -Recurse -Force ../ai-backup -ErrorAction SilentlyContinue
Copy-Item -Recurse ai ../ai-backup
git fetch
git switch -f main
git branch -D feature/agent-tool-1
git clean -fd -- ai docs requirements.txt
git switch feature/agent-tool-1
git diff --no-index --name-status ai/tools ../ai-backup/tools
```

`git switch -f main` отбрасывает незакоммиченные правки в отслеживаемых файлах (иначе при симптоме `cannot pull with rebase: You have unstaged changes` переключение не пройдёт) — поэтому копия `../ai-backup` снимается до него. `git branch -D` может ответить `error: branch 'feature/agent-tool-1' not found` — значит, своей локальной ветки у вас не было. Это безвредно, продолжайте.

Последняя команда ничего не меняет: она сравнивает опубликованные файлы Tool с вашей копией. Строки в её выводе означают:

- `A	../ai-backup/tools/<файл>` — файл есть только у вас. Верните его: `cp ../ai-backup/tools/<файл> ai/tools/` (PowerShell: `Copy-Item ../ai-backup/tools/<файл> ai/tools/`). Строки про `__pycache__` пропускайте.
- `M	ai/tools/<файл>` — файл с тем же именем уже опубликован, обычно с контрактом из шага 1.3. **Не копируйте его поверх вслепую:** копия перезапишет опубликованный файл. Сначала посмотрите разницу: `git diff --no-index ai/tools/<файл> ../ai-backup/tools/<файл>`. Если опубликованный файл — каркас с контрактом, перенесите в него свой код вручную, контракт оставьте. Если ваш вариант полнее, скопируйте его и верните в начало контракт из опубликованной версии.
- `D	ai/tools/<файл>` — файл опубликован, а в вашей копии его нет (например, `_check.py`, который написала другая пара). Ничего не делайте: опубликованный файл остаётся.
- Вывода нет — ваша копия совпадает с опубликованной, возвращать нечего.

Если в копии были файлы вне `ai/tools` (например, черновик `ai/config.py` с настройками модели), разберите их так же: `git diff --no-index --name-status ai ../ai-backup`, затем `A` — скопировать, `M` — сравнить и перенести вручную. Строки `D` и уже разобранные строки из `ai/tools` пропускайте: `D` значит, что файла нет в копии, удалять его не нужно (`ai/traces/.gitkeep` нужен для логов).

Проверка: `git status` печатает `On branch feature/agent-tool-1`, а в `ai/tools/` лежит ваш код Tool и контракт из шага 1.3, а не пустой каркас.

Ветка помощника любая. Бэкенд при этом не меняется: ruff только читает его файлы, каталоги `venv` и `.venv` пропускает сам, а флаг `--no-cache` не даёт ему положить в бэкенд каталог кеша `.ruff_cache/` (без флага кеш появляется рядом с конфигурацией ruff бэкенда — `[tool.ruff]` в `pyproject.toml` или `ruff.toml`, если она есть). Правила ruff берёт из этой конфигурации бэкенда, а если её нет — из конфигурации ruff помощника (`[tool.ruff]` в его `pyproject.toml` или `ruff.toml`: команда запускается из корня помощника), если нет и её — свой набор по умолчанию. Найденные замечания — это нормально: ruff при этом завершается с кодом 1. Если в файле только `[]`, а код выхода 0, тоже всё в порядке: в небольшом аккуратном проекте замечаний может не быть (на `../sample-backend` их нет). Тогда посмотрите, как выглядит одно замечание, на заведомо плохой строке. Команда ничего не записывает в репозиторий и печатает JSON с замечанием `F401` (неиспользуемый импорт):

```bash
echo "import os" | ruff check --output-format=json --stdin-filename demo.py -
```

В PowerShell: `'import os' | ruff check --output-format=json --stdin-filename demo.py -`.

Посмотрите структуру JSON: именно её на практике 2 будет разбирать Tool `run_linter`, и именно из неё агенту придётся понять, что чинить.

`docs/lint-report.json` не коммитится: он уже в `.gitignore` помощника («Подготовка», п. 0). Это снимок вашей машины: в поле `filename` лежат абсолютные пути вида `C:\Users\<вы>\…`. На воркшопе 2 он нужен вам локально, а на практике 2 такой же JSON будет получать сам Tool.

**5. Спецификации двух инструментов для работы с кодом (25–35 мин). Срок — до начала воркшопа 2.**
По форме воркшопа 1 (имя, назначение для LLM, параметры с допустимыми значениями, формат возврата, краевые случаи) спроектируйте:

- инструмент поиска по кодовой базе — что принимает и что возвращает, чтобы результат влезал в контекст модели;
- инструмент чтения файла — как ограничить его так, чтобы агент не мог прочитать `.env` или что-либо за пределами репозитория бэкенда (`AI_REPO_ROOT`).

Оба инструмента работают по коду бэкенда, а живут в помощнике. Запишите в `docs/tools-spec-cycle2.md` репозитория помощника. Ограничения доступа продумайте письменно: на воркшопе 2 вы будете защищать именно их.

Файл живёт в отдельной ветке `feature/code-tools` репозитория помощника, от `main`, — в неё же после воркшопа 2 уйдёт версия v2. Создайте ветку **до** того, как запишете файл, в корне помощника:

```bash
git switch main
git pull
git switch -c feature/code-tools
```

PR практики к этому моменту обычно ещё не влит, поэтому в новой ветке нет ни `ai/`, ни `docs/`. Это нормально: спецификация от кода не зависит. Создайте каталог: `mkdir -p docs` (Git Bash) или `New-Item -ItemType Directory -Force docs` (PowerShell).

Когда файл готов (вместе с абзацем из пункта 6):

```bash
git add docs/tools-spec-cycle2.md
git commit -m "docs: add tools spec for cycle 2"
git push -u origin feature/code-tools
```

Ссылку на файл в этой ветке отправьте в общий чат курса до начала воркшопа 2.
