# Практика 1. Первый Tool и переключаемая конфигурация LLM

**Длительность:** 180 минут (2 пары)
**Формат:** самостоятельная командная работа по этому руководству. Pair Programming в командах 3–4 человека, в конце — peer review с соседней командой.
**Роль преподавателя:** организационная. Он следит за временем, объявляет стоп-точки, фиксирует прогресс команд и назначает пары для peer review. Всё содержание занятия — в этом файле и по ссылкам из него.

> ⚠️ Руководство рассчитано на то, что вы дойдёте до конца сами. Если шаг не получается — сначала читайте блок «Если не получилось» у этого шага, потом таблицу Troubleshooting в конце файла, потом документацию по ссылке.

**Проверено на:** Python 3.11, `crewai==1.15.22`, `pydantic-settings==2.15.0`, Ollama с моделью `qwen3:4b-instruct` — сентябрь 2026. Если читаете заметно позже, сверьте с документацией CrewAI способ объявления Tool (`from crewai.tools import tool`) и параметры класса `LLM`: между мажорными версиями они менялись.

## Что вы сделаете сегодня

В конце занятия в вашем репозитории будет:

1. Ветка `feature/agent-tool-1` и Pull Request в `main` с комментариями peer review от соседней команды.
2. `ai/config.py` — конфигурация AI-слоя на `pydantic-settings`, читающая `.env`.
3. `ai/llm_factory.py` — одна функция `get_llm()`, возвращающая LLM для локальной Ollama или для любого облачного провайдера с OpenAI-совместимым API. Переключение — правкой `.env`, без изменения кода.
4. `ai/tools/<ваш_инструмент>.py` — рабочий Tool по спецификации, которую ваша команда защитила на воркшопе 1: с валидацией входа и безопасным возвратом ошибки.
5. `ai/run_agent.py` и сохранённые логи в `ai/traces/`, в которых видно, что агент **вызвал ваш Tool**, а не придумал ответ.
6. `docs/adr-001-agent-tool-design.md` — ADR с обоснованием принятых решений.

## Подготовка ДО занятия

**Путь А (основной, локально и бесплатно).** Делается дома: модель весит 4,7 ГБ, на паре её скачать не получится.

1. Установить Ollama: [ollama.com/download](https://ollama.com/download), 10 минут.
2. Скачать модель: `ollama pull qwen3:4b-instruct` (2,5 ГБ — [карточка модели](https://ollama.com/library/qwen3)). Нужно около 3 ГБ свободной оперативной памяти сверх занятой системой. Если машина мощная и хочется модель крупнее — `qwen2.5:7b` (4,7 ГБ, контекст 32K).
3. Проверить, что модель отвечает: `ollama run qwen3:4b-instruct "скажи привет"`.
4. ⚠️ **Проверить, что модель умеет вызывать инструменты.** Это главное требование сегодняшнего занятия, и ему удовлетворяет не каждая модель: у модели в Ollama должна быть возможность **tools** (на карточке модели она указана рядом с размерами). У `qwen2.5-coder` её нет — Ollama просто откажется принимать запрос с инструментами. Проверка (на Windows — в Git Bash):

```bash
curl -s http://localhost:11434/api/chat -d '{
  "model": "qwen3:4b-instruct",
  "stream": false,
  "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
  "tools": [{"type": "function", "function": {
    "name": "get_tasks", "description": "Возвращает задачи по приоритету",
    "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
    "required": ["priority"]}}}]}'
```

   Ожидаемый ответ — JSON, в котором есть `"tool_calls"` с именем `get_tasks`. Если вместо этого пришло `{"error":"... does not support tools"}` — модель для занятия не годится, берите другую с возможностью tools. Если пришёл обычный текстовый ответ без `tool_calls` — модель инструменты принимает, но в этом запросе решила не вызывать; для занятия это допустимо, вернёмся к этому в шаге 3.2.

**Путь Б (запасной на занятии и обязательный для домашнего задания).** Нужен ключ любого облачного сервиса с **OpenAI-совместимым API**, у которого модель умеет вызывать функции. Какой именно сервис — курсу всё равно: смысл задания в том, что провайдер меняется правкой `.env`, а не кода. Ключ нужен **минимум одному человеку в команде**; если путь А не завёлся ни у кого — каждому. Три рабочих варианта:

| Провайдер | Что нужно для регистрации | `CLOUD_BASE_URL` | `CLOUD_MODEL` | `CLOUD_PROJECT` |
|---|---|---|---|---|
| **OpenRouter** — самый простой | почта или вход через Google/GitHub, карта не нужна | `https://openrouter.ai/api/v1` | бесплатная модель **с поддержкой tools** со страницы моделей | пусто |
| **Yandex AI Studio** — российский, оплата рублями | аккаунт Yandex Cloud с платёжным аккаунтом, каталог, сервисный аккаунт и API-ключ | `https://ai.api.cloud.yandex.net/v1` | `gpt://<идентификатор_каталога>/yandexgpt-5.1` | идентификатор каталога |
| Свой или университетский эндпоинт (vLLM, LM Studio, корпоративный шлюз) | как договоритесь с владельцем | адрес шлюза | имя модели на шлюзе | пусто |

1. **Заведите ключ.**
   *OpenRouter:* зарегистрируйтесь на [openrouter.ai](https://openrouter.ai/docs/quickstart), создайте ключ в разделе Keys. На [странице моделей](https://openrouter.ai/models) включите фильтры бесплатных моделей и поддержки tools — бесплатных моделей много, но функции умеют не все. Бесплатные модели работают без покупки кредитов, действующие лимиты — 50 запросов в сутки и 20 в минуту ([Limits](https://openrouter.ai/docs/api-reference/limits)). Список меняется, поэтому имя модели берите со страницы в день работы.
   *Yandex AI Studio:* нужен аккаунт Yandex Cloud с платёжным аккаунтом. Создайте каталог, в нём сервисный аккаунт с правом на вызов моделей, затем [API-ключ](https://yandex.cloud/ru/docs/iam/operations/authentication/manage-api-keys) с областью действия для языковых моделей. Идентификатор каталога (`b1g...`) — это `CLOUD_PROJECT`, без него запрос не уйдёт. Вызов функций в OpenAI-совместимом режиме поддерживается ([документация](https://aistudio.yandex.ru/docs/ru/ai-studio/operations/generation/completions-function.html)), список моделей — на [странице моделей](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models). Тарификация по токенам, на учебные запросы уходят копейки, но платёжный аккаунт нужен.

2. **Ключ показывается один раз** — сохраните сразу.

3. **Проверьте ключ, адрес и модель дома, а не на паре** — той же проверкой на вызов функции, что и для локальной модели. Подставьте свои значения (на Windows выполняйте в Git Bash — он ставится вместе с Git):

```bash
curl -s <ВАШ_CLOUD_BASE_URL>/chat/completions \
  -H "Authorization: Bearer <ВАШ_КЛЮЧ>" -H "Content-Type: application/json" \
  -d '{"model": "<ВАША_МОДЕЛЬ>",
       "messages": [{"role": "user", "content": "Какие задачи с приоритетом high?"}],
       "tools": [{"type": "function", "function": {
         "name": "get_tasks", "description": "Возвращает задачи по приоритету",
         "parameters": {"type": "object", "properties": {"priority": {"type": "string"}},
         "required": ["priority"]}}}]}'
```

   Ожидаемый ответ — JSON, в котором в `choices[0].message` есть `tool_calls` с именем `get_tasks`. Запишите работающую четвёрку «адрес — модель — ключ — каталог (если он нужен)»: на занятии она пойдёт в `.env`.
   Ответ пришёл, но `tool_calls` в нём нет, а есть обычный текст — модель инструменты приняла, но вызывать не стала: для занятия допустимо, вернёмся к этому в шаге 3.2.
   Ошибка вида `No endpoints found that support tool use` или `tools is not supported` — модель не умеет функции, берите другую.
   `model not found` — имя модели неверное или больше не обслуживается.
   `401` / `Unauthorized` — ключ скопирован с пробелом, отозван или не от этого адреса.

### Шаг 1.2: Зависимости AI-слоя (5 мин + установка идёт фоном)

**Зачем это нужно.** Версии фиксируем явно: CrewAI меняет API между мажорными версиями, и «у меня работало» без пина превращается в сломанный CI у всей команды.

**Что сделать**

1. Активируйте виртуальное окружение проекта (то же, что и в курсе «Конфигурирование»).
2. Создайте в корне репозитория `requirements-ai.txt`:

```
crewai==1.15.22
pydantic-settings==2.15.0
```

3. Запустите установку: `pip install -r requirements-ai.txt`.
4. **Не ждите её.** Это 134 пакета, и на общем канале аудитории установка идёт от 5 до 15 минут. Пока она работает, переходите к шагу 1.3 в соседнем окне терминала — вернётесь за результатом.
5. Когда установка закончится, проверьте:

```bash
python -c "import crewai, pydantic_settings; print(crewai.__version__)"
```

**Как понять, что получилось.** Напечатано `1.15.22`, traceback нет.

**Если не получилось**

- `Could not find a version that satisfies the requirement crewai` — Python вне диапазона 3.10–3.13. Проверьте `python --version` и активированное окружение.
- Установка оборвалась по таймауту — повторите ту же команду: скачанное уже в кеше pip, второй заход быстрее.
- `ModuleNotFoundError` при проверке — `pip` поставил пакеты в другое окружение. Сверьте `python -m pip --version` и путь к интерпретатору.

**Документация.** [CrewAI: Installation](https://docs.crewai.com/en/installation) — раздел про поддерживаемые версии Python, 3 минуты. Команды `uv` оттуда сегодня не нужны, ставьте через `pip`.

### Шаг 1.3: Каталоги и контракт вашего Tool (10 мин)

**Зачем это нужно.** Контракт, записанный в одном месте, не даёт Driver и Navigator реализовывать разное. Каталоги создаём сейчас, чтобы позже команды записи логов и коммита не падали на отсутствующем пути.

**Что сделать**

1. Создайте структуру. Linux / macOS / Git Bash:

```bash
mkdir -p ai/tools ai/traces docs
touch ai/__init__.py ai/tools/__init__.py ai/traces/.gitkeep docs/.gitkeep
```

   PowerShell:

```powershell
New-Item -ItemType Directory -Force ai\tools, ai\traces, docs
New-Item -ItemType File -Force ai\__init__.py, ai\tools\__init__.py, ai\traces\.gitkeep, docs\.gitkeep
```

   Пустые файлы `.gitkeep` нужны потому, что git не хранит пустые каталоги: без них на второй машине команды не окажется `ai/traces/` и `docs/`, и запись логов в блоке 3 упадёт.

2. Создайте `ai/tools/<имя_вашего_инструмента>.py` и запишите в начало контракт с воркшопа 1:

```python
# Контракт Tool (воркшоп 1)
# Имя:        ...
# Назначение: одно предложение, которое прочитает LLM
# Вход:       имя: тип — обязателен/нет, допустимые значения
# Выход:      JSON-строка; поля при успехе / поля при ошибке
# Краевые случаи: что считаем ошибкой и какой текст возвращаем
```

3. Проверьте контракт по трём вопросам:
   - Все ли параметры имеют тип и явный список допустимых значений? «Строка» недостаточно, нужно «одно из `high`, `medium`, `low`».
   - Можно ли по одному предложению назначения понять, **когда** этот Tool вызывать, а когда нет? Это описание читает не человек, а модель.
   - Что возвращается, если данных нет? Пустой список — это успех, а не ошибка; так и запишите.

4. **Если команда будет работать двумя парами** (см. шаг 1.4) — Driver сразу публикует каркас, чтобы вторая машина могла встать на ту же ветку:

```bash
git add ai/ docs/ requirements-ai.txt
git commit -m "chore(ai): scaffold ai layer"
git push -u origin feature/agent-tool-1
```

   Вторая пара на своей машине — в репозитории проекта, с активированным окружением. Шаг 1.1 на ней **не** выполняется, и свой `requirements-ai.txt` там не создаётся:

```bash
git fetch
git switch feature/agent-tool-1
pip install -r requirements-ai.txt
```

   Проверка: `git switch` печатает `branch 'feature/agent-tool-1' set up to track 'origin/feature/agent-tool-1'`. Установка идёт фоном, как в шаге 1.2. Модель второй машине не нужна: Tool проверяется без LLM.

**Как понять, что получилось.** `ls ai` показывает `tools`, `traces`, `__init__.py`; любой участник команды по одному комментарию называет сигнатуру функции и формат ответа, не задавая вопросов.

### Шаг 1.4: Роли Pair Programming (2 мин)

**Зачем это нужно.** Двое за одним экраном ловят ошибки, которые один не видит, — но только если роли разделены.

**Правила на сегодня**

- **Driver** — держит клавиатуру, пишет код, вслух проговаривает, что делает.
- **Navigator** — код не пишет. Держит открытой документацию, сверяет реализацию с контрактом из шага 1.3, задаёт вопросы «а что будет, если сюда придёт пустая строка».
- Роли меняются **по стоп-точке**.
- Команда из 3–4 человек может разделиться на две пары: одна пишет конфигурацию (шаги 2.1–2.3), другая — Tool (шаг 2.4). ## Блок 2. Конфигурация и Tool (00:30–01:40)

### Шаг 2.1: `ai/config.py` (12 мин)

**Зачем это нужно.** Провайдер модели, имя модели и API-ключ не должны лежать в коде: через месяц те же агенты поедут в CI, где Ollama нет.

**Что сделать.** Создайте `ai/config.py`:

```python
from typing import Literal

from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class AISettings(BaseSettings):
    """Конфигурация AI-слоя. Значения берутся из .env или переменных окружения."""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",  # в .env лежат ещё и переменные FastAPI/Postgres
    )

    llm_provider: Literal["ollama", "cloud"] = "ollama"

    ollama_model: str = "qwen3:4b-instruct"
    ollama_base_url: str = "http://localhost:11434"

    # cloud — любой провайдер с OpenAI-совместимым API
    cloud_model: str = ""
    cloud_base_url: str = "https://openrouter.ai/api/v1"
    cloud_api_key: SecretStr | None = None
    cloud_project: str = ""  # нужен только там, где провайдер требует каталог/проект

    llm_temperature: float = 0.1


settings = AISettings()
```

Три места, где обычно теряют час:

- `extra="ignore"` обязателен. По умолчанию `pydantic-settings` работает в режиме `extra="forbid"`, и общий `.env` вашего проекта (там уже есть `DATABASE_URL` и прочее из параллельного курса) уронит конфиг с ошибкой `Extra inputs are not permitted`.
- `Literal[...]` — опечатка `LLM_PROVIDER=olama` в `.env` упадёт сразу при старте с понятным текстом, а не через десять минут внутри агента.
- `SecretStr` вместо `str` для ключа. Обычная строка печатается в `repr` целиком — и уезжает в скриншот, в лог, в описание PR. `SecretStr` показывает звёздочки, а настоящее значение отдаёт только по явному `.get_secret_value()`.

**Как понять, что получилось**

```bash
python -c "from ai.config import settings; print(settings)"
```

Вывод: `llm_provider='ollama' ollama_model='qwen3:4b-instruct' ... cloud_api_key=None llm_temperature=0.1`. Ключа в `.env` ещё нет, поэтому `None` — это правильно; после шага 2.2 с пустым `CLOUD_API_KEY=` здесь будет `SecretStr('')`, а когда впишете ключ — `SecretStr('**********')`. Если вместо звёздочек покажется сам ключ, значит остался тип `str`.

**Если не получилось.** `ModuleNotFoundError: No module named 'ai'` — запускайте из корня репозитория и проверьте `ai/__init__.py`. Остальные ошибки этого шага (`Extra inputs are not permitted`, `Input should be 'ollama' or 'cloud'`) разобраны в таблице Troubleshooting.

**Документация.** [pydantic-settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/) — разделы «Dotenv (.env) support» и абзац про `extra`, 10 минут. Остальное сейчас не нужно.

**Зачем это нужно.** `.env` с ключом в истории Git — это утечка, которую нельзя отменить `git revert`. А `.env.example` — единственный способ для нового человека узнать, какие переменные нужны.

### Шаг 2.3: `ai/llm_factory.py` и smoke-тест (25 мин)

**Зачем это нужно.** Это единственная точка в проекте, которая знает, какая модель используется. Всё остальное просит `get_llm()` — благодаря этому в цикле 6 вы подмените LLM моком в тестах, не трогая агентов.

**Что сделать.** Создайте `ai/llm_factory.py`:

```python
from crewai import LLM

from ai.config import settings


def get_llm() -> LLM:
    """Возвращает LLM согласно .env. Единственная точка переключения провайдера."""
    if settings.llm_provider == "ollama":
        return LLM(
            model=f"ollama/{settings.ollama_model}",
            base_url=settings.ollama_base_url,
            temperature=settings.llm_temperature,
        )

    if not settings.cloud_api_key or not settings.cloud_model:
        raise RuntimeError(
            "LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст. Проверьте .env"
        )

    return LLM(
        model=f"openai/{settings.cloud_model}",
        base_url=settings.cloud_base_url,
        api_key=settings.cloud_api_key.get_secret_value(),
        project=settings.cloud_project or None,  # нужен, например, Yandex AI Studio
        temperature=settings.llm_temperature,
    )
```

Что здесь важно и не очевидно:

- Префикс в `model` (`ollama/`, `openai/`) — это то, как CrewAI выбирает провайдера. Без префикса он угадывает по имени модели и почти наверняка уйдёт в настоящий OpenAI.
- Префикс `openai/` вместе с явным `base_url` означает «говори по протоколу OpenAI вот с этим адресом». Так работает любой OpenAI-совместимый сервис: OpenRouter, Yandex AI Studio, ваш собственный vLLM. Именно поэтому смена провайдера — это правка `.env`, а не кода. У CrewAI есть и специальные префиксы (`openrouter/` и другие), которые сами подставляют адрес, но тогда адрес возвращается в код — а нам нужно обратное.
- Модель у некоторых провайдеров содержит слеши и двоеточия (`qwen/qwen3-coder:free`, `gpt://b1g…/yandexgpt-5.1`) — это нормально: всё, что после первого префикса `openai/`, уезжает провайдеру как есть.
- `project` передаётся, только если он заполнен. Yandex AI Studio без идентификатора каталога запрос не примет, OpenRouter про этот параметр ничего не знает — поэтому `or None`.
- Проверка ключа стоит **до** создания `LLM`: ваше сообщение понятнее, чем то, что выдаст библиотека.
- `temperature=0.1` — для агента, который вызывает инструменты, творчество вредно.

**Smoke-тест**

```bash
python -c "from ai.llm_factory import get_llm; print(get_llm().call('Ответь одним словом: работает?'))"
```

**Как понять, что получилось.** В консоли короткий ответ модели. На пути А первый запуск занимает 10–40 секунд: модель загружается в память.

**Проверка переключения.** Если у вашей команды есть облачный ключ — поменяйте в `.env` `LLM_PROVIDER=cloud`, впишите свою четвёрку «адрес — модель — ключ — каталог» и запустите ту же команду ещё раз. Ответ должен прийти снова, **без единой правки в коде**; затем верните `LLM_PROVIDER=ollama`.
Если ключа нет — проверьте переключение наполовину: поставьте `LLM_PROVIDER=cloud` с пустым `CLOUD_API_KEY` и убедитесь, что `get_llm()` падает с **вашим** сообщением `LLM_PROVIDER=cloud, но CLOUD_MODEL или CLOUD_API_KEY пуст`, а не с ошибкой из недр библиотеки. Это подтверждает, что ветка провайдера выбирается конфигом. Полное переключение доделаете дома — оно входит в домашнее задание.

**Если не получилось**

- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=ollama` — сообщение обманчивое, речь не про OpenAI: не поднят сервер Ollama. Запустите `ollama serve` и повторите.
- `AuthenticationError: Error code: 401` — ключ неверный, отозван или не от этого адреса. Сверьте `CLOUD_API_KEY` и `CLOUD_BASE_URL`: ключ OpenRouter к адресу Yandex AI Studio не подойдёт.
- `NotFoundError` / `model not found` — имя модели неверное или больше не обслуживается. Возьмите актуальное со страницы моделей своего провайдера и впишите в `CLOUD_MODEL`.
- `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=cloud` — адрес недоступен: опечатка в `CLOUD_BASE_URL` или сеть не выпускает запрос наружу.

**Документация.** [CrewAI: LLMs](https://docs.crewai.com/en/concepts/llms) — разделы «Ollama» и «Custom OpenAI-Compatible Endpoints», 10 минут.

### Шаг 2.4: Ваш Tool (25 мин)

**Зачем это нужно.** Tool — это граница между вероятностной моделью и вашей детерминированной системой. Всё, что модель может испортить, должно останавливаться здесь и возвращаться агенту текстом, который он способен прочитать и исправить.

**Что сделать.** В файле `ai/tools/<имя>.py`, где лежит контракт, напишите Tool. Ниже каркас; содержательная часть у каждой команды своя.

```python
import json

from crewai.tools import tool


def _fail(message: str) -> str:
    """Единый формат ошибки, который вернётся агенту."""
    return json.dumps({"status": "error", "message": message}, ensure_ascii=False)


@tool("имя_из_вашего_контракта")
def your_tool_name(param: str, limit: int = 10) -> str:
    """Одно предложение: что делает инструмент и когда его вызывать.

    Args:
        param: что это и какие значения допустимы (перечислите их явно).
        limit: что ограничивает, диапазон и значение по умолчанию.

    Returns:
        JSON-строка. При успехе: {"status": "ok", ...}.
        При ошибке: {"status": "error", "message": "<что не так и что делать>"}.
    """
    # 1. Валидация входа: каждое условие из контракта — отдельная проверка с _fail()

    # 2. Полезная работа — внутри try/except

    # 3. Успешный ответ: json.dumps({...}, ensure_ascii=False)
```

Пять требований, по которым это будут проверять на peer review:

1. **Docstring обязателен.** Это не стиль, которому договорились придерживаться в команде, а обязательная механика: `@tool` берёт описание для модели именно из docstring, а функция без него падает с `ValueError: Function must have a docstring` ещё на импорте. Пишите его для LLM: явно перечисляйте допустимые значения.
2. **Имя, которое видит модель, — это аргумент декоратора**, а не имя функции. `@tool("get_ticket_status")` над `def your_tool_name(...)` даст модели инструмент `get_ticket_status`. Имя функции модель не видит вообще.
3. **Аннотации типов у всех параметров.** По ним CrewAI строит схему аргументов, которую видит модель.
4. **Безопасный возврат.** Из Tool не должно вылетать необработанное исключение. Любая ошибка — `return _fail("...")` с текстом, из которого понятно, **что именно** исправить: «priority должен быть 'high', 'medium' или 'low', получено 'urgent'» вместо «invalid input».
5. **Одна строка на выходе.** Всегда `str` (JSON внутри строки), всегда одинаковая структура — и при успехе, и при ошибке.

*Пример одной команды (хелпдеск) для иллюстрации формы:*

```python
@tool("get_ticket_status")
def get_ticket_status(ticket_id: str) -> str:
    """Возвращает текущий статус тикета поддержки по его идентификатору.

    Args:
        ticket_id: идентификатор вида 'HD-123'. Префикс 'HD-' обязателен.

    Returns:
        JSON-строка: {"status": "ok", "ticket_id": ..., "state": ...}
        или {"status": "error", "message": ...}.
    """
    if not ticket_id.startswith("HD-"):
        return _fail(f"ticket_id должен начинаться с 'HD-', получено '{ticket_id}'")
    try:
        ...  # обращение к хранилищу; в цикле 5 здесь будет вызов вашего FastAPI
    except Exception as exc:  # noqa: BLE001 — граница системы, наружу ничего не летит
        return _fail(f"не удалось получить тикет: {exc}")
```

**Как понять, что получилось.** Проверьте Tool напрямую, без агента, — LLM для этого не нужна. Создайте `ai/tools/_check.py` и поправьте две строки под себя:

```python

print("name:", <имя_функции>.name)
print("ok  :", <имя_функции>.run(<корректные аргументы>))
print("err :", <имя_функции>.run(<заведомо неверные аргументы>))
```

Запуск: `python -m ai.tools._check`. Файл остаётся в репозитории и уезжает в PR — так и задумано: ревьюеры соседней команды запустят его сами.

Ожидаемый вывод: имя инструмента из аргумента декоратора, затем строка со `"status": "ok"`, затем строка со `"status": "error"` и понятным сообщением. Ни одного traceback.

**Если не получилось**

- `ValueError: Function must have a docstring` — у функции под `@tool` нет docstring.
- Traceback вместо строки с ошибкой — остался непокрытый путь. Оберните тело в `try/except Exception` и возвращайте `_fail()`.
- `ImportError` — проверьте `ai/__init__.py` и `ai/tools/__init__.py` из шага 1.3.

**Если ваша команда работала двумя парами — сведите код перед блоком 3.** Пара с конфигурацией коммитит и пушит первой:

## Блок 3. Агент и проверка на прочность (01:40–02:20)

### Шаг 3.1: `ai/run_agent.py` (15 мин)

**Зачем это нужно.** Сборка контура целиком: модель получает описание вашего Tool, решает вызвать его, получает результат и формулирует ответ.

**Что сделать.** Создайте `ai/run_agent.py`:

```python
from crewai import Agent, Crew, Task

from ai.llm_factory import get_llm
from ai.tools.<модуль> import <имя_инструмента>

agent = Agent(
    role="<роль из вашей предметной области>",
    goal="<чего агент добивается — одно предложение>",
    backstory="<кто он и как себя ведёт: например, всегда проверяет данные перед действием>",
    tools=[<имя_инструмента>],
    llm=get_llm(),
    verbose=True,
    max_iter=5,  # страховка от бесконечного цикла; по умолчанию 20
)

task = Task(
    description="<запрос пользователя, для которого нужен ваш инструмент>",
    expected_output="<в каком виде вы хотите финальный ответ>",
    agent=agent,
)

crew = Crew(agents=[agent], tasks=[task], verbose=True)

if __name__ == "__main__":
    print(crew.kickoff())
```

### Шаг 3.2: Чтение трассы (10 мин)

**Зачем это нужно.** Отладка агента — это чтение его трассы: логика здесь не в вашем коде, а в последовательности решений модели.

**Что сделать.** Откройте `ai/traces/run-01.log` и ответьте письменно (это пойдёт в ADR):

1. Сколько раз вызывался Tool? Если больше одного — почему? Посмотрите `Args` каждого вызова.
2. Какие именно аргументы подставила модель? Совпадают ли они с тем, что описано в вашем docstring?
3. Финальный ответ основан на `Output` инструмента или содержит факты, которых в `Output` не было?

Концептуально это цикл ReAct: рассуждение → действие → наблюдение. CrewAI 1.15 печатает его как панели `Agent Started` → `Tool Execution Started/Completed` → `Agent Final Answer`; отдельных строк `Thought:` в выводе может не быть, и это не признак поломки.

**Если агент не вызвал Tool и придумал ответ** — проверьте по порядку:

1. Описание в docstring не объясняет, **когда** вызывать инструмент. «Работает с задачами» модель не поймёт; «возвращает задачи с указанным приоритетом; используй, когда спрашивают о задачах по приоритету» — поймёт.
2. `Task.description` сформулирован так, что на него можно ответить без данных. Сделайте запрос конкретным: он должен требовать значения, которого у модели нет.
3. Локальная 4b слабее в function calling, чем облачная. Сначала убедитесь, что модель вообще принимает инструменты (проверка 6 из «Проверки окружения»), потом попробуйте `qwen2.5:7b`, а если в команде есть ключ — прогоните тот же сценарий по пути Б. Если там Tool вызывается, дело в размере модели, и это честный вывод для ADR.

**Документация.** [Prompt Engineering Guide: ReAct](https://www.promptingguide.ai/techniques/react) — первые два раздела, 10 минут.

### Шаг 3.3: Провокация ошибок (15 мин)

**Зачем это нужно.** Агент, который работает только на правильных данных, бесполезен. Паттерн «безопасный возврат» проверяется ровно одним способом: сломать вход специально.

**Что сделать.** Сценарий 1 обязателен, логи двух остальных доберёте дома, если не успеете на паре. Меняйте только `Task.description`, логи сохраняйте как `run-02.log`, `run-03.log`, `run-04.log`.

1. **Недопустимое значение** (обязательно). Попросите то, чего в допустимых значениях нет («задачи с приоритетом `super-high`»).
2. **Пустой или отсутствующий вход.** Запрос без обязательного параметра.
3. **Несуществующая сущность.** Идентификатор правильного формата, которого нет в данных.

**Как понять, что получилось.** В логе есть панель `Tool Execution Completed` с вашим `{"status": "error", ...}`, процесс **не падает**, и финальный ответ агента осмысленный: либо повторный вызов с исправленными аргументами, либо вежливое сообщение пользователю. Traceback в консоли — это провал сценария.

Так выглядит успешная самокоррекция в реальном логе: первый вызов с неверным аргументом, ошибка от Tool, второй вызов с исправленным.

```
│  Tool: get_tasks_by_priority
│  Args: {'priority': 'urgent'}
│  Output: {"status": "error", "message": "priority должен быть 'high', 'medium' или 'low'"}
...
│  Tool: get_tasks_by_priority
│  Args: {'priority': 'high'}
│  Output: {"status": "ok", "count": 0, "items": []}
```

**Если не получилось**

- Упал traceback — где-то в Tool осталось необработанное исключение. Вернитесь к шагу 2.4, требование 4.
- Агент получил ошибку, но не исправился и сдался — текст `message` не подсказывает решение. Добавьте в него допустимые значения.
- Агент зациклился на одной ошибке до `max_iter` — противоречие между docstring и валидацией: вы принимаете не то, что обещаете. Сверьте оба места с контрактом из шага 1.3.

> **Закончили раньше?** Не начинайте блок 4 досрочно — peer review стартует у всех одновременно. Полезное на эти минуты, по убыванию ценности: (1) прогоните четвёртый сценарий — два вызова Tool подряд в одной задаче — и посмотрите по трассе, не теряет ли агент контекст между ними; (2) добавьте в Tool второй параметр из вашего контракта, который отложили; (3) напишите черновик разделов «Контекст» и «Рассмотренные варианты» будущего ADR: в блоке 4 на него отведено десять минут, и это мало.

## Troubleshooting

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| `Failed to connect to OpenAI API: Connection error.` при `LLM_PROVIDER=ollama` | Сервер Ollama не запущен (упоминание OpenAI обманчиво: CrewAI ходит в Ollama по OpenAI-совместимому протоколу) | `ollama serve` в отдельном окне; проверить `curl http://localhost:11434/api/tags` |
| `address already in use` при `ollama serve` | Ollama уже запущен фоном (приложение в трее) | Ничего не делать, сервер работает; проверить `curl` к 11434 |
| Порт 11434 занят другим приложением | Конфликт портов | Запустить Ollama на другом порту (`OLLAMA_HOST=127.0.0.1:11500 ollama serve`) и указать тот же адрес в `OLLAMA_BASE_URL` |
| `... does not support tools` (HTTP 400) при запуске агента | У модели в Ollama нет возможности tools. `qwen2.5-coder` любого размера сюда не годится: он умеет писать код, но не вызывать функции | Взять модель с возможностью tools: `qwen3:4b-instruct` (2,5 ГБ) или `qwen2.5:7b` (4,7 ГБ), поправить `OLLAMA_MODEL` в `.env` |
| `model '...' not found` | Модель не скачана в этом профиле пользователя | `ollama pull qwen3:4b-instruct` либо путь Б |
| Ответ модели идёт минутами, машина уходит в своп | Не хватает RAM (4b нужно ~3 ГБ свободных, 7b — ~5 ГБ) | Закрыть тяжёлые приложения; взять `qwen3:1.7b`; путь Б |
| `AuthenticationError: Error code: 401` при `LLM_PROVIDER=cloud` | Ключ неверный, отозван или не от этого адреса (ключ одного провайдера к адресу другого) | Сверить `CLOUD_API_KEY` и `CLOUD_BASE_URL`, проверить пробелы и кавычки в `.env` |
| `NotFoundError` / `model not found` при `LLM_PROVIDER=cloud` | Имя модели неверное или больше не обслуживается (у бесплатных моделей список меняется) | Взять актуальное имя со страницы моделей провайдера и вписать в `CLOUD_MODEL` |
| `No endpoints found that support tool use` / `tools is not supported` | Облачная модель не умеет вызывать функции — та же беда, что и с локальной моделью без tools | Взять модель с поддержкой функций (на OpenRouter это фильтр на странице моделей) |
| Yandex AI Studio отвечает 400 или «folder not specified» | Не заполнен `CLOUD_PROJECT` — идентификатор каталога | Вписать `b1g…` в `CLOUD_PROJECT`; он же должен быть внутри `gpt://<каталог>/…` в `CLOUD_MODEL` |
| `429` / `rate limit` у бесплатной модели | Исчерпан дневной или минутный лимит бесплатного тарифа | Подождать минуту; если кончился дневной лимит — работать по пути А, а облачную проверку доделать дома |
| Облачный провайдер не отвечает, таймаут соединения | Сеть аудитории не выпускает запросы на его адрес | Проверить `curl` из «Проверки окружения»; перейти на путь А или на мобильный интернет |
| `ValidationError: Extra inputs are not permitted` при импорте конфига | В общем `.env` есть переменные, которых нет в `AISettings`, а режим по умолчанию — `extra="forbid"` | Добавить `extra="ignore"` в `SettingsConfigDict` |
| `ValidationError: Input should be 'ollama' or 'cloud'` | Опечатка в `LLM_PROVIDER` | Исправить значение в `.env`; конфиг отработал правильно |
| `ValueError: Function must have a docstring` | У функции под `@tool` нет docstring | Написать docstring: он же является описанием инструмента для модели |
| Агент не вызывает Tool, выдумывает ответ | Описание не объясняет, когда вызывать; задача решается без данных; модель слишком мала | См. шаг 3.2 |

| `ModuleNotFoundError: No module named 'ai'` | Запуск не из корня, нет `__init__.py` или не сведён код двух пар | Запускать `python -m ai.run_agent` из корня; проверить `ai/__init__.py`; см. сведение кода в конце шага 2.4 |

| Кракозябры вместо кириллицы в выводе (Windows) | Кодировка консоли | `chcp 65001` перед запуском либо переменная `PYTHONUTF8=1` |

## Домашнее задание (СРС, 2–3 часа)

Ведёт в цикл 2 — «Инструменты агентов»: function calling и инструменты для работы с кодом (`search_codebase`, `read_file`, `run_linter`, безопасное выполнение кода).

**1. Доработка и хвосты с пары (40–60 мин).**
Закройте замечания peer review и доделайте всё, что не успели: `run_agent.py`, логи, ADR. На каждое замечание — ответ в ветке комментария: исправлено или почему решили иначе. PR должен быть готов к слиянию.

**2. Полное переключение провайдера (20–30 мин).**
Если на паре вы проверили переключение только наполовину — доведите до конца: `LLM_PROVIDER=cloud`, своя четвёрка «адрес — модель — ключ — каталог» в `.env`, тот же smoke-тест и тот же `run_agent.py` без единой правки кода. Сохраните лог как `ai/traces/run-cloud.log` и допишите в ADR, чем отличалось поведение локальной модели и облачной. Если успели на паре — прогоните оставшиеся сценарии из шага 3.3.

**3. Function calling — механика (30 мин).**
[Prompt Engineering Guide: Function Calling](https://www.promptingguide.ai/applications/function_calling). Читайте с одним вопросом: что именно модель получает на вход, когда «видит» ваш инструмент, и в каком виде сообщает о желании его вызвать.

**4. Разведка своего репозитория (15 мин).**
Запустите линтер и сохраните машиночитаемый вывод:

```bash
ruff check --output-format=json > docs/lint-report.json
```

Если `ruff` в проекте не настроен — поставьте его в окружение и запустите как есть ([Ruff: The Linter](https://docs.astral.sh/ruff/linter/), 5 минут). Посмотрите структуру JSON: именно её на практике 2 будет разбирать Tool `run_linter`, и именно из неё агенту придётся понять, что чинить.

**5. Спецификации двух инструментов для работы с кодом (25–35 мин).**
По форме воркшопа 1 (имя, назначение для LLM, параметры с допустимыми значениями, формат возврата, краевые случаи) спроектируйте:

- инструмент поиска по кодовой базе — что принимает и что возвращает, чтобы результат влезал в контекст модели;
- инструмент чтения файла — как ограничить его так, чтобы агент не мог прочитать `.env` или что-либо за пределами репозитория.

Запишите в `docs/tools-spec-cycle2.md`. Ограничения доступа продумайте письменно: на воркшопе 2 вы будете защищать именно их.

**6. Один вопрос к обсуждению (10 мин).**
Сформулируйте письменно: какой инструмент в вашем проекте опаснее всего давать агенту и почему. Одного абзаца достаточно.
