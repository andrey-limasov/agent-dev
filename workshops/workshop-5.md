# Воркшоп 5: Что помощник знает об API и что он отдаёт людям — контракт результата

**Формат:** Нечётная неделя (неделя 9), 1 пара (2 академических часа = 90 минут)
**Тип:** Лекция-семинар в формате перевёрнутого класса (Flipped Classroom)
**Тема:** Помощник и внешний мир. Контракт API бэкенда (OpenAPI-схема FastAPI) как источник истины для агента вместо догадок модели. Вызовы REST API из агентов: таймауты, обработка ошибок сети, асинхронные задачи. Structured Output через Pydantic для гарантированного формата результата помощника. **Формат:** Анализ кейсов, проектирование Pydantic-контракта результата помощника (тест-кейсы, отчёт) и правил доступа к репозиторию бэкенда: чтение — да, изменения — только через Pull Request, который принимают люди.

**Термины темы в курсе:** контракт — договорённость о полях: их имена, типы, ограничения и что происходит при нарушении; контракт API — что бэкенд обещает клиенту, контракт результата — что помощник обещает людям и коду запуска; схема — OpenAPI-описание бэкенда, которое FastAPI отдаёт по адресу `/openapi.json`; Structured Output — итог агента разбирается в заданную Pydantic-модель, а не остаётся текстом; таймаут — сколько секунд клиент ждёт ответ, прежде чем считать запрос неудавшимся; асинхронная задача — сервер принимает работу, отвечает сразу (обычно 202), а результат клиент забирает позже отдельным запросом.

> **Важно:** на этом занятии **нет кодинга**. Мы сверяем схему с кодом, разбираем сбои по карточкам и проектируем контракт таблицей, без `class` и без Python. Код — на практике 5.

## Цели воркшопа

После занятия вы сможете:
1. **Разделять**, что об эндпоинте знает схема и что знает только код.
2. **Оценивать** сбой запроса: повторять ли его и что вернуть агенту.
3. **Объяснять**, что Structured Output проверяет и чего не проверяет.
4. **Проектировать** контракт результата помощника: поля, типы, ограничения, что при нарушении.
5. **Определять** правила доступа помощника к бэкенду и к работающему стенду.
6. **Проверять** чужой контракт на плохих ответах модели.

## Инженерная проблема

**Контекст:**
Разработчик вашей команды просит помощника: «Нужен тест к `GET /version`». После практики 4 Crew находит эндпоинт по коду, Кодер записывает файл через `write_generated`, проверяет его `run_linter`, а итог Crew — текст по `CODER_OUTPUT`: путь, текст теста, итог линтера, записка.

**Проблема:**
- Исследователь ищет эндпоинты поиском по коду. На практике 5 у него появится схема работающего бэкенда: `GET /openapi.json`. Но у бэкендов курса в схеме ответ `/version` выглядит как `"schema": {}`, полей `version` и `team` там нет. Что тогда берётся из схемы, а что по-прежнему из кода?
- Запрос к стенду может не удаться: стенд не поднят, отвечает слишком долго, отвечает 404 при живом приложении. Модель не должна принимать сбой за факт об API, а Crew не должна зависать.
- Итог Crew — текст. Код запуска не может проверить, что записанный файл существует и что эндпоинт настоящий. Человек получает «тест готов» и верит на слово.
- У помощника появляется новое право: сетевой запрос к работающему бэкенду. Правил для него пока нет.

**Вопросы для обсуждения:**
- Что из ответа модели можно проверить без человека и чем?
- Какой сбой стоит повторить, а какой повтор только потратит время?
- Что должно произойти с результатом, если модель заполнила поле неверно?

## Плохие ответы (этап 4)

**Порядок.** Файл `docs/result-contract.md` отправьте в чат курса в конце этапа 3 как есть и больше не правьте: на его строки ссылаются проверяющие, пустые ячейки они отметят «не определено». Кто чей файл проверяет, преподаватель выпишет на доске, круг тот же, что на защите воркшопа 4: файл команды N проверяет команда N+2, через одну (в круге из трёх файл команды 2 проверяет команда 1, файл команды 3 — команда 2). В круге из четырёх команд проверяет предыдущая: файл команды 1 — команда 4, команды 2 — команда 1, команды 3 — команда 2, команды 4 — команда 3. Защит нет: все команды работают одновременно.

| Минуты | Что делаете |
|---|---|
| 2 | Читаете чужой файл |
| 9 | По карточке проходите шесть ответов модели О1–О6 и три вопроса Д1–Д3, ставите вердикты в карту |
| 3 | Один участник идёт к авторам файла с вопросами по строкам, где поставили «не определено»; остальные остаются и отвечают на вопросы о вашем файле |
| 2 | Фотографируете бланк и отправляете карту авторам в чат; самый частый вердикт «пройдёт» — на доску |

**Вердикты.**
- По ответам модели О1–О6 вердикт берётся из столбца «Что при нарушении» в чужом файле: «отказ формата» — **отвергнет формат** (объект результата не будет создан), «отказ кода» — **отвергнет код** (объект создан, проверка кодом сообщит об отказе), «заметит человек» — **пройдёт** (никто, кроме человека, не заметит), об этом нарушении ничего — **не определено**. Если в ответе нет поля целиком, а столбец об этом молчит, решает фраза раздела 2 «Все поля обязательны»: она есть — **отвергнет формат**.
- По вопросам Д1–Д3: **есть**, **нет** или **не определено**. Смотрите только столбец «У нас»: столбец «Правило курса» заполнен у всех одинаково и не считается.

У каждого вердикта — раздел чужого файла и цитата из него в 3–5 слов или номер строки. «Не определено» считается как «нет»: о чём контракт молчит, то в коде сделают как попало.

## Домашнее задание к практике 5

1. **PR практики 4 — в `main` помощника.** Практика 5 начинается с ветки от `main`, где уже есть Crew, `write_generated` и `generated/conftest.py`. Посмотрите статус PR и выберите свой случай:
   - **PR нет** — откройте PR `feature/crew` → `main` и выберите случай ниже.
   - **Влит** — переходите к пункту 2.
   - **Не влит, влить можно** — влейте (одобряет участник, который не автор PR), затем пункт 2.
   - **Влить нельзя** — в описании PR напишите, что мешает. Пункты 2 и 3 выполните, но команды `git` не запускайте: файлы остаются в рабочей папке и не теряются при переключении веток, пока не закоммичены. Что делать дальше, скажет шаг 1.2 практики 5.
2. **Контракт — правки в рабочей папке (10 мин).** Закройте вердикты «пройдёт» и «не определено» из карты, которую вам прислали, если решите, что их надо закрыть; оставленные запишите в файл строкой «оставили: …, потому что …». Две проверки кодом на практике 5 обязательны: пара `method` и `path` есть в схеме и файл `test_file` существует на диске. Если у этих полей в столбце «Что при нарушении» другое, поправьте.
3. **Черновик ADR 005 помощника (15 мин).** Создайте `docs/adr/005-result-contract.md` по каркасу из [`materials-5.md`](materials-5.md), статус «Предложено». На практике 5 он станет «Принято» с замером.
4. **Коммит (2 мин).** Команды ниже выполняет **один** участник — тот, у кого итоговые файлы. Из корня репозитория помощника (одинаково в PowerShell и Git Bash):
   ```
   git switch main
   git pull
   git switch -c feature/api-contract
   git add docs/result-contract.md docs/adr/005-result-contract.md
   git commit -m "docs: add result contract and ADR 005 draft"
   git push -u origin feature/api-contract
   ```
   Ожидаемый вывод третьей команды: `Switched to a new branch 'feature/api-contract'`, последней — строка `* [new branch]      feature/api-contract -> feature/api-contract`. **Как проверить:** `git log --oneline -1` показывает коммит `docs: add result contract and ADR 005 draft`, а `git status` — `nothing to commit, working tree clean` или только файлы, которые вы не собирались коммитить. Файла схемы в выводе `git status` быть не должно: он лежит вне репозитория.

   **Остальные участники** — после его `push`:
   ```
   git fetch
   git switch feature/api-contract
   ```
   Ожидаемый вывод: `Switched to a new branch 'feature/api-contract'` и `branch 'feature/api-contract' set up to track 'origin/feature/api-contract'.`

   **Если не получилось:**
   - `git add` ответил `fatal: pathspec '...' did not match any files` — файл лежит не там или называется иначе, либо файл у другого участника: проверьте `git status`.
   - `git push` ответил `! [rejected]` и `Updates were rejected` — ветку уже запушил сокомандник. Скопируйте оба своих файла рядом с репозиторием (`cp docs/result-contract.md ../result-contract-mine.md` и `cp docs/adr/005-result-contract.md ../005-result-contract-mine.md`), удалите свою ветку и возьмите его: `git switch main`, `git branch -D feature/api-contract`, `git fetch`, `git switch feature/api-contract`. Перенесите свои правки вручную, затем `git add`, `git commit -m "docs: update result contract"`, `git push`.
   - `git switch feature/api-contract` ответил `error: The following untracked working tree files would be overwritten by checkout` — у вас своя незакоммиченная копия. Отложите все файлы из сообщения `git`: `mv docs/result-contract.md ../result-contract-untracked.md` и, если он там назван, `mv docs/adr/005-result-contract.md ../005-result-contract-untracked.md`. Повторите команду и перенесите правки вручную.
   - `git switch -c` ответил `fatal: a branch named 'feature/api-contract' already exists` — ветка у вас уже есть, блок не повторяйте: `git switch feature/api-contract`, затем `git add`, `git commit`, `git push -u origin feature/api-contract`.
5. **Стенд к практике 5.** На практике 5 Tool помощника читает схему с работающего стенда, поэтому стенд нужен на той машине, где запускается Crew, — там, где работает Ollama. Если на входном билете стенд не поднялся, билет вы не делали или стенд поднимали на другом ноутбуке, поднимите его на машине Crew. Проверка — шаги 1–4 билета в [`materials-5.md`](materials-5.md), выполненные на этой машине. Учебный бэкенд «Заметки» запускается по его `README.md` на машине Crew, подробности будут на практике 5.

   **Если не получилось:**
   - Ошибка Docker или Compose, которой нет в ветках билета, — раздел «Если не работает» практики 3 «Конфигурирования», подразделы «Сборка и запуск образа» и «Compose и база данных» ([`practice-3-guide.md`](https://github.com/andrey-limasov/app-conf/blob/main/practices/practice3/practice-3-guide.md#если-не-работает)): найдите строку со своей ошибкой, 5–10 минут.
   - Docker на машине Crew не работает или его нет ни у кого в команде — стенд не чините. До практики 5 напишите в чат курса строку «стенд: Docker не работает на машине Crew» или «стенд: Docker нет ни у кого». На практике 5 вы возьмёте готовую схему из [`materials-5.md`, раздел «Бэкенд недели 8»](materials-5.md#бэкенд-недели-8); как передать её помощнику и как запускать тесты, скажет практика 5.
6. **СРС до практики 5** — раздел «После воркшопа» в [`materials-5.md`](materials-5.md), около 45 минут.
