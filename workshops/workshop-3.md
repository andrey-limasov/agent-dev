# Воркшоп 3: Что агент помнит и что он знает — схема RAG для документации бэкенда

**Формат:** Нечётная неделя (неделя 5), 1 пара (2 академических часа = 90 минут)
**Тип:** Лекция-семинар в формате перевёрнутого класса (Flipped Classroom)
**Тема:** Управление памятью и контекстом. Краткосрочная vs долгосрочная память. Введение в RAG (Retrieval-Augmented Generation). Стратегии чанкинга и эмбеддинга технической документации.

**Термины темы в курсе:** краткосрочная память — контекст текущего запуска Crew (промпт, задача, ответы инструментов этого запуска); долгосрочная память — векторное хранилище документации (ChromaDB в репозитории помощника); чанк — кусок документа, который ищется и попадает в промпт целиком; эмбеддинг — вектор чисел, который модель эмбеддингов строит по тексту так, что близкие по смыслу тексты получают близкие векторы.

> **Важно:** на этом занятии **нет кодинга**. Мы раскладываем карточки, режем документы карандашом и проектируем схему RAG-пайплайна. Код — на практике 3.

---

## Цели воркшопа

После занятия вы сможете:
1. **Различать** краткосрочный контекст запуска агента и долгосрочное знание в векторном хранилище — и называть то, что не должно попасть никуда.
2. **Объяснять**, на какие вопросы к документации `search_codebase` (подстрока и `ast`) не отвечает и зачем нужен поиск по смыслу.
3. **Оценивать** стратегии чанкинга на одном корпусе по набору вопросов.
4. **Проектировать** RAG-пайплайн для документации своего бэкенда: корпус и deny-list, нарезка, метаданные, эмбеддинги, хранилище, Tool `search_docs`, обновление индекса, память.
5. **Проверять** чужую схему по контракту Доступ / Объём / Сбой из воркшопа 2.

## Инженерная проблема

**Контекст:**
Разработчик вашей команды спрашивает помощника: «Что вернёт сервис, если удалить заметку, которой нет, и почему у новой заметки бывает id удалённой?» У помощника есть `read_file` и `search_codebase` из практики 2: подстрока и определения `def`/`class` через `ast`.

**Проблема:**
- `search_codebase("404")` найдёт строку в `main.py`. Но «почему» записано в ADR, и там нет слова «id» — там «номер новой заметки». Поиск по подстроке этот абзац не найдёт.
- Можно прочитать всю документацию в контекст. Пока её 150 строк — работает. Через месяц в бэкенде появятся Dockerfile, compose, новые ADR, и каждый вопрос будет стоить всего корпуса в промпте — и всего корпуса, отправленного облачному провайдеру.
- Можно «запомнить» прошлые ответы агента. Но вчерашний ответ мог быть ошибкой, а завтра документация изменится.

**Вопросы для обсуждения:**
- Что агент должен знать между запусками, а что — забыть, как только запуск закончился?
- Если резать документацию на куски, где резать, чтобы ответ не развалился на два куска?
- Что будет, когда в бэкенде появится `.env` с паролем базы, а индексатор пройдёт по всему каталогу?

## Домашнее задание к практике 3

1. **PR практики 2 — в `main` помощника.** К воркшопу 3 он должен был быть готов к слиянию (домашнее задание практики 2). Влейте его до практики 3: она начинается с ветки от `main`, в котором уже есть `ai/tools/code_tools.py` и `crewai_tools()`.
2. **Схема — в своей ветке (10 мин).** Закройте вердикты «нет» и «не определено» из карты проверки, которую прислали соседи. Команды ниже выполняет **один** участник — тот, у кого итоговый файл. Из корня репозитория помощника (одинаково в PowerShell и Git Bash):
   ```
   git switch main
   git pull
   git switch -c feature/rag-search
   git add docs/rag-design.md
   git commit -m "docs: add RAG pipeline design"
   git push -u origin feature/rag-search
   ```
   Ожидаемый вывод третьей команды: `Switched to a new branch 'feature/rag-search'`, последней — строка `* [new branch]      feature/rag-search -> feature/rag-search`. **Как проверить:** `git log --oneline -1` показывает ваш коммит `docs: add RAG pipeline design`, а `git status` — `nothing to commit, working tree clean` или только файлы, которые вы не собирались коммитить.

   **Остальные участники** — после его `push`:
   ```
   git fetch
   git switch feature/rag-search
   ```
   Ожидаемый вывод: `Switched to a new branch 'feature/rag-search'` и `branch 'feature/rag-search' set up to track 'origin/feature/rag-search'.` Ключ `-c` здесь не нужен: git сам создаст ветку, связанную с веткой на сервере.

   **Если не получилось:**
   - PR практики 2 ещё не влит — команды не выполняйте: файл остаётся в рабочей папке и не теряется при переключении веток, пока он не закоммичен. Выполните их сразу после слияния; не успели до практики 3 — приходите с файлом в рабочей папке.
   - `git add` ответил `fatal: pathspec 'docs/rag-design.md' did not match any files` — файл лежит не в `docs/` или называется иначе: проверьте `git status`.
   - `git push` ответил `! [rejected] ... (non-fast-forward)` или `(fetch first)` и `Updates were rejected` — ветку уже запушил сокомандник. Отложите свой файл и возьмите его ветку:
     ```
     cp docs/rag-design.md ../rag-design-mine.md
     git switch main
     git branch -D feature/rag-search
     git fetch
     git switch feature/rag-search
     ```
     Перенесите свои правки из `../rag-design-mine.md` в `docs/rag-design.md` вручную, затем `git add docs/rag-design.md`, `git commit -m "docs: update RAG pipeline design"`, `git push`.
   - `git switch feature/rag-search` ответил `error: The following untracked working tree files would be overwritten by checkout: docs/rag-design.md` — у вас свой незакоммиченный файл. Отложите его: `mv docs/rag-design.md ../rag-design-untracked.md`, повторите `git switch feature/rag-search` и перенесите правки из `../rag-design-untracked.md` вручную, как в предыдущем пункте. Если файл с таким именем уже есть, возьмите другое имя.
   - Повторный запуск блока: `git switch main` ответил `error: Your local changes to the following files would be overwritten by checkout: docs/rag-design.md` или `git switch -c` — `fatal: a branch named 'feature/rag-search' already exists`. Ветка у вас уже есть, блок не повторяйте и `stash` не делайте. `git status` покажет, на какой вы ветке; если не на `feature/rag-search` — `git switch feature/rag-search` (без `-c`). Затем `git add docs/rag-design.md`, `git commit -m "docs: update RAG pipeline design"`, `git push -u origin feature/rag-search`. Если `git commit` ответил `nothing to commit, working tree clean` — правки уже в коммите, выполните только `git push`. Отказ `push` — см. пункт про `rejected` выше.
3. **Кандидат в эмбеддинги (10 мин).** В разделе «4. Эмбеддинги» — кандидат и запасной вариант по справке из `materials-3.md` с одной фразой «почему». Окончательное решение — в ADR 003 на практике 3.
4. **СРС до практики 3** — раздел «После воркшопа» в [`materials-3.md`](materials-3.md): ChromaDB, эмбеддинги Ollama, нарезка текста (около 45 минут).

## Связь с курсом «Конфигурирование приложений»

- Опираемся только на то, что есть в бэкенде к неделе 5: README, `CONTRIBUTING.md`, ADR, у некоторых — схема окружения. На неделе 6 «Конфигурирования» появятся (у кого-то, возможно, уже есть) `Dockerfile`, `compose.yaml`, `.env` с паролем базы и ADR 002 в статусе «Принято». Поэтому в схеме есть раздел «Обновление индекса» и deny-list в «Корпусе»: `.env` бэкенда не должен попасть в индекс ни на неделе 6, ни позже.
- pgvector — только в собственном контейнере помощника и только если Docker есть у всех в команде; БД бэкенда помощник не использует. Без Docker — ChromaDB, индекс лежит файлами в репозитории помощника.
- Новые настройки индекса (путь к хранилищу, модель эмбеддингов, `top_k`) — поля того же `AISettings` в `ai/config.py`, что и настройки инструментов практики 2, а не константы в коде.
