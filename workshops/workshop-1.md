# Воркшоп 1: От LLM к Агенту — Проектирование первого Tool

**Формат:** Нечётная неделя, 1 пара (2 академических часа = 90 минут)  
**Тип:** Лекция-семинар в формате перевернутого класса (Flipped Classroom)  
**Тема:** Что отличает агента от обычного вызова LLM? Проектирование инструментов (Tools).

> ⚠️ **Важно:** На этом занятии **нет кодинга**. Мы занимаемся анализом, проектированием, презентацией идей и рефлексией. Весь код будет написан на практикуме.

---

## 🎯 Цели воркшопа

После занятия студенты смогут:
1. **Анализировать** разницу между простым вызовом LLM и агентом (понимание концепции Agent Loop).
2. **Проектировать** интерфейс кастомного Tool (входы, выходы, обработка ошибок) для помощника разработчиков своего бэкенда.
3. **Оценивать** решения других команд через конструктивный Peer Review на уровне архитектуры.
4. **Планировать** реализацию Tool на предстоящем 4-часовом практикуме.

## 📚 Подготовка ДО занятия (Flipped Classroom)

**Время на самостоятельную работу:** 2–3 часа  
**Обязательные материалы:**

1. **Концепция агентов (30 мин):**
   - Статья: [What is an AI Agent?](https://www.datacamp.com/blog/ai-agent) — краткий обзор.
   - Видео: [AI Agents Explained](https://www.youtube.com/watch?v=F8NKVhkZZWI) (10 мин) — визуальное объяснение Agent Loop.

2. **Техническая подготовка (1–2 часа):**
   - Установить [Ollama](https://ollama.com/download) и запустить модель с возможностью **tools**: `ollama run qwen3:4b-instruct` (2,5 ГБ) или `qwen2.5:7b` (4,7 ГБ). Модели без возможности tools (в том числе `qwen2.5-coder`) для агента с инструментами не годятся: Ollama отклонит запрос.
   - *Альтернатива:* Получить ключ облачного провайдера с OpenAI-совместимым API — OpenRouter (бесплатные модели, регистрация без карты) или Yandex AI Studio.
   - Прочитать документацию: [CrewAI Tools Overview](https://docs.crewai.com/tools/overview) — понять, как описываются инструменты.

3. **Рефлексивный вопрос (подготовить ответ для команды):**
   - Бэкенд вашей команды появится на неделе 2 в курсе «Конфигурирование»; представьте, что он уже есть. Вы просите ИИ-помощника: «Напиши pytest-тест к эндпоинту, который возвращает запись по id, в нашем бэкенде». Модель ни разу не видела код этого бэкенда. Откуда она узнает, какой путь у этого эндпоинта, как называется функция-обработчик и есть ли такой эндпоинт вообще? Что ей нужно, кроме генерации текста? Нарисуйте схему взаимодействия: разработчик — помощник — модель — код бэкенда.

## 🏗️ Инженерная проблема (Problem-Based Learning)

**Контекст:**  
Мульти-агентная система, которую вы строите весь курс, — **помощник вашей команды разработчиков бэкенда** из курса «Конфигурирование»: он генерирует код и тесты, делает ревью, анализирует код. Помощник живёт в отдельном репозитории команды, а репозиторий бэкенда только читает; изменения в бэкенд попадают через Pull Request, который делают и принимают люди.

Разработчик пишет помощнику:  
> "Напиши тест к эндпоинту, который возвращает тикет по номеру"

Помощник уверенно выдаёт тест на `GET /api/v1/tickets/{id}` и импортирует `from app.models import Ticket`. В вашем бэкенде нет ни такого пути, ни такого модуля: модель собрала «типичный FastAPI-проект» из обучающих данных. Тест падает, а если его не запустить перед PR — падает уже в CI.

**Проблема:**  
LLM понимает запрос, но **не видит** код вашего бэкенда, а код меняется каждый день. Как заставить модель не угадывать эндпоинты, имена функций и сигнатуры, а **проверять** их в реальном коде перед тем, как писать код или тест?

**Вопросы для командного обсуждения:**
- Что должно быть "мостом" между LLM и кодом вашего бэкенда?
- Как LLM поймёт, что перед написанием теста нужно вызвать именно проверку эндпоинта, а не, например, поиск по документации?
- Как гарантировать, что помощник только читает код бэкенда и ничего в нём не меняет?

**Цель:** Синхронизировать группу, убедиться в готовности, сфокусировать внимание на проблеме.

### Блок 2: Командное проектирование (25 мин)

**Активность:** Работа в командах (3-4 человека)  
**Формат:** Мозговой штурм, рисование схем, написание псевдокода на доске/бумаге

**Задание для команд:**
Спроектировать **один** Tool для помощника разработчиков вашего бэкенда.
1. **Название и цель:** Что делает инструмент? Когда модель должна его вызывать, а когда нет?
2. **Входные параметры (Args):** Какие данные ему нужны? (Типы, обязательность, допустимые значения).
3. **Выходные данные (Returns):** В каком формате он вернет результат? (JSON, строка).
4. **Edge-cases:** Что произойдет, если передать некорректные данные или искомого нет в коде? Как Tool должен сообщить об ошибке агенту?

Бэкенда у команды пока нет: он появится на неделе 2 в «Конфигурировании» (`main.py` с `GET /` и `GET /health`), Tool проектируете под него. Если к практике 1 бэкенда не будет, Tool работает с учебным бэкендом `templates/sample-backend/` из репозитория курса.

**Ограничения первого Tool** (его вы реализуете на практике 1; те же четыре условия проверяются в её шаге 1.3):
- работает **с кодом бэкенда** и только **читает** его;
- **не принимает от модели путь к файлу** и не обходит всё дерево каталогов: какие файлы бэкенда читать, задаёт настройка помощника, модель передаёт только то, что ищет (метод и путь URL, имя функции или класса);
- не запускает ни код бэкенда, ни другие программы (линтер, тесты, git) — у таких инструментов свои опасности, их разбираем на воркшопе 2 и делаем на практике 2;
- в бэкенде к практике 1 уже есть то, что Tool ищет (на неделе 2 — `main.py` с `GET /` и `GET /health`): на практике Tool должен вернуть успешный ответ на настоящих данных, а не только ошибки.

*Пример — `find_endpoint`:*  
- Название: `find_endpoint`. Цель для модели: «Ищет в коде бэкенда обработчик HTTP-эндпоинта по методу и пути и возвращает имя функции, файл и строку. Вызывай, когда нужно убедиться, что эндпоинт существует, перед тем как писать к нему код или тест; не придумывай пути — бери их у пользователя».  
- Args: `path: str` (обязательно, начинается с `/`); `method: str` (необязательно, по умолчанию `GET`, одно из `GET`, `POST`, `PUT`, `PATCH`, `DELETE`).  
- Returns: JSON-строка. Успех: `{"status": "ok", "method": "GET", "path": "/health", "function": "health_check", "file": "main.py", "line": 17}`. Ошибка: `{"status": "error", "message": "...", "known": [...]}`.  
- Edge-cases: метод не из списка → ошибка с перечнем допустимых; путь без `/` → ошибка; эндпоинта нет → ошибка «эндпоинт не найден» и в `known` список найденных «МЕТОД путь», чтобы модель исправилась по реальным данным, а не придумала новый путь. Ни в одном случае Tool не падает с исключением.

Другие Tool, которые укладываются в ограничения: найти определение функции или класса по имени; вернуть сигнатуру функции (параметры и типы); узнать версию зависимости бэкенда. Tool вроде «перечислить поля Pydantic-модели» для практики 1 не подходит: моделей в бэкенде на неделе 2 ещё нет, успешный ответ получить не на чем. Можно взять `find_endpoint`, но тогда краевые случаи и описание для модели продумайте сами, а не перепишите отсюда.

**Цель:** Перевести абстрактную идею в конкретную техническую спецификацию перед написанием кода.

### Блок 3: Презентации и Peer Review идей (30 мин)

**Активность:** Публичные защиты проектов  
**Формат:** Каждая команда презентует свое решение, остальные задают вопросы

1. **Презентации (20 мин):**  
   - У каждой команды есть **3 минуты** на презентацию своего Tool.
   - Фокус на: зачем это нужно, как защищены входные данные, как агент поймет, когда это использовать.

2. **Peer Review идей (10 мин):**  
   - После каждой презентации другие команды задают по 1-2 уточняющих или критических вопроса.  
   - *Примеры хороших вопросов:* "А что если в коде нет того, что ищут? Ваш Tool вернет пустой JSON или ошибку? Как агент поймёт, что имя нужно спросить у пользователя, а не выдумать?", "Ваш Tool возвращает список — почему вы не ограничили его длину параметром `limit`?", "Где в вашей спецификации видно, что Tool только читает код бэкенда?"

**Цель:** Развить критическое мышление, найти слабые места в проектировании до написания кода, научиться аргументировать технические решения.

### Блок 4: Анализ, синтез и эталонные паттерны (10 мин)

**Активность:** Модерация преподавателя  
**Формат:** Обобщение лучших практик на основе услышанного

- Преподаватель не пишет код, но показывает **готовые схемы/слайды** с эталонными паттернами:
  1. **Паттерн "Безопасный возврат":** Tool никогда не бросает исключения (exceptions), которые крашат агента. Он всегда возвращает строку с описанием ошибки, которую LLM может "прочитать" и исправить свои действия.
  2. **Паттерн "Понятный Docstring":** Описание Tool написано не для программиста, а для LLM. Оно говорит, когда инструмент вызывать и когда нет, и перечисляет допустимые значения. Конкретное значение-пример (путь, идентификатор) в описание не ставят: маленькая модель подставит его, когда пользователь своё не назвал.
  3. **Паттерн "Структурированный вывод":** Предпочтение JSON перед свободным текстом для последующего парсинга.

**Цель:** Закрепить правильные ментальные модели проектирования агентных инструментов.

1. **Спецификация вашего Tool** — лист или фото доски: название и цель; описание для модели (когда вызывать); входные параметры с типами, обязательностью и допустимыми значениями; формат возврата; краевые случаи и что Tool возвращает при ошибке. Проверьте её по ограничениям первого Tool из блока 2. На практике 1 в шаге 1.3 вы запишете её в начало файла Tool, а в шаге 2.4 реализуете.
2. **Вопросы других команд к вашей спецификации** (блок 3) и ваше решение по каждому: исправить спецификацию или оставить как есть с объяснением почему.
3. **Три эталонных паттерна** из блока 4: безопасный возврат ошибки, docstring для модели, структурированный вывод. Проверьте по ним свою спецификацию.
4. **Правила работы с LLM в помощнике** (черновик AI Definition of Done, показан на занятии):
   - конфигурация модели (адрес, имя модели, температура) — в `.env` репозитория помощника через `pydantic-settings`;

   - основной путь — локальная Ollama, запасной — облачный провайдер с OpenAI-совместимым API (OpenRouter или Yandex AI Studio); переключение — только правкой `.env`, без изменения кода.
5. **Роли на практику 1:** кто начинает Driver, кто Navigator.

- На курсе "Конфигурирование" команда строит бэкенд на FastAPI; здесь — помощник для разработчиков этого бэкенда. - Требование к четким входным/выходным данным (JSON) продиктовано необходимостью строгой типизации, которую пропагандирует курс "Конфигурирование".
