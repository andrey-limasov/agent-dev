# Воркшоп 1: От LLM к Агенту — Проектирование первого Tool

**Формат:** Нечётная неделя, 1 пара (2 академических часа = 90 минут)  
**Тип:** Лекция-семинар в формате перевернутого класса (Flipped Classroom)  
**Тема:** Что отличает агента от обычного вызова LLM? Проектирование инструментов (Tools).

> ⚠️ **Важно:** На этом занятии **нет кодинга**. Мы занимаемся анализом, проектированием, презентацией идей и рефлексией. Весь код будет написан на практикуме.

---

## 🎯 Цели воркшопа

После занятия студенты смогут:
1. **Анализировать** разницу между простым вызовом LLM и агентом (понимание концепции Agent Loop).
2. **Проектировать** интерфейс кастомного Tool (входы, выходы, обработка ошибок) для своей предметной области.
3. **Оценивать** решения других команд через конструктивный Peer Review на уровне архитектуры.
4. **Планировать** реализацию Tool на предстоящем 4-часовом практикуме.

---

## 📚 Подготовка ДО занятия (Flipped Classroom)

**Время на самостоятельную работу:** 2–3 часа  
**Обязательные материалы:**

1. **Концепция агентов (30 мин):**
   - Статья: [What is an AI Agent?](https://www.datacamp.com/blog/ai-agent) — краткий обзор.
   - Видео: [AI Agents Explained](https://www.youtube.com/watch?v=F8NKVhkZZWI) (10 мин) — визуальное объяснение Agent Loop.

2. **Техническая подготовка (1–2 часа):**
   - Установить [Ollama](https://ollama.com/download) и запустить модель с возможностью **tools**: `ollama run qwen3:4b-instruct` (2,5 ГБ) или `qwen2.5:7b` (4,7 ГБ). Модели без возможности tools (в том числе `qwen2.5-coder`) для агента с инструментами не годятся: Ollama отклонит запрос.
   - *Альтернатива:* Получить ключ облачного провайдера с OpenAI-совместимым API — OpenRouter (бесплатные модели, регистрация без карты) или Yandex AI Studio.
   - Прочитать документацию: [CrewAI Tools Overview](https://docs.crewai.com/tools/overview) — понять, как описываются инструменты.

3. **Рефлексивный вопрос (подготовить ответ для команды):**
   - Представьте, что вы пишете чат-бота для Task Tracker. Пользователь говорит: "Создай задачу 'Купить молоко' с высоким приоритетом". Как LLM может выполнить это действие? Что ей нужно, кроме генерации текста? Нарисуйте схему взаимодействия.

---

## 🏗️ Инженерная проблема (Problem-Based Learning)

**Контекст:**  
Вы работаете над общим проектом (например, Task Tracker). Пользователь пишет в чат:  
> "Покажи все мои задачи с приоритетом 'high' и дедлайном на этой неделе"

**Проблема:**  
LLM (Qwen) может понять запрос, но она **не имеет доступа** к базе данных вашего приложения. Как заставить LLM не просто ответить текстом ("Я не могу это сделать"), а **выполнить действие** — получить реальные данные и вернуть их пользователю?

**Вопросы для командного обсуждения:**
- Что должно быть "мостом" между LLM и вашей системой?
- Как LLM поймёт, что ей нужно вызвать именно функцию получения задач, а не, например, отправки email?
- Как гарантировать, что агент не выполнит деструктивное действие (например, удаление) вместо безопасного чтения?

## 📋 План занятия (90 минут)

### Блок 1: Открытие и постановка проблемы (15 мин)

**Активность:** Общая дискуссия  
**Формат:** Преподаватель задаёт контекст, студенты активируют знания

1. **Проверка подготовки (5 мин):**
   - "У кого Ollama запустилась и модель работает? У кого есть API-ключ?"
   - "Кто прочитал документацию по Tools в CrewAI?"

2. **Формулировка проблемы (10 мин):**
   - Преподаватель озвучивает инженерную проблему (см. выше).
   - Краткий обзор концепции: LLM — это "мозг", но без "рук" (Tools) он беспомощен. Agent Loop — это цикл: Мысль → Действие (Tool) → Наблюдение → Ответ.

**Цель:** Синхронизировать группу, убедиться в готовности, сфокусировать внимание на проблеме.

---

### Блок 2: Командное проектирование (25 мин)

**Активность:** Работа в командах (3-4 человека)  
**Формат:** Мозговой штурм, рисование схем, написание псевдокода на доске/бумаге

**Задание для команд:**
Спроектировать **один** Tool, который понадобится вашему выпускному проекту.
1. **Название и цель:** Что делает инструмент?
2. **Входные параметры (Args):** Какие данные ему нужны? (Типы, обязательность).
3. **Выходные данные (Returns):** В каком формате он вернет результат? (JSON, строка).
4. **Edge-cases:** Что произойдет, если передать некорректные данные? Как Tool должен сообщить об ошибке агенту?

*Пример для Task Tracker:*  
- Название: `get_tasks_by_priority`  
- Args: `priority: str` (обязательно, one of: high, medium, low)  
- Returns: JSON-строка со списком задач или сообщение "Задачи не найдены".  
- Edge-case: Если передан приоритет "super-high", вернуть четкую ошибку валидации, а не падать с исключением.

**Цель:** Перевести абстрактную идею в конкретную техническую спецификацию перед написанием кода.

---

### Блок 3: Презентации и Peer Review идей (30 мин)

**Активность:** Публичные защиты проектов  
**Формат:** Каждая команда презентует свое решение, остальные задают вопросы

1. **Презентации (20 мин):**  
   - У каждой команды есть **3 минуты** на презентацию своего Tool.
   - Фокус на: зачем это нужно, как защищены входные данные, как агент поймет, когда это использовать.

2. **Peer Review идей (10 мин):**  
   - После каждой презентации другие команды задают по 1-2 уточняющих или критических вопроса.  
   - *Примеры хороших вопросов:* "А что если база данных вернет пустой список? Ваш Tool вернет пустой JSON или ошибку? Как агент это интерпретирует?", "Почему вы не сделали параметр `limit` для ограничения количества задач?"

**Цель:** Развить критическое мышление, найти слабые места в проектировании до написания кода, научиться аргументировать технические решения.

---

### Блок 4: Анализ, синтез и эталонные паттерны (10 мин)

**Активность:** Модерация преподавателя  
**Формат:** Обобщение лучших практик на основе услышанного

- Преподаватель не пишет код, но показывает **готовые схемы/слайды** с эталонными паттернами:
  1. **Паттерн "Безопасный возврат":** Tool никогда не бросает исключения (exceptions), которые крашат агента. Он всегда возвращает строку с описанием ошибки, которую LLM может "прочитать" и исправить свои действия.
  2. **Паттерн "Понятный Docstring":** Описание Tool написано не для программиста, а для LLM. Оно должно содержать примеры использования.
  3. **Паттерн "Структурированный вывод":** Предпочтение JSON перед свободным текстом для последующего парсинга.

**Цель:** Закрепить правильные ментальные модели проектирования агентных инструментов.

---

### Блок 5: Рефлексия и планирование практикума (10 мин)

**Активность:** Командное планирование  
**Формат:** Фиксация договоренностей

1. **Рефлексия (5 мин):**
   - "Какое самое неожиданное ограничение в проектировании Tools вы обнаружили сегодня?"
   - "Почему описание Tool (docstring) так же важно, как и его код?"

2. **Планирование практикума (5 мин):**
   - Команды фиксируют финальную спецификацию своего Tool.
   - Распределяют роли на практикум: кто будет Driver (писать код), кто Navigator (проверять документацию и логику).
   - **Домашняя задача:** Убедиться, что у всех членов команды к началу практикума работает Ollama или настроен API-ключ Qwen.

**Цель:** Четко поставить задачи на 4-часовой практикум, чтобы время было использовано максимально эффективно.

## 🔗 Связь с курсом "Конфигурирование приложений"

- Пока на курсе "Конфигурирование" команды настраивают Git, линтеры и базовую структуру FastAPI-приложения, здесь мы проектируем AI-компоненты, которые **должны** вписаться в эту структуру.
- Спроектированный сегодня Tool в будущем станет частью общего проекта. Например, если команда делает Task Tracker, то Tool `create_task` будет вызываться агентом, но **реально** задача будет создаваться через FastAPI-эндпоинт, который они пишут в параллельном курсе.
- Требование к четким входным/выходным данным (JSON) продиктовано необходимостью строгой типизации, которую пропагандирует курс "Конфигурирование".
