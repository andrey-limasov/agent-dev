### 1. Входной билет: корпус и пять вопросов к нему (30 мин)

Входной билет — начало вашей схемы RAG-пайплайна. На воркшопе вы допишете её до конца.

1. В репозитории помощника создайте файл `docs/rag-design.md` и скопируйте в него [каркас](#каркас-docsrag-designmd) целиком.
   **Не коммитьте его в `feature/code-tools`**: у схемы своя ветка `feature/rag-search`, она появится после слияния PR практики 2 (домашнее задание воркшопа). До тех пор файл просто лежит в рабочей папке.
2. Заполните в разделе «1. Корпус» только таблицу «Что индексируем»: документы бэкенда и документы помощника, по одной строке на файл — путь и о чём он одной фразой. Список Markdown-файлов бэкенда покажет команда из корня репозитория помощника (одинаково в PowerShell и Git Bash):
   ```
   git -C ../<проект> ls-files "*.md"
   ```
   Ожидаемый вывод — пути относительно корня бэкенда, по одному на строку, например:
   ```
   CONTRIBUTING.md
   README.md
   docs/adr/001-branching-strategy.md
   ```
   **Если не получилось:** `fatal: cannot change to '../<проект>'` — подставьте имя каталога бэкенда из `AI_REPO_ROOT` в `.env` помощника; пустой вывод — в бэкенде нет закоммиченных `.md`, работайте по абзацу «Если у бэкенда почти нет документации» ниже.
3. Заполните раздел «Проверочные вопросы»: **пять вопросов**, которые разработчик вашей команды реально задал бы помощнику и ответ на которые есть в документации. Для каждого — где ответ: файл и раздел (заголовок). Два правила:
   - формулируйте вопрос так, как спросили бы коллегу в чате, а не словами заголовка («как у нас называют ветки?», а не «Ветки»);
   - хотя бы у одного вопроса ответ должен лежать в двух местах (в двух разделах или двух файлах).
4. До начала пары пришлите в чат курса **сам файл** `docs/rag-design.md` (не ссылку: он ещё не закоммичен) и отдельной строкой — ссылку на PR практики 2.

**Если у бэкенда почти нет документации** (учебный `sample-backend`, или в бэкенде только README в несколько строк): корпус — [«Заметки»](#раздаточный-корпус-заметки) ниже плюс документация самого помощника (`README.md`, `docs/tools-spec-cycle2.md`, `docs/adr/`). Вопросы — к этим файлам. Это полноценный вариант: документация помощника по требованиям курса тоже источник знаний RAG.

На воркшопе эти пять вопросов понадобятся дважды: на этапе 2 вы проверите, какие из них найдёт обычный поиск по подстроке, а на практике 3 — станут проверочным набором для вашего RAG.

## После воркшопа, до практики 3 (СРС, ≈ 45 минут)

Это понадобится, когда вы будете строить индекс и Tool `search_docs`.

**ChromaDB**

- [Getting Started](https://docs.trychroma.com/docs/overview/getting-started) — вкладка Python, шаги от *Create a Chroma Client* до *Inspect Results*: `add` с `ids` и `documents`, `query` с `n_results`, что лежит в ответе (`distances`). 10 минут. Заметьте: Chroma возвращает `n_results` самых похожих чанков, даже если ни один на самом деле не подходит, — порога похожести по умолчанию нет.
- [Clients](https://docs.trychroma.com/docs/run-chroma/clients) — разделы *Persistent Client* и *In-Memory Client*: где хранится индекс на диске. 5 минут. Путь к индексу задавайте явно: значение по умолчанию у `PersistentClient` в документации и в установленной версии библиотеки может различаться.
- [Embedding Functions](https://docs.trychroma.com/docs/embeddings/embedding-functions) — раздел *Default: all-MiniLM-L6-v2* и таблица *All Embedding Functions*. 5 минут. Ollama в таблице для Python нет — для неё следующая ссылка.
- [Ollama Embeddings в Chroma](https://docs.trychroma.com/integrations/embedding-models/ollama) — `OllamaEmbeddingFunction` с параметрами `url` и `model_name`. 3 минуты. `model_name` указывайте всегда: по умолчанию это та же англоязычная MiniLM (`chroma/all-minilm-l6-v2-f32`). У функции есть параметр `timeout` (по умолчанию 60 с), а `add` отправляет все документы одним запросом: на CPU добавляйте чанки порциями по 10–20.
- [Metadata Filtering](https://docs.trychroma.com/docs/querying-collections/metadata-filtering) — первый пример с `where`: как искать только в одном источнике. 5 минут.

**Ollama**

- [Embeddings](https://docs.ollama.com/capabilities/embeddings) — эндпоинт `/api/embed` и раздел *Tips*: одна и та же модель для индексации и запросов. 5 минут.

**Нарезка текста**

- [LangChain: Text splitters](https://docs.langchain.com/oss/python/integrations/splitters/index) — три семейства (по структуре текста, по длине, по структуре документа), параметры `chunk_size` и `chunk_overlap`. 7 минут.
- [LangChain: MarkdownHeaderTextSplitter](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter) — заголовки разделов попадают в метаданные чанка; параметр `strip_headers`. 5 минут.

**Для любопытных (не обязательно)**

- [CrewAI: Memory](https://docs.crewai.com/en/concepts/memory) — разделы *Overview*, *Embedder Configuration* и *Privacy Note*. Нужен, чтобы решить в разделе 8 своей схемы, включать ли память CrewAI (см. справку ниже).

## Справка: модели эмбеддингов и Memory CrewAI

Модель эмбеддингов в курсе не задана: команда выбирает её сама и записывает решение в ADR 003 на практике 3. На воркшопе (раздел 4 схемы) достаточно назвать кандидата и запасной вариант по критериям ниже. Все факты — из документации по ссылкам выше и карточек моделей.

**Критерии.** Документация бэкенда — на русском. Машины команд — CPU, на одной из них уже работает `qwen3:4b-instruct` или `qwen2.5:7b`. Индексация и запрос должны использовать **одну и ту же** модель — или пару «документ / запрос» одного семейства, если её прямо предлагает провайдер (так у Yandex AI Studio). Векторы двух не связанных моделей несравнимы. Имя модели (или пары) — одна настройка, её читают и индексатор, и Tool поиска. Модель обрезает слишком длинный вход молча, без ошибки — значит, её предел длины (тот, с которым её запускает Ollama) ограничивает размер чанка сверху.

| Вариант | Как подключается | Язык | Размер загрузки | Предел входа | Что учесть |
|---|---|---|---|---|---|
| Встроенная функция ChromaDB, [`all-MiniLM-L6-v2`](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) | по умолчанию, если функцию эмбеддингов не указать | карточка модели помечена как англоязычная | ≈ 80 МБ, скачиваются автоматически при первом использовании | текст длиннее 256 word pieces обрезается | Ничего не настраивать, но для русской документации не подходит: на корпусе «Заметки» нужный раздел не попадает даже в три ближайших. Годится как базовая линия для сравнения |
| [`embeddinggemma`](https://ollama.com/library/embeddinggemma) через Ollama | `OllamaEmbeddingFunction` в Chroma или `/api/embed` | обучена на 100+ языках | 622 МБ | 2K токенов | Нужна Ollama v0.11.10 или новее. У запроса и документа разные префиксы — [карточка модели](https://ai.google.dev/gemma/docs/embeddinggemma/model_card), раздел *Prompt Instructions* |
| [`qwen3-embedding:0.6b`](https://ollama.com/library/qwen3-embedding) через Ollama | то же | 100+ языков | 639 МБ | 32K у модели; Ollama по умолчанию запускает её с контекстом 4096 токенов | Тег `latest` — это 8b (4,7 ГБ), для CPU указывайте `:0.6b` явно. На CPU индексирует в несколько раз медленнее `embeddinggemma` и занимает в памяти ≈ 2,4 ГБ, хотя файл модели почти того же размера. К запросу добавляется инструкция, без неё качество поиска падает на 1–5 % — [карточка модели](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) |
| [`bge-m3`](https://ollama.com/library/bge-m3) через Ollama | то же | 100+ языков | 1,2 ГБ | 8K | Самая тяжёлая из трёх локальных |
| Облачный провайдер | OpenRouter — [`POST /api/v1/embeddings`](https://openrouter.ai/docs/api-reference/embeddings), есть бесплатные модели с суффиксом `:free`; Yandex AI Studio — [пара моделей](https://aistudio.yandex.ru/docs/ru/ai-studio/concepts/embeddings) `text-search-doc` для документов и `text-search-query` для запросов | зависит от модели | — | зависит от модели | Весь корпус при индексации и каждый вопрос уходят провайдеру: это ещё один канал наружу (воркшоп 2). Индексация — по запросу на пачку чанков: на бесплатных моделях OpenRouter лимит запросов в сутки ([Limits](https://openrouter.ai/docs/api-reference/limits)); распространяется ли он на эмбеддинги, в документации не сказано. Условия хранения данных бесплатных моделей проверьте в карточке модели |

**Memory CrewAI** — обсуждаемый вариант, не требование курса. По [документации](https://docs.crewai.com/en/concepts/memory): включается `memory=True` у Crew; один класс `Memory` заменяет прежние отдельные виды памяти (краткосрочную, долгосрочную, сущностей); по умолчанию использует эмбеддинги OpenAI `text-embedding-3-large` — без своего эмбеддера нужен `OPENAI_API_KEY`, и текст памяти уходит в OpenAI вместе с запросами эмбеддингов; сохраняемое анализирует LLM; данные лежат на диске в базе LanceDB. Эмбеддер можно перенастроить на Ollama — пример есть в разделе *Embedder Configuration*. Документация описывает последнюю версию; в `crewai==1.15.22` из практики 1 при `memory=True` у Crew анализ выполняет LLM агента (у отдельно созданного `Memory()` по умолчанию — `gpt-5.4-mini`, в документации — `gpt-4o-mini`), а данные лежат не в `./.crewai/memory`, а в каталоге данных пользователя — на Windows `%LOCALAPPDATA%\CrewAI\<имя каталога проекта>\memory`, на macOS и Linux путь без `CrewAI` (`~/Library/Application Support/<имя каталога проекта>/memory`, `~/.local/share/<имя каталога проекта>/memory`) — или в `$CREWAI_STORAGE_DIR/memory`, если переменная задана.

### `docs/adr/001-in-memory-storage.md` (46 строк)

```text
 1  # ADR 001. Хранение заметок в памяти процесса
 2
 3  **Статус:** Принято
 4  **Дата:** 2026-09-20
 5  **Участники:** вся команда
 6
 7  ## Контекст
 8
 9  Сервис нужен как учебный объект: на нём команда отрабатывает работу
10  с репозиторием, Pull Request и инструменты анализа кода. Заметки не имеют
11  ценности, после перезапуска их никто не ищет. На старте у команды не было
12  времени настраивать базу, а у части участников нет Docker.
13
14  ## Рассмотренные варианты
15
16  1. **Словарь в памяти процесса.** Ноль зависимостей, запуск одной командой.
17  2. **SQLite-файл рядом с приложением.** Данные переживают перезапуск,
18     но появляются миграции и файл, который легко случайно закоммитить.
19  3. **PostgreSQL в контейнере.** Как в настоящем проекте, но нужен Docker
20     у каждого участника и отдельная настройка подключения.
21
22  ## Решение
23
24  Выбран вариант 1: заметки лежат в словаре `notes` в модуле `main.py`,
25  ключ — целое число. Вариант 3 откладываем, пока Docker есть не у всех.
26
27  ## Последствия
28
29  Плюсы:
30  - запуск без внешних сервисов, тестам не нужна база;
31  - код хранения занимает несколько строк, его легко читать.
32
33  Минусы:
34  - все заметки теряются при перезапуске сервера;
35  - нельзя запускать несколько процессов: у каждого будет свой словарь;
36  - номер новой заметки — наибольший существующий плюс один: если удалить
37    заметку с наибольшим номером, этот номер получит следующая созданная,
38    и клиент, сохранивший старый номер, удалит чужую заметку;
39  - при переходе на базу придётся заменить словарь слоем доступа
40    к данным во всех обработчиках.
41
42  ## Когда пересмотреть
43
44  - Заметки понадобятся после перезапуска.
45  - В проекте появится Docker Compose с базой данных.
46  - Сервис начнут запускать с несколькими воркерами.
```

24  - Python 3.11–3.13, своё виртуальное окружение `.venv` в корне репозитория.
25  - Зависимости: `pip install fastapi uvicorn`. Файл со списком зависимостей
26    появится, когда команда выберет менеджер зависимостей.
27  - Каталог `.venv` в репозиторий не попадает: он указан в `.gitignore`.
28  - Новая зависимость добавляется в том же Pull Request, где она понадобилась.

30  ## Настройки окружения
31
32  Сейчас у сервиса нет значений, которые нельзя публиковать. Когда они появятся
33  (например, ключ внешнего сервиса), они хранятся только в локальном файле `.env`
34  в корне репозитория. Файл `.env` указан в `.gitignore` и не коммитится никогда.
35  В репозиторий кладётся `.env.example` с теми же именами переменных и пустыми
36  значениями, чтобы новый участник знал, что заполнить.
37
38  Если значение всё же попало в коммит, удалить строку недостаточно: значение
39  считается скомпрометированным, его отзывают и выпускают новое.

41  ## Проверки перед Pull Request
42
43  Перед тем как открыть Pull Request, автор проверяет у себя:
44
45  1. Ветка обновлена от `main`, конфликтов нет.
46  2. Сервер запускается командой `uvicorn main:app` без ошибок.
47  3. `GET /health` отвечает `{"status": "healthy"}`.
48  4. Новые эндпоинты добавлены в таблицу «Эндпоинты» в `README.md`.
49  5. У новых функций есть docstring в одну строку.
50  6. Если в репозитории есть каталог `tests/`, тесты проходят: `python -m pytest -q`.
51  7. Линтер не находит ошибок: `ruff check .`.
52  8. В изменениях нет файла `.env` и отладочных `print`.
53  9. Сообщения коммитов соответствуют разделу «Коммиты».

58  - В описании: что изменено, как проверить, ссылка на задачу.

66  в ревью не обсуждаются.
