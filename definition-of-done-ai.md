# Definition of Done (DoD) для AI-части проекта

**Курс:** Мульти-агентная разработка приложений  
**Формат:** Командный проект (интегрирован с курсом "Конфигурирование")  

---

## Критерии завершенности AI-компонентов

AI-часть проекта считается завершенной и готовой к интеграции и защите, если выполнены **ВСЕ** следующие требования:

---

### 1. Архитектура и оркестрация агентов

- [ ] Реализована мульти-агентная система (Crew) из **минимум 2-х специализированных агентов**.
- [ ] Каждый агент имеет четко определенные: `role`, `goal`, `backstory`.
- [ ] Выбран и обоснован паттерн оркестрации (Sequential или Hierarchical).
- [ ] Агенты успешно передают контекст и результаты друг другу без потери критической информации.

---

### 2. Инструменты (Tools) и Function Calling

- [ ] Реализовано **минимум 2 кастомных инструмента** (Python-функции с декоратором `@tool` или аналогом).
- [ ] **Обязательно:** Реализован инструмент для работы с кодом/файлами проекта (например, `read_file`, `search_codebase`, или запуск `ruff`/`mypy` для самопроверки).
- [ ] Все инструменты имеют подробные описания (`description`), позволяющие LLM корректно выбирать их для использования.
- [ ] Реализована обработка ошибок внутри инструментов: агент получает читаемое сообщение об ошибке и может предпринять альтернативное действие, а не падает с исключением.

---

### 3. Retrieval-Augmented Generation (RAG)

- [ ] Реализован пайплайн RAG с использованием векторной БД (ChromaDB или pgvector).
- [ ] Данные для RAG (документация, бизнес-правила, исторические данные) корректно разбиты на чанки (chunking) и векторизованы.
- [ ] Агент использует Tool для семантического поиска в RAG перед генерацией финального ответа.
- [ ] В промпт агента явно добавлена инструкция опираться на найденный контекст и указывать источники (если применимо).

---

### 4. Конфигурация и управление моделями

- [ ] API-ключи и названия моделей **НЕ** захардкожены в коде.
- [ ] Используется `pydantic-settings` (или аналог) для управления конфигурацией LLM.
- [ ] Поддерживается переключение между как минимум двумя режимами через переменные окружения:
  - Облачный провайдер с OpenAI-совместимым API (например, OpenRouter или Yandex AI Studio).
  - Локальный провайдер (например, Ollama с моделью `qwen3:4b-instruct` — обязательно модель с возможностью tools).
- [ ] Приложение корректно обрабатывает ситуацию, когда локальная модель недоступна (fallback на облако или понятная ошибка).

---

### 5. Интеграция с основным приложением

- [ ] AI-функционал интегрирован в основное FastAPI-приложение (не является изолированным консольным скриптом).
- [ ] Создан как минимум один защищенный эндпоинт (например, `POST /api/ai/analyze`), который запускает агентную систему и возвращает результат.
- [ ] Время выполнения агентного сценария ограничено (timeout), чтобы не блокировать HTTP-запросы бесконечно. Для долгих задач реализован асинхронный паттерн или фоновая задача.

---

### 6. Тестирование и надежность

- [ ] Написаны unit-тесты для всех кастомных Tools (без вызова LLM).
- [ ] Написаны интеграционные тесты для Crew/агентов с **обязательным мокированием (mocking)** ответов LLM.
- [ ] В CI/CD пайплайне (настроенном в курсе "Конфигурирование") тесты AI-компонентов запускаются и проходят успешно.
- [ ] Реализован механизм Retry (минимум 2 попытки) при сбое вызова LLM или инструмента.
- [ ] Вывод агента, который передается дальше в систему, валидируется через Pydantic-модель (Structured Output).

---

### 7. Observability и логирование

- [ ] Настроено структурированное логирование шагов агентов (ReAct traces: Thought, Action, Observation, Final Answer).
- [ ] Логи включают идентификатор запроса (Request ID) для отслеживания конкретного вызова.
- [ ] (Рекомендуется) Интегрирована простая система визуализации трасс (например, LangFuse или кастомный логгер, выводящий цепочку в читаемом виде).

---

### 8. Документация

**В README.md (основного проекта) добавлен раздел "AI-компоненты":**
- [ ] Описание бизнес-сценария, который решают агенты.
- [ ] Список агентов и их ролей.
- [ ] Описание доступных Tools и как их вызвать.
- [ ] Инструкция по настройке переменных окружения для LLM (облачный провайдер / Ollama).
- [ ] Пример запроса к AI-эндпоинту и ожидаемый ответ.

**Architecture Decision Records (ADR):**
- [ ] Добавлен минимум **1 ADR**, посвященный AI-архитектуре, содержащий:
  - Контекст: какую бизнес-задачу решаем с помощью AI.
  - Решение: выбранный фреймворк (CrewAI/LangChain), модель, паттерн оркестрации.
  - Обоснование: почему выбрано это решение (сравнение с альтернативами).
  - Последствия: ограничения, затраты токенов, сложность поддержки.

**Промпт-гайдлайны:**
- [ ] Промпты агентов вынесены в отдельные файлы или константы, а не разбросаны по коду.
- [ ] Промпты содержат четкие инструкции по формату вывода и обработке крайних случаев.

---

## Чек-лист для самопроверки перед защитой

Перед защитой команда должна убедиться, что:

- [ ] Переменная окружения переключает модель между облачным провайдером и локальной Ollama без изменения кода.
- [ ] При отключении интернета (или имитации ошибки API) срабатывает fallback или выдается понятная ошибка, а не stack trace.
- [ ] Тесты с моками LLM проходят стабильно и быстро (менее 5 секунд).
- [ ] Агент успешно использует Tool для чтения файла или поиска по коду в рамках демонстрации.
- [ ] RAG выдает релевантный ответ на вопрос по документации проекта.
- [ ] В логах видна цепочка рассуждений агента (Thought -> Action -> Observation).
- [ ] ADR по AI-архитектуре написан и соответствует действительности.

---

## Примечания

1. **Стабильность важнее "магии".** Лучше простой агент, который стабильно возвращает валидный JSON и корректно использует Tools, чем сложный агент, который иногда галлюцинирует и ломает пайплайн.
2. **Мокирование обязательно.** Реальные вызовы LLM в CI/CD запрещены, так как они делают пайплайн медленным, нестабильным и зависимым от внешних сервисов.
3. **Интеграция — ключ к успеху.** AI-часть не оценивается изолированно. Она должна быть частью единого приложения, удовлетворяющего DoD курса "Конфигурирование".
